# Расследование: почему при выделении нескольких чекбоксов + «пробел» в PENDING_EDITS попадает только ОДНА позиция

> Отчёт сохранён в `project_info__66.md`. Ниже — суть и места, где нужно менять код. Я в **Explore Mode** — реализацию делать не могу; правки — в **Act Mode**.

---

## 0. Краткий ответ

Система определяет, **какие позиции изменились, ТОЛЬКО из объекта события `onEdit`** — `e.range` (строки/колонки), `e.value`, `e.values` и запасного `range.getValues()` (см. `v12CaptureCheckboxEdit` и `v12CaptureDeficitEdit` в `v12_queue.js`).

Когда вы **выделяете несколько чекбоксов и нажимаете «пробел»**, Google Sheets выполняет это как **ОДНУ правку** и вызывает `onEdit` **один раз**. В «одиночной» форме события `range.getNumRows()`/`getNumColumns()` возвращают `1`, а `e.values` не заполняется (он бывает только у «вставки»). Из-за этого код идёт по ветке `singleCell === true`, берёт значение **одной** ячейки и пишет **ровно одну** строку в очередь.

Итог: «одно событие → одна позиция» — это и есть «программа считает это за одно изменение».

Существующая «страховка» `v12ReconcilePendingHandoffs()` → `v12RebuildPendingFromChecked()` лечит это **только для чекбоксов HANDOFF** (ОТБОРКА / WORKING BOM). Для колонки **«Реальная поставка» (`REAL_DELIVERY`) в «Сводке дефицитов» страховки НЕТ** — там «одна позиция» воспроизводится стабильно.

## 1. Механизм захвата правки чекбокса

Точка входа — `v12OnEdit(e)` (`v12_trigger.js`) → быстрый путь:

```js
if (v12CaptureCheckboxEdit(e, name)) { return; }  // фиксирует намерение
```

`v12CaptureCheckboxEdit` (`v12_queue.js`):

```js
const singleCell = (numRows === 1 && numCols === 1);
const values = singleCell
  ? [[e.value !== undefined ? e.value : range.getValue()]]
  : ((e.values && e.values.length === numRows) ? e.values : range.getValues());
...
for (let r = 0; r < numRows; r++) { /* одна строка очереди на строку диапазона */ }
```

**Ключ проблемы:** если событие сообщает `numRows === 1` (а при массовом переключении это так), идёт «одиночная» ветка → значение **одной** ячейки → цикл выполняется **один раз** → одна строка `PENDING_EDITS`.

Для «Сводки дефицитов» аналог — `v12CaptureDeficitEdit(e)`: **точно та же логика** выбора `values` и тот же цикл по `numRows`.

---

## 2. Почему это «одно изменение» — поведение Google Sheets

- Простой триггер `onEdit` вызывается **один раз на действие пользователя**. «Выделить диапазон + пробел» — это одно действие.
- В таком событии `e.values` обычно `undefined` (заполняется только при «вставке»), а `e.value` — значение одной (активной) ячейки. То есть событие **не перечисляет** все переключённые ячейки.
- Единственный надёжный способ узнать, что стало отмечено, — **прочитать фактическое состояние колонки с листа** (это уже реализовано как `v12RebuildPendingFromChecked` — но лишь для HANDOFF).

> Это та же корневая причина, что описана в `project_info__59.md`/`__60.md` («Google „глотает“ всплески onEdit при массовой отметке»).

## 3. Где именно теряются позиции

| Слой | Файл / функция | Роль в дефекте |
|---|---|---|
| Триггер | `v12_trigger.js` → `v12OnEdit` | Получает **единственный** `onEdit` |
| Захват HANDOFF | `v12_queue.js` → `v12CaptureCheckboxEdit` | Берёт `numRows`/`values` из события → 1 строка |
| Захват Сводки | `v12_queue.js` → `v12CaptureDeficitEdit` | То же + **нет никакой реконсиляции** |
| Страховка HANDOFF | `v12_queue.js` → `v12ReconcilePendingHandoffs` / `v12RebuildPendingFromChecked` | Читает фактические галочки ОТБОРКИ/WORKING BOM → баг маскируется для HANDOFF |
| Ввод в очередь | `v12_queue.js` → `v12EnqueuePendingRows` | UPSERT по ключу `SOURCE\|POSITION_ID\|FIELD` |

**Ключевая асимметрия (подтверждено чтением кода и поиском):**

- `v12ReconcilePendingHandoffs()` вызывается **в конце** `v12CaptureCheckboxEdit`;
- `v12CaptureDeficitEdit(e)` **завершается без реконсиляции**:

```js
if (pendingRows.length) { v12EnqueuePendingRows(pendingRows); }
return true;   // ← никакой v12Reconcile* для REAL_DELIVERY / ORDERED_QTY / EXPECTED_DATE
```

**Следствие:**
- **ОТБОРКА / WORKING BOM (HANDOFF):** скорее всего «самолечится» (реконсиляция добёрет все галочки).
- **Сводка дефицитов («Реальная поставка»):** в очереди останется **одна** позиция при любом размере выделения — **это и есть воспроизводимый дефект**.

Факторы, усугубляющие «одну строку» и там, где страховка есть: реконсиляция при занятом локе **тихо возвращает `null`**; она умеет только «галочка стоит ⇒ HANDOFF», не выражает «снятие»; если событие пришло с колонкой, не пересекающей колонку чекбокса, захват возвращает `false` до вызова реконсиляции.

## 4. Как убрать некорректное поведение (для Act Mode)

Принцип: **не выводить список позиций из формы события, а перечитывать фактическое состояние колонки.**

**Вариант A (рекомендуемый):** обобщить `v12RebuildPendingFromChecked` на колонку **«Реальная поставка»** (`DEFICIT_COLUMNS.REAL_DELIVERY = 12`, источник `SOURCE_UI.DEFICIT_SUMMARY`) и вызвать реконсиляцию **в конце `v12CaptureDeficitEdit`** — по образцу `v12CaptureCheckboxEdit`. Тогда «одна позиция» → «все фактически отмеченные», UPSERT-идемпотентность сохраняется.

**Вариант B (дополнение):** перечислить фактически выделенные диапазоны через `SpreadsheetApp.getActiveRangeList().getRanges()` (даёт точный набор, в т.ч. несмежных) — но сервис в триггере может быть недоступен/не отражать выделение.

**Вариант C:** сменить «точный захват» на «replace-семантику» — полностью перестраивать PENDING-множество поля по состоянию колонки (по сути A для всех полей).

**Что не сломать:** UPSERT по ключу `SOURCE|POSITION_ID|FIELD` (иначе вернутся дубли «снял → поставил»); фиксация «снятия» через `VALUE=false` (`v12IsBooleanPendingField`); проверку прав `v12CanEditField(role, "REAL_DELIVERY")`.

| Файл | Что менять |

| `v12_queue.js` → `v12CaptureDeficitEdit` | В конце вызвать реконсиляцию для REAL_DELIVERY |
| `v12_queue.js` → `v12RebuildPendingFromChecked` | Обобщить: добавить источник `DEFICIT_SUMMARY` / поле `REAL_DELIVERY` |

| `v12_trigger.js` → `v12OnEdit` | (Опц.) при «одиночной» форме события на чекбокс-колонке уходить в реконсиляцию |
| `_local_tests/*` | Тест: массовые (в т.ч. **несмежные**) чекбоксы → строк в очереди = числу галочек; отдельно для REAL_DELIVERY |

## 6. Почему тесты «зелёные», а баг есть

`_local_tests/v12_queue_capture_fix_test.js` подаёт событие функцией `rangeEvent(sheet, firstRow, numRows, col, values)`, где `numRows` **уже** равен числу строк (F5: `rangeEvent(PK, 2, 5, K.CHECKBOX, maskValues)`). Реальное поведение «пробела по выделению» (когда приходит одиночное событие) не воспроизводится. Нужен тест, который ставит галочки **на листе**, а через `v12OnEdit` подаёт событие **одной** ячейки и ожидает все отмеченные в очереди.

## 7. Что можно сделать прямо сейчас (без правки кода)

- **ОТБОРКА/WORKING BOM:** после массовой отметки «пробелом» → меню **«BOM CONTROL V12» → «♻ Пересобрать очередь (по галочкам)»** (`v12RebuildPendingFromCheckedUI`) либо сразу «Применить» — HANDOFF-галочки доберутся.
- **Сводка дефицитов («Реальная поставка»):** авто-добора нет — отмечать по одной либо дождаться исправления (Вариант A).

## 8. Контекст

- Колонки-чекбоксы: `PICKING.CHECKBOX = 12`, `WORKING_BOM.CHECKBOX = 14`, `DEFICIT_COLUMNS.REAL_DELIVERY = 12`, `DASHBOARD.DONE = 1`.
- Dashboard «Выполнено» — только одиночная ячейка (`v12HandleDashboardEdit` откатывает диапазоны) — осознанно.
- Модель — «V3 Применить»: `onEdit` только фиксирует намерение, применение — вручную (`v12ApplyChanges` → `v12DrainPendingEdits`).
- Проекции при пересборке пишут в чекбоксы `false` (`v12RefreshPicking` / `v12RefreshWorkingBOM`), поэтому «добор по факту галочек» работает только если лист не пересобран между отметкой и «Применить».

**Резюме:** корень — вывод списка из **единичного** `onEdit`; HANDOFF спасает реконсиляция, а **Сводку дефицитов («Реальная поставка») — нет**. Минимальная правка: обобщить `v12RebuildPendingFromChecked` на `REAL_DELIVERY` и вызвать реконсиляцию в конце `v12CaptureDeficitEdit`, сохранив UPSERT и RBAC.
