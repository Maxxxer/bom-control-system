# BOM CONTROL SYSTEM V12 — Расследование: «массовая отметка чекбоксов „Реальная поставка“ отмечает только первую позицию»

## Краткое описание симптома
При массовой отметке чекбоксов **«Реальная поставка»** в листе «Сводка дефицитов» (`DEFICIT_SUMMARY`) в центральное состояние (`POSITION_STATE`) попадает отметка **только первой** позиции. Остальные отмеченные строки:
- остаются в «Сводке дефицитов» (не убираются),
- их чекбоксы снова показываются снятыми.

Одиночная отметка одного чекбокса работает.

## Цепочка обработки (актуальный код)

Точка входа — простой/установленный триггер `v12OnEdit(e)` (`v12_trigger.js`):

1. `isActionable` включает `DEFICIT_SUMMARY`.
2. `isSingleCell = e.range.getNumRows()===1 && e.range.getNumColumns()===1`.
   `isSummaryRange = !isSingleCell && name === DEFICIT_SUMMARY`.
3. Далее:
   - **одиночная ячейка** → `v12HandleDeficitEdit(e)`; ветка `column === D.REAL_DELIVERY` (кол. 12) →
     `v12SetRealDeliveryQty(positionId, checked ? required : 0)`;
   - **диапазон** → `v12HandleDeficitRangeEdit(e)` — проходит все строки диапазона, собирает `writes` и пишет одним `batchWrite`.

`v12SetRealDeliveryQty` (`v12_operations.js`) в конце вызывает `v12RefreshProjections()`.
`v12HandleDeficitRangeEdit` в конце вызывает `v12RefreshDeficitSummary()`, `v12RefreshPicking()`, `v12RefreshWorkingBOM()`, `v12RefreshSupply()`, `v12RefreshDashboard()`.

## Корневая причина (структурная)

Каждая обработанная правка чекбокса завершается **полной пересборкой** «Сводки дефицитов». В `v12RefreshDeficitSummary()` (`v12_projections.js`):

```js
v12ClearBody("DEFICIT_SUMMARY");          // clearContent + clearDataValidations по телу листа
if (rows.length) v12WriteRows("DEFICIT_SUMMARY", 2, rows);
v12InstallDeficitCheckboxes(rows.length); // clearDataValidations + setDataValidation заново
v12ApplyDeficitColors(rows);
```

То есть лист сводки **полностью очищается и создаётся заново**. При этом:
- строка чекбокса формируется в `v12BuildDeficitRow()`, где колонка «Реальная поставка» **жёстко зашита как `false`**:
  ```js
  false, // REAL_DELIVERY checkbox
  ```
- строки, ставшие неактивными (`v12IsDeficitRowActive === false`), из сводки удаляются, а оставшиеся **сдвигаются вверх**.

Последствия при массовой отметке:
1. Любая обработанная правка **затирает состояние чекбоксов всех ещё активных строк** — они перезаписываются как `false`, валидация переустанавливается. Отметки, которые пользователь уже проставил, но которые ещё не перенесены в `POSITION_STATE`, теряются.
2. Удаление отмеченных строк **сдвигает нумерацию**. Если правки приходят несколькими событиями (клик по каждому чекбоксу), последующие события читают `sheet.getRange(row, D.POSITION_ID)` уже на сдвинутых строках — отметка «попадает не туда» либо теряется.
3. В итоге «доживает» только первая обработанная отметка; остальные строки снова отображаются со снятым чекбоксом и остаются в сводке.

## Почему локальный тест НЕ воспроизводит проблему

Локальный диагностический тест `_local_tests/v12_delivery_test.js` (сценарий S5 «массовая отметка») подаёт **одно** событие-диапазон с `numRows = 3` и значениями `TRUE`. Обработчик `v12HandleDeficitRangeEdit` успевает пометить все три строки **одним проходом до пересборки**, поэтому тест проходит (24/24 PASS). Мок не воспроизводит реальный сценарий, когда отметки приходят **несколькими отдельными событиями `onEdit`** и между ними успевает отработать полная пересборка сводки из предыдущего события.

## Дополнительные факторы, усиливающие симптом

- **`v12BuildDeficitRow`: `false` для чекбокса** — проекция не отражает сохранённое состояние; при любой пересборке чекбокс снят, даже если отметка успела сохраниться.
- **`v12SetRealDeliveryQty` пересчитывает ВСЕ проекции** (`v12RefreshProjections` → DeficitSummary + Picking + WorkingBOM + Supply + Dashboard) — дорого и избыточно для одной строки; увеличивает окно, в котором параллельные правки конфликтуют.
- **Нет межсобытийной сериализации.** `acquireScriptLock()` (`lock.js`) реентрантный только внутри одного исполнения (глобальный `_lockDepth`), а каждое событие `onEdit` — отдельное исполнение. Правки, пришедшие подряд, не выстраиваются в очередь и перетирают результат друг друга через полную пересборку.
- **`v12HarvestDeficitInput()`** вызывается в начале каждой пересборки, читает лист сводки целиком — при частично отмеченных строках это ещё один источник «мигания» состояния.

## Рекомендации (для режима Act — изменения кода здесь не вносятся)

1. **Не пересобирать весь лист сводки при отметке чекбокса.** Обновлять/удалять **только затронутую строку** (по аналогии с существующей точечной `v12RefreshDeficitSummaryRow`), а не `clearBody` + `writeRows`. Это сохранит состояние чекбоксов соседних строк и исключит сдвиг нумерации.
2. **Сделать колонку «Реальная поставка» производной от состояния** — выводить значение на основе `POSITION_STATE` (например, `REAL_DELIVERY_QTY > 0` или отдельный флаг «отмечено»), а не константу `false`. Тогда пересборка не будет «терять» отметки.
3. **Точечный пересчёт проекций.** Для одиночной отметки обновлять только сводку (и, при необходимости, Supply/Dashboard), не гоняя все пять проекций.
4. **Разобраться с доставкой массовой отметки.** Для операции отметки диапазона чекбоксов убедиться, что обработчик получает все строки (`e.values` / `e.range.getValues()`, диапазон `firstRow..firstRow+numRows`). Если Google Sheets доставляет отметку **по одному событию на ячейку**, решение п.1 (точечное обновление строки, без полной пересборки) обязательно — иначе события будут перетирать друг друга.
5. **Опционально — буферизация правок.** Накопление правок с отложенной пересборкой (по времени/по завершении серии правок), чтобы серия отметок чекбоксов обрабатывалась одним проходом.

## Дополнение (этап 2): та же проблема в «Отборке» (PICKING)

### Проверка
В листе ОТБОРКА массовая отметка чекбоксов передачи **вообще не обрабатывалась**: `v12OnEdit` пропускал диапазоны (`isSummaryRange` был только для `DEFICIT_SUMMARY`), то есть при выделении нескольких чекбоксов и простановке отметок не срабатывал ни один. Плюс одиночные отметки, как и в сводке, затирались полной пересборкой листа отборки (`v12RefreshPicking`: `clearBody` + `writeRows`) и строки сдвигались.

### Что исправлено
1. `v12_trigger.js`:
   - в `v12OnEdit` добавлен признак `isPickingRange` — диапазонные правки ОТБОРКИ теперь обрабатываются (а не отбрасываются);
   - добавлен `v12HandlePickingRangeEdit(e)` — обходит ВСЕ отмеченные строки диапазона и вызывает передачу для каждой; пересчёт проекций делается один раз в конце; заблокированные строки снимают отметку.
2. `v12_handoff.js`: у `v12MarkReceivedByProduction(positionId, sourceUI, skipRefresh)` появился параметр `skipRefresh` — при массовой передаче проекции не пересчитываются на каждую строку.
3. `v12_projections.js`: добавлен `v12HarvestPickingInput()` — вызывается в начале `v12RefreshPicking()` и подбирает «зависшие» отметки передачи (строка отмечена в листе, но передача не зафиксирована), идемпотентно выполняя передачу ДО перезаписи листа. Аналог `v12HarvestDeficitInput` для сводки.

### Проверка
Локальный тест `_local_tests/v12_delivery_test.js`, сценарий S9: диапазонная отметка трёх чекбоксов передачи в ОТБОРКЕ → передача вызвана для всех трёх позиций (уникальных = 3). Итог по всем сценариям: **37/37 PASS**; `node --check` по всем 19 js-файлам — OK.
