# Дубли в PENDING_EDITS при массовой отметке (после сканирующего захвата)

> Пользователь: «Теперь позиции в edit pending при массовой отметке чекбоксов иногда задваиваются». Причина — в самом сканирующем захвате (Fix «38→38»): он пишет в очередь ВСЕ отмеченные строки на КАЖДОЕ событие, из-за чего перекрывающиеся исполнения `onEdit` создают дубли.

## Что подтверждено по коду
- Триггер ровно один: `ScriptApp.newTrigger("v12OnEdit").onEdit()` (`v12_trigger.js`). Отдельной `function onEdit` (simple trigger) нет — двойного вызова нет.
- Писатели `PENDING_EDITS`: `v12EnqueuePendingRows` (append/update), `v12MarkPendingProcessed` (status), `v12PurgeDonePendingEdits` (rewrite). Последние два — только внутри `v12DrainPendingEdits` под локом.
- **`v12EnqueuePendingRows` пишет строки (append/update), но НЕ вызывает `SpreadsheetApp.flush()`** перед снятием лока. `flush()` есть только в `v12DrainPendingEdits` и `v12_operations.js`, но не в пути захвата.

## Механизм дублей
Сканирующий захват на каждое событие:
1. читает ВСЮ колонку ОТБОРКИ и строит намерения для **всех** стоящих галочек (не только для редактируемых строк);
2. в `v12EnqueuePendingRows` под локом читает очередь, делит на `updates` (ключ уже есть как PENDING) и `appends` (нет), пишет.

Дубли возникают, когда **два исполнения `onEdit` перекрываются** (массовая отметка = много быстрых событий):
- событие A сканирует → собирает N отмеченных строк;
- событие B (почти одновременно) сканирует → собирает те же N;
- по локy они выполняются по очереди, НО второе читает очередь, **не видя ещё записи первого** (запись не была `flush`-нута, а исполнение первого ещё не завершилось). Для него ключей «нет» → **append** → те же позиции добавляются второй раз.

Сканирующий захват **усиливает** проблему: раньше на событие писалось ~1 намерение (строка правки), теперь — **все отмеченные** (десятки), поэтому окно перекрытия и объём совпадающих записей резко выросли. Отсюда «иногда задваиваются» (a не всегда — зависит от того, совпали ли исполнения).

Дополнительно: upsert матчит только `PENDING`-строки и обновляет **одну** (последнюю) из совпадающих; если дубли уже появились, они не «схлопываются» автоматически — повторное применение их лишь обновляет, оставляя визуальные дубли.

## Как правильно (надёжная схема без дублей и без потерь)
Нельзя одновременно (а) писать «все отмеченные» на каждое событие и (б) гарантировать отсутствие дублей при перекрытии — это противоречивые требования при отсутствии атомарного «read-modify-write» между исполнениями.

Рекомендуемая схема — **разделить «фиксацию» и «пересборку»**:

1. **Точный захват (onEdit) — только редактируемые строки.** Вернуть `v12CaptureCheckboxEdit` к обработке **строк события** (значение true/false по `e.values`/`e.value`). Дубли при этом невозможны по построению: каждое событие добавляет/обновляет строго свои строки, а upsert по ключу идемпотентен. Потеря «не доехавших» событий здесь возможна, но её закрывает п.2 и п.3.

2. **Реконсиляция при Apply (уже есть) — без записи в очередь.** `v12ReconcileCheckedHandoffs` добавляет **синтетические** намерения (row:0) только в момент применения; в лист `PENDING_EDITS` ничего не пишется → дублей не создаёт. Гарантия «галочка стоит ⇒ позиция будет передана» сохраняется.

3. **Явная ПЕРЕСБОРКА очереди по кнопке/пункту меню — детерминированная и идемпотентная.** Новая `v12RebuildPendingFromChecked()`:
   - читает все отмеченные строки ОТБОРКИ и WORKING BOM (`Position ID` + `CHECKBOX`);
   - **полностью перезаписывает** множество `PENDING`-намерений HANDOFF: по каждому ключу `SOURCE|POSITION_ID|FIELD` гарантируется **ровно одна** строка (существующие дубли схлопываются, отсутствующие — добавляются, лишние — помечаются DONE/CANCELLED);
   - поскольку это **rebuild (replace), а не append**, повторный вызов не плодит строк, а приводит очередь к каноническому виду.
   Можно вызывать из меню вручную и (опц.) в начале `v12DrainPendingEdits` вместо синтетических интенентов — тогда видимая очередь до применения будет полной и без дублей.

4. **Hardening лока и видимости.** В `v12EnqueuePendingRows` (и в rebuild) — `SpreadsheetApp.flush()` под локом после записи, чтобы следующее исполнение гарантированно видело строки.

5. **Физическая дедупликация на сливе.** В начале `v12DrainPendingEdits` — схлопнуть дубли `PENDING` по ключу (оставить последнюю строку, остальные пометить DONE с пометкой «дубль»). Это страхует от уже накопившихся дублей и от любых будущих гонок.

### Почему это лучше
- **Нет дублей:** точный захват пишет только свои строки; rebuild заменяет множество (не добавляет); слив дедуплицирует.
- **Нет потерь:** rebuild/реконсиляция сканируют фактическое состояние галочек.
- **Идемпотентность:** и upsert, и rebuild можно вызывать многократно.

## Что НЕ надо делать
- Оставлять «полный скан на каждое событие с append» — это прямой источник перекрывающихся appends.
- Полагаться только на лок без `flush` — видимость между перекрывающимися исполнениями не гарантирована.
- Матчить upsert только `PENDING` — накопленные дубли не схлопываются.

## Затронутые файлы
`v12_queue.js` (`v12CaptureCheckboxEdit` — вернуть к строкам события; добавить `v12RebuildPendingFromChecked` и/или дедуп в `v12DrainPendingEdits`; `v12EnqueuePendingRows` — `flush` под локом), `v12_ui.js`/`v12_controller.js` — при добавлении пункта меню «Пересобрать очередь».

# РЕАЛИЗОВАНО (устранение дублей без потери позиций)

## Изменения в `v12_queue.js`

### 1. Точный захват (без дублей по построению)
`v12CaptureCheckboxEdit` возвращён к обработке **только строк редактируемого события** (`e.value`/`e.values` + `Position ID` строк диапазона). Каждое событие добавляет/обновляет **строго свои ключи**, upsert по ключу `SOURCE|POSITION_ID|FIELD` идемпотентен — **перекрывающиеся `onEdit` больше НЕ могут создать дубли** (раньше полный скан на каждое событие писал все отмеченные строки → совпадающие appends).

### 2. `SpreadsheetApp.flush()` под локом
В `v12EnqueuePendingRows` после записи строк добавлен `SpreadsheetApp.flush()` **до снятия лока**, чтобы перекрывающееся исполнение увидело запись и обновило её upsert-ом, а не добавило дубли.

### 3. `v12RebuildPendingFromChecked()` — идемпотентная пересборка на сливе
Добавлена функция (и помощник `v12CollectCheckedHandoffs()`), вызываемая в начале `v12DrainPendingEdits`:
- **схлопывает дубли** `PENDING` по ключу (оставляет последнюю строку, лишние помечает `DONE` с пометкой «дубль») — устраняет уже накопившиеся задвоения;
- **добирает отмеченные галочки**, по которым строки нет (восстановление потерянных `onEdit`);
- **НЕ отменяет** существующие намерения — очередь авторитетна (снятие галочки фиксирует точный захват значением `false`).

Это REPLACE (не append): повторный вызов не увеличивает число строк. Намерения других полей (Заказано/Ожидаемая/Реальная поставка) не трогаются.
