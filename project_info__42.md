# BOM CONTROL SYSTEM V12 — Проектное предложение: переход на модель «ввод → кнопка "Применить"»

> **Статус:** проектный анализ (Explore Mode). Изменения НЕ вносились.
> **Вопрос:** *«Что если вместо постоянных перерисовок и автоматических триггеров пользователь вводит данные, а по завершении подтверждает кнопкой "Применить"? Насколько это упростит приложение, повысит надёжность и скорость?»*
> **Контекст:** текущая архитектура и уже внедрённая очередь — `project_info__39.md` (Вариант D), `project_info__41.md` (Вариант A), диагностика — `project_info__40.md`.

---

## 1. Короткий ответ

**Да — это упростит систему и повысит надёжность, при умеренном изменении объёма кода** (инфраструктура очереди `PENDING_EDITS`, нужная для этого, **уже реализована** в Вариантах D/A). Скорость **в среднем** вырастет за счёт резкого сокращения числа пересборок, но **задержка в момент нажатия «Применить» останется** (полная пересборка 5 проекций).

Ключевой выигрыш — **не в скорости как таковой, а в устранении самого класса дефектов «быстрого ввода»**: он возникает из-за конкуренции *пользовательской правки ячейки* и *фоновой пересборки проекции*. Если пересборка происходит только по явной команде, окно гонки во время набора **исчезает**.

---

## 2. Почему это вообще работает в этой архитектуре

Система **уже** построена как «батч-ориентированная»: `POSITION_STATE` — источник истины, все остальные листы (Сводка, ОТБОРКА, WORKING BOM, СНАБЖЕНИЕ, Dashboard) — **производные проекции**, которые `v12RefreshProjections()` **полностью пересобирает** из `POSITION_STATE`. Единственная причина, по которой onEdit делает тяжёлую работу немедленно, — поддержать проекции «живыми» сразу после правки.

Более того, `v12_controller.js` уже содержит ручные пункты меню:

```
🔄 Полная синхронизация        → v12RunFullSync
📊 Обновить проекции           → v12RefreshAllProjections
⏱ Обработать очередь правок     → v12ScheduledQueueDrain
```

То есть «кнопка Применить» **почти существует** — её надо сделать основным (а не резервным) способом применения, убрав автоприменение.

---

## 3. Три варианта реализации

### V1 — Минимальный (оставить всё, отключить автоприменение)
- Захват намерений в `PENDING_EDITS` в onEdit **остаётся** (быстро, без лока).
- Отключается `QUEUE_INLINE_DRAIN` (не сливать из onEdit) и **удаляется/отключается минутный триггер** `v12ScheduledQueueDrain`.
- Меню: `✅ Применить изменения` → `v12ScheduledQueueDrain` (переименовать в `v12ApplyChanges`).
- Объём: правки только в `v12_config.js` (настройки), `v12_trigger.js` (установка триггеров), `v12_controller.js` (меню). **Полдня работы.**

### V2 — Полный «Применить» (без очереди)
- onEdit **ничего не делает**; «Применить» читает редактируемые колонки листов, «подхватывает» их изменения в `POSITION_STATE` и делает один `v12RefreshProjections()`.
- Требует надёжного определения «что изменилось в редактируемых колонках» — это ровно та задача harvest, от которой мы уходим (§5). Повышает риск затирания при многопользовательской работе, теряет per-field last-wins.
- **Не рекомендуется** — сложнее и менее надёжно, чем V1/V3.

### V3 — Очередь + явное «Применить» (рекомендуется)
- Как V1, но:
  - `PENDING_EDITS` остаётся **буфером применяемых изменений**;
  - добавляется наглядный индикатор «⚠ Есть необработанные изменения (N)» (ячейка-статус на видном листе + пункт меню);
  - «Применить» — единая locked-операция: прочитать очередь → применить в `POSITION_STATE` → **один** пересчёт проекций → пометить `DONE`.
- Объём: правки в `v12_config.js`, `v12_trigger.js`, `v12_controller.js`, `v12_queue.js` (удаление `v12TryInlineDrain`, переименование точки входа). Плюс удаление harvest (§5). **1–2 дня работы.**

## 4. Насколько упростится (по коду)

| Место | Сейчас | При модели «Применить» |
|---|---|---|
| `v12_trigger.js` → `v12OnEdit` | Захват → `v12TryInlineDrain`, гейт лока `tryOnly(10 c)`, ветка отбрасывания/отката | Только захват намерения (или вообще ничего). Вся логика лока/отката в пути правки **исчезает** |
| `v12_trigger.js` → `v12InstallTriggers` | 3 триггера: `v12OnEdit`, `v12ScheduledUpdate` (час), `v12ScheduledQueueDrain` (мин) | `v12ScheduledQueueDrain` **удаляется** (остаётся часовая синхронизация источника — она не про правки) |
| `v12_queue.js` → `v12TryInlineDrain` | Есть | **Удаляется** |
| `v12_queue.js` → `v12ScheduledQueueDrain` | Фоновый слив по таймеру | Превращается в «Применить» (по кнопке) |
| `v12_projections.js` → `v12HarvestDeficitInput` / `v12HarvestPickingInput` | «Подхват» правок листа в состояние (борьба с гонками) | **Можно удалить целиком** — редактирование больше не конкурирует с пересборкой |
| `v12_operations.js` → `v12SetOrderedQty`/`v12SetExpectedDate` | Тяжёлые (тянут за собой СНАБЖЕНИЕ + Dashboard) | Остаются только как часть «Применить» (пакетно) |
| `v12_controller.js` | Ручные пункты меню (уже есть) | «Применить» становится основным; + индикатор |

**Итог по сложности:** удаляются **две тонкие и «глючные» подсистемы** — «подхват» (harvest) и «инлайн-слив с гейтом лока». Слой «запись и согласование» сокращается примерно **на треть** и перестаёт быть конкурентным. Слой «пересчёт проекций» (`v12RefreshProjections`) **не меняется** — это по-прежнему центр стоимости.

## 5. Надёжность

**Что улучшается:**
- Устраняется **первопричина** дефектов «быстрого ввода»: при «Применить» нет фоновой пересборки во время набора → окно гонки схлопывается до одного защищённого лока операцией.
- Применение становится **атомарным и детерминированным**: один вход, один лок, один пересчёт.
- Исчезает «иногда быстро, иногда медленно» поведение onEdit (инлайн-слив когда лок свободен / минутный иначе).
- Меньше запусков скрипта → меньше расхода квот Apps Script и меньше записей в лог.

**Что остаётся риском / появляется:**
- **«Забыл нажать Применить».** Митигация: заметный индикатор (N необработанных), а сами ячейки сохраняют введённые значения (они видны до применения). Плюс: очередь `PENDING_EDITS` — первичный источник истины, значение не теряется даже при перезагрузке.
- **Многопользовательская работа.** Сейчас last-wins по `(SOURCE, POSITION_ID, FIELD)`; при «Применить» надо решить область — применять **все** намерения или **только свои**. Last-wins сохраняется, но появляется момент «наш Apply применил и чужие правки».
- **Нет живой пересборки статусов** сразу после ввода (см. §6).

---

## 6. Скорость

**Средняя скорость — существенно вырастет.** Сегодня правка может тянуть пересборку (а `v12SetOrderedQty` при заполненной дате — ещё и полную пересборку СНАБЖЕНИЯ и Dashboard). Серия из N правок по 5 листам в худшем случае даёт **несколько** пересборок; при «Применить» — **ровно одна** на всю пачку.

**Латентность в момент нажатия — не изменится**: это по-прежнему полный пересчёт 5 проекций (секунды, `clearBody` + `writeValues` + переустановка чекбоксов/цветов/фильтра). Кнопка «Применить» **не ускоряет сам пересчёт**, она лишь **сокращает число** пересчётов и делает их предсказуемыми. Чтобы ускорить и сам Apply, нужны **инкрементальные проекции** (пересобирать только затронутые строки) — отдельная, более крупная задача (уже частично сделана для Сводки: `v12RefreshDeficitSummaryRow`).

**Что уберётся из «горячего пути» навсегда:** пересборки внутри обработчиков одиночных правок (`v12SetOrderedQty`/`v12SetExpectedDate`/`v12SetRealDeliveryQty`/`v12MarkReceivedByProduction`), гейт лока и таймауты в onEdit.

**Что останется:** часовая `v12ScheduledUpdate` → `v12RunFullSync` (импорт новых BOM из Drive — не связан с пользовательскими правками) и полный пересчёт при Apply.

---

## 7. Цена с точки зрения UX

- **Пропадает live-статус**: после ввода пользователь видит введённые значения, но пересчитанные `Статус`, `Дефицит`, колонка «Проекты» в СНАБЖЕНИИ и т.п. обновятся только после «Применить».
- Появляется **двухшаговость** для каждой серии правок (набрал → применить).
- Для **разовой точечной правки** это чуть больше действий, чем сейчас.
- **Плюс:** поведение становится понятным и предсказуемым — «пока не применил, ничего не пересчитывается».

---

## 8. Что НЕ упростится / не изменится

- `v12RefreshProjections` — полная пересборка 5 листов остаётся центром стоимости (Apply её не делает инкрементальной).
- Импорт исходных BOM (`v12RunFullSync`, часовой триггер) — вне темы.
- Базовая схема «редактируемые ячейки живут внутри проекции» сохраняется (именно она порождает обратную запись в `POSITION_STATE`). Полное упрощение потребовало бы вынести ввод в отдельный лист-форму (более крупный редизайн).

## 9. Рекомендация

**Принять V3** (очередь + явное «Применить», убрать автоприменение и минутный триггер). Обоснование:

1. Это **небольшое** изменение на уже готовой инфраструктуре очереди (Варианты D/A) — не переписывание.
2. Оно **структурно** устраняет класс дефектов «быстрый ввод → сброс в 0.0» (убирает конкуренцию правка↔пересборка), а не «латает» его.
3. Позволяет **удалить** harvest и инлайн-слив — две наиболее тонкие и подверженные ошибкам подсистемы.
4. Даёт заметную экономию времени скрипта и квот, делает применение атомарным и предсказуемым.

**Отдельно (следующим шагом, при желании ускорить сам Apply):** инкрементальные проекции — точечно пересобирать только затронутые строки каждого листа (для Сводки уже сделано `v12RefreshDeficitSummaryRow`; аналоги нужны для ОТБОРКИ/WORKING BOM/СНАБЖЕНИЯ/Dashboard).
