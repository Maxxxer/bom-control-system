# BOM CONTROL SYSTEM V12 — Расследование: «массовая отметка чекбоксов „Реальная поставка“ отмечает только первую позицию»

## Краткое описание симптома
При массовой отметке чекбоксов **«Реальная поставка»** в листе «Сводка дефицитов» (`DEFICIT_SUMMARY`) в `POSITION_STATE` попадает отметка **только первой** позиции. Остальные отмеченные строки остаются в сводке, а их чекбоксы снова показываются снятыми. Одиночная отметка одного чекбокса работает.

## Цепочка обработки (актуальный код)
`v12OnEdit(e)` (`v12_trigger.js`) обрабатывает лист `DEFICIT_SUMMARY`:
- **одиночная ячейка** → `v12HandleDeficitEdit(e)`; ветка `column === D.REAL_DELIVERY` (кол. 12) → `v12SetRealDeliveryQty(positionId, checked ? required : 0)` → в конце `v12RefreshProjections()` (все 5 проекций);
- **диапазон** → `v12HandleDeficitRangeEdit(e)` — обходит все строки диапазона, копит `writes`, пишет одним `batchWrite` → в конце `v12RefreshDeficitSummary()` + `v12RefreshPicking/WorkingBOM/Supply/Dashboard`.

## Корневая причина (структурная)
Каждая обработанная правка чекбокса завершается **полной пересборкой** сводки — `v12RefreshDeficitSummary()` (`v12_projections.js`):
```js
v12ClearBody("DEFICIT_SUMMARY");          // clearContent + clearDataValidations по телу
if (rows.length) v12WriteRows("DEFICIT_SUMMARY", 2, rows);
v12InstallDeficitCheckboxes(rows.length); // clearDataValidations + setDataValidation заново
v12ApplyDeficitColors(rows);
```
Лист сводки **полностью очищается и создаётся заново**. При этом:
- `v12BuildDeficitRow()` жёстко пишет `false` в колонку «Реальная поставка» (`false, // REAL_DELIVERY checkbox`) — проекция не отражает сохранённое состояние;
- строки, ставшие неактивными (`v12IsDeficitRowActive === false`), удаляются, оставшиеся **сдвигаются вверх**.

Последствия при массовой отметке:
1. Любая обработанная правка **затирает состояние чекбоксов всех ещё активных строк** (перезапись `false` + переустановка валидации); уже проставленные, но ещё не перенесённые в `POSITION_STATE` отметки теряются.
2. Удаление строк **сдвигает нумерацию** — последующие события читают `sheet.getRange(row, D.POSITION_ID)` на сдвинутых строках.
3. «Доживает» только первая обработанная отметка; остальные строки снова сняты и остаются в сводке.

## Почему локальный тест НЕ воспроизводит
`_local_tests/v12_delivery_test.js` (сценарий S5) подаёт **одно** событие-диапазон (`numRows = 3`, значения `TRUE`). `v12HandleDeficitRangeEdit` успевает пометить все строки одним проходом до пересборки — тест проходит (24/24 PASS). В реальном Google Sheets массовая отметка приходит **несколькими событиями `onEdit`**, и между ними успевает выполниться полная пересборка сводки из предыдущего события.

## Дополнительные факторы
- `v12BuildDeficitRow`: колонка чекбокса = константа `false`.
- `v12SetRealDeliveryQty` пересчитывает **все 5 проекций** — избыточно, расширяет окно конфликта.
- **Нет межсобытийной сериализации**: `acquireScriptLock()` (`lock.js`) реентрантный только внутри одного исполнения, а каждое `onEdit` — отдельное исполнение.
- `v12HarvestDeficitInput()` читает лист сводки целиком в начале каждой пересборки — дополнительный источник «мигания» состояния.

## Рекомендации (изменения вносить в режиме Act)
1. Не пересобирать весь лист сводки при отметке чекбокса — обновлять/удалять **только затронутую строку** (образец — существующая `v12RefreshDeficitSummaryRow`), без `clearBody` + `writeRows`.
2. Колонку «Реальная поставка» делать производной от состояния (`REAL_DELIVERY_QTY > 0` или отдельный флаг), а не константой `false`.
3. Для одиночной отметки — точечный пересчёт проекций, не все пять.
4. Проверить фактическую доставку массовой отметки (возможно, Google Sheets доставляет её по одному событию на ячейку) — тогда п.1 обязателен, иначе события перетирают друг друга.
5. Опционально — буферизация серии правок с отложенной пересборкой.
