# Расследование: почему при выделении нескольких чекбоксов + «пробел» в PENDING_EDITS попадает только ОДНА позиция

> **Режим: Explore Mode.** Это результат исследования кодовой базы (`d:\Bom_control\bom-control-system`) под конкретный вопрос пользователя. Здесь — анализ причины и указание мест, где нужно менять код. Реализация — в **Act Mode**. Отчёт сохранён как `project_info__66.md`.

---

## 0. Краткий ответ

Система определяет, **какие позиции изменились, ТОЛЬКО из объекта события `onEdit`** — `e.range` (строки/колонки), `e.value`, `e.values` и запасного `range.getValues()` (см. `v12CaptureCheckboxEdit` и `v12CaptureDeficitEdit` в `v12_queue.js`).

Когда пользователь **выделяет несколько ячеек-чекбоксов и нажимает «пробел»**, Google Sheets выполняет всю операцию как **ОДНУ правку** и вызывает `onEdit` **один раз**. При этом объект события не перечисляет все переключённые ячейки как отдельные: в «одиночной» форме события `range.getNumRows()`/`getNumColumns()` возвращают `1`, а `e.values` не заполняется (он бывает только у «вставки»/`onChange`). Код из-за этого идёт по «одиночной» ветке (`singleCell === true`) и фиксирует **ровно одну** строку очереди.

Итог: «одно событие → одна позиция`. Это и есть наблюдаемое «программа считает это за одно изменение».

Частично проблему лечит уже существующая «страховка» `v12ReconcilePendingHandoffs()` → `v12RebuildPendingFromChecked()`, но **только для чекбоксов HANDOFF** (ОТБОРКА / WORKING BOM). Для колонки **«Реальная поставка» (`REAL_DELIVERY`) в «Сводке дефицитов» такой страховки НЕТ** — именно там «одна позиция» воспроизводится стабильно.

## 1. Механизм: как сейчас захватывается правка чекбокса

Точка входа — `v12OnEdit(e)` (`v12_trigger.js`). Для листов с чекбоксами он вызывает быстрый путь:

```js
if (v12CaptureCheckboxEdit(e, name)) {
  return;   // намерение зафиксировано; применение — по кнопке
}
```

`v12CaptureCheckboxEdit(e, sheetName)` (`v12_queue.js`) для ОТБОРКИ / WORKING BOM:

1. берёт границы диапазона из **события**: `range.getColumn()`, `getNumColumns()`, `getRow()`, `getNumRows()`;
2. проверяет, что диапазон задевает колонку чекбокса: `col > column || lastCol < column → return false`;
3. вычисляет `const singleCell = (numRows === 1 && numCols === 1);`
4. **читает значения так:**

```js
const values = singleCell
  ? [[e.value !== undefined ? e.value : range.getValue()]]
  : ((e.values && e.values.length === numRows) ? e.values : range.getValues());
```

5. читает `Position ID` строк диапазона **одной выборкой** по `numRows`;
6. в цикле `for (let r = 0; r < numRows; r++)` строит по одной строке очереди на каждую строку диапазона.

**Ключ проблемы — шаги 3–4:** если событие сообщает `numRows === 1` (а для «точечной» формы события при массовом переключении это именно так), то `singleCell === true`, берётся значение **одной** ячейки, и цикл выполняется **один раз**. Отсюда одна строка в `PENDING_EDITS`.

Для «Сводки дефицитов» аналог — `v12CaptureDeficitEdit(e)` (`v12_queue.js`), где **точно та же логика** выбора `values` и тот же цикл по `numRows`/`editable`:

```js
const values = singleCell
  ? [[e.value !== undefined ? e.value : range.getValue()]]
  : ((e.values && e.values.length === numRows) ? e.values : range.getValues());
```

## 2. Почему это «одно изменение» — поведение Google Sheets

Важно понимать: **это не дефект вашего кода сам по себе, а поведение платформы**, на которое код опирается.

- Для простого триггера `onEdit` Google вызывает обработчик **один раз на действие пользователя**. Выделение нескольких ячеек + «пробел» (или `Ctrl+Enter` для ввода значения в диапазон) — это **одно действие**.
- Для такого массового переключения объект события **не гарантирует** представление всех затронутых ячеек как отдельного массива: `e.values` у простого `onEdit` заполняется **только для «вставки»/массового ввода**, а для «пробела» по выделению обычно `undefined`; `e.value` — значение одной (активной) ячейки.
- Соответственно, единственный надёжный способ узнать, **что именно** стало отмечено — **прочитать фактическое состояние колонки с листа** (а не верить форме события). Именно поэтому в проекте и появилась «пересборка по фактическим галочкам» (`v12RebuildPendingFromChecked`).

> Это ровно та же корневая причина, что уже описана в отчётах `project_info__59.md`/`__60.md` («Google „глотает“ всплески onEdit при массовой отметке»). Там проблему лечили реконсиляцией очереди по факту галочек — но **только для HANDOFF**.

## 3. Где именно теряются позиции (карта)

| Слой | Файл / функция | Роль в дефекте |
|---|---|---|
| Триггер | `v12_trigger.js` → `v12OnEdit` | Получает **единственный** `onEdit`; дальше передаёт форму события в захват |
| Захват HANDOFF | `v12_queue.js` → `v12CaptureCheckboxEdit` | Берёт `numRows`/`values` из события; при «одиночной» форме события пишет 1 строку |
| Захват Сводки | `v12_queue.js` → `v12CaptureDeficitEdit` | То же; **плюс не вызывает никакой реконсиляции** |
| Страховка HANDOFF | `v12_queue.js` → `v12ReconcilePendingHandoffs` / `v12RebuildPendingFromChecked` | Читает **фактические галочки** ОТБОРКИ/WORKING BOM и «добирает» все отмеченные → для HANDOFF баг маскируется |
| Ввод в очередь | `v12_queue.js` → `v12EnqueuePendingRows` | UPSERT по ключу `SOURCE\|POSITION_ID\|FIELD`; одна пачка — одна запись на ключ |

**Ключевая асимметрия:** `v12ReconcilePendingHandoffs()` вызывается **в конце** `v12CaptureCheckboxEdit`:

```js
if (pendingRows.length) { v12EnqueuePendingRows(pendingRows); }
v12ReconcilePendingHandoffs();   // ← есть ТОЛЬКО тут
return true;
```

А `v12CaptureDeficitEdit(e)` **завершается без всякой реконсиляции**:

```js
if (pendingRows.length) { v12EnqueuePendingRows(pendingRows); }
return true;                   // ← никакой v12Reconcile* для REAL_DELIVERY/ORDERED_QTY/EXPECTED_DATE
```

Поиск по проекту подтверждает: `v12RebuildPendingFromChecked` / `v12ReconcilePendingHandoffs` упоминаются и вызываются только в пути HANDOFF и в `v12DrainPendingEdits` (при «Применить»). Для колонок Сводки их нет.

**Следствие:**
- **ОТБОРКА / WORKING BOM (HANDOFF):** массовое переключение «пробелом» скорее всего «самолечится» — реконсиляция добёрет все отмеченные галочки (если она успела взять лок и если событие вообще задело колонку чекбокса).
- **Сводка дефицитов («Реальная поставка» = REAL_DELIVERY):** реконсиляции **нет** → в очереди останется **одна** позиция при сколь угодно большом выделении. **Это и есть воспроизводимый дефект из вопроса.**

Дополнительные факторы, усугубляющие «одну строку» и там, где страховка есть:
- реконсиляция берёт **свой** лок (`acquireScriptLock({ tryOnly: true, timeoutMs: 10000 })`) и при занятости **тихо возвращает `null`** («пересборка отложена») — тогда добор не происходит;
- `v12RebuildPendingFromChecked` умеет только «галочка стоит ⇒ намерение HANDOFF», т.е. **не выражает «снятие»** (отмену) и не покрывает типизированные поля;
- если «одиночная» форма события пришла с колонкой, **не** пересекающей колонку чекбокса, `v12CaptureCheckboxEdit` вернёт `false` до вызова реконсиляции, и быстрый путь вообще не отработает.

## 4. Как убрать некорректное поведение (варианты для Act Mode)

Все варианты исходят из одного принципа: **не выводить множество изменённых позиций из формы события, а перечитывать фактическое состояние колонки.**

### Вариант A (рекомендуемый) — распространить «пересборку по факту» на все редактируемые чекбокс-колонки

1. Обобщить `v12RebuildPendingFromChecked` (или добавить рядом `v12RebuildPendingFromCheckedAll`), чтобы он собирал «желаемое» множество не только по ОТБОРКЕ/WORKING BOM (HANDOFF), но и по колонке **«Реальная поставка»** «Сводки дефицитов» (REAL_DELIVERY, `DEFICIT_COLUMNS.REAL_DELIVERY = 12`) с источником `SOURCE_UI.DEFICIT_SUMMARY`.
2. Вызвать эту реконсиляцию **в конце `v12CaptureDeficitEdit`** — точно так же, как сейчас в `v12CaptureCheckboxEdit` (см. `v12ReconcilePendingHandoffs`). Тогда «одна позиция» превратится в «все фактически отмеченные».
3. Соблюсти идемпотентность/UPSERT: пересборка уже схлопывает дубли по ключу и добавляет только отсутствующие (тесты F11/F12 это фиксируют).

Плюс: пользователь видит в очереди столько же позиций, сколько галочек, ещё **до** «Применить».
Минус: пересборка читает всю колонку (одно `getValues()` на лист) — разумная цена за корректность.

### Вариант B — читать фактическое выделение через `getActiveRangeList()`

Вместо (или вдобавок к) `e.range` перечислить все выделенные диапазоны:

```js
const rl = SpreadsheetApp.getActiveRangeList(); // .getRanges() -> массив Range
```

и обработать каждый диапазон. Это даёт **точный** набор выделенных ячеек (в т.ч. несмежных), если сервис доступен в контексте триггера. Минус: `getActiveRangeList()` может быть недоступен/не отражать выделение в момент срабатывания триггера; поведение менее предсказуемо, чем полное чтение колонки. Поэтому B — как дополнение к A.

### Вариант C — «replace-семантика» вместо «точного захвата»

При каждом событии по чекбокс-колонке полностью **перестраивать** множество PENDING-намерений этого поля по фактическому состоянию колонки (а не дописывать «строки события»). По сути это Вариант A, применённый ко всем полям. Риск — объём работы на событие; при массовой отметке это допустимо.

### Что важно НЕ сломать
- **UPSERT по ключу** `SOURCE|POSITION_ID|FIELD` (иначе вернутся дубли «снял → поставил», отчёты `project_info__57/58`).
- **Отмена через `false`**: для чекбокс-полей `VALUE=false` — это «отменить намерение» (`v12IsBooleanPendingField`); реконсиляция по «фактическим галочкам» строит только `true`-намерения, поэтому снятие галочки должно фиксироваться точным захватом (см. тест F13), а не теряться.
- **Права (RBAC)**: `v12CanEditField(role, action)` проверяется на этапе захвата; при обобщении реконсиляции нужно сохранить проверку для REAL_DELIVERY (`action: "REAL_DELIVERY"`).

## 6. Тесты (что и где проверять)

Существующие тесты не покрывают именно этот сценарий — они моделируют **сплошной** диапазон одним событием:

```js
// _local_tests/v12_queue_capture_fix_test.js
function rangeEvent(sheet, firstRow, numRows, col, values) {
  return { range: { getRow(){return firstRow;}, getNumRows(){return numRows;}, ... },
           value: values[0] ? values[0][0] : "", values: values };
}
...
N.v12OnEdit(rangeEvent(PK, 2, 5, K.CHECKBOX, maskValues));  // F5: ожидается 5 позиций
```

То есть тест подаёт событие, где `numRows` **уже** равен числу строк, — поэтому F5 «зелёный», а реальное поведение «пробела по выделению» (когда событие приходит одиночным) не воспроизводится. Для проверки дефекта нужен тест, который:
1. ставит несколько галочек **на листе** (`_setCell`), а через `v12OnEdit` подаёт событие **одной** ячейки (как «одно изменение»);
2. ожидает, что в очереди окажутся **все** отмеченные (по Варианту A — для HANDOFF и для REAL_DELIVERY).

## 7. Связанные находки (контекст, полезный для правки)

- Вся модель — «V3 Применить»: `onEdit` **только фиксирует намерение** в листе `PENDING_EDITS`; применение — вручную (`v12ApplyChanges` → `v12DrainPendingEdits`). Никакого автоприменения/минутного слива нет (`v12InstallTriggers` ставит только `onEdit` + часовой `v12ScheduledUpdate`).
- Колонки-чекбоксы в системе: `PICKING.CHECKBOX = 12`, `WORKING_BOM.CHECKBOX = 14`, `DEFICIT_COLUMNS.REAL_DELIVERY = 12`, `DASHBOARD.DONE = 1`.
- Dashboard «Выполнено» — **только одиночная ячейка** (`v12HandleDashboardEdit`: при `numRows≠1 || numCols≠1` вызывается `v12RevertEdit`). Массовое выделение Dashboard-чекбоксов системно не поддерживается (и это осознанно).
- При «Применить» (`v12DrainPendingEdits`) пересборка по фактическим галочкам вызывается ещё раз как страховка — но тоже **только для HANDOFF**.
- Полная синхронизация / обновление проекций **сбрасывают чекбоксы в `false`** (`v12RefreshPicking` / `v12RefreshWorkingBOM` пишут `false`), поэтому «добор по факту галочек» работает, только если лист не был пересобран между отметкой и Apply (см. `project_info__59.md`, Причина №4).

- **ОТБОРКА/WORKING BOM:** после массовой отметки «пробелом» нажмите меню **«BOM CONTROL V12» → «♻ Пересобрать очередь (по галочкам)»** (`v12RebuildPendingFromCheckedUI`) — это добёрет все отмеченные HANDOFF-галочки в очередь до «Применить». - **Сводка дефицитов («Реальная поставка»):** авто-добора нет — пока позиции придётся отмечать по одной, либо дождаться исправления (Вариант A/B). Это и есть место, которое нужно чинить.

## 9. Резюме для Act Mode

**Корень:** захват выводит множество изменённых позиций из **единичного** события `onEdit` (`e.range`/`e.value`/`e.values`), поэтому массовое переключение чекбоксов «пробелом» даёт одну позицию.
**Почему HANDOFF «проходит», а Сводка — нет:** для HANDOFF есть реконсиляция по фактическим галочкам (`v12ReconcilePendingHandoffs`), для `REAL_DELIVERY` в Сводке её нет.
**Минимальная правка:** обобщить `v12RebuildPendingFromChecked` на колонку «Реальная поставка» и вызвать реконсиляцию в конце `v12CaptureDeficitEdit` (по образцу `v12CaptureCheckboxEdit`), сохранив UPSERT и RBAC.

## 10. РЕАЛИЗОВАНО (Вариант A) — что именно изменено

Дата: 2026-09-14. Модель правки — **Вариант A**: очередь пересобирается по ФАКТИЧЕСКИМ галочкам, реконсиляция распространена на `REAL_DELIVERY` «Реальной поставки» Сводки дефицитов.

### `v12_queue.js`
1. **Добавлена `v12CollectCheckedRealDeliveries()`** — собирает отмеченные чекбоксы «Реальная поставка» (`DEFICIT_COLUMNS.REAL_DELIVERY`, источник `SOURCE_UI.DEFICIT_SUMMARY`). Аналог `v12CollectCheckedHandoffs` для Сводки.
2. **`v12RebuildPendingFromChecked()` обобщена**: «желаемое» множество теперь строится по ОБОИМ источникам (HANDOFF + REAL_DELIVERY), поле хранится в элементе `desired`, и строка очереди создаётся с корректным `field` (а не жёстко `HANDOFF`). Типизированные поля (Заказано/Ожидаемая) пересборкой по-прежнему не трогаются.
3. **`v12CaptureDeficitEdit()`** в конце вызывает `v12ReconcilePendingHandoffs()` (как `v12CaptureCheckboxEdit`): при массовой отметке «пробелом» (одно событие) очередь добирает ВСЕ отмеченные «Реальную поставку» позиции.
4. **`v12HasCheckedHandoffs()`** расширена колонкой `DEFICIT_SUMMARY.REAL_DELIVERY` — предфильтр «Применить» теперь ловит и отмеченные «Реальную поставку» без строки в очереди (если реконсиляция при захвате не успела взять лок).
5. Обновлены doc-комментарии `v12RebuildPendingFromChecked` / `v12ReconcilePendingHandoffs` (охват HANDOFF + REAL_DELIVERY).
