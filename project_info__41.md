# BOM CONTROL SYSTEM V12 — Вариант A: очередь намерений для типизированных полей «Сводки дефицитов»

> **Статус:** реализовано, локальная верификация пройдена (§7). Требуется `clasp push` и ручная приёмка (§9).
> **Предыстория:** диагностика дефекта — `project_info__40.md`. Базовая очередь (Вариант D) — `project_info__39.md`.
> **Проблема (репорт):** *«При вводе в сводку дефицита количества заказанного материала, если это делать быстро, значение сбрасывается и не сохраняется и сбрасывается на 0.0».*

---

## 1. Что сделано (коротко)

Дефект — **гонка (lost update)** между мгновенной правкой ячейки «Сводки дефицитов» и асинхронной тяжёлой пересборкой проекции из `POSITION_STATE`: правка «Заказано» выполнялась прямо в onEdit (с локом, с перезаписью строки и с полной пересборкой СНАБЖЕНИЯ/Dashboard), удерживала лок секунды, а при быстром вводе либо **отбрасывалась** по таймауту лока, либо её **затирала** очередная пересборка, писавшая `0`.

**Исправление по Варианту A:** типизированные поля Сводки — «Заказано» (`ORDERED_QTY`, кол. 9) и «Ожидаемая поставка» (`EXPECTED_DATE`, кол. 10) — переведены на **ту же очередь намерений `PENDING_EDITS`**, что и чекбоксы (Вариант D):

- onEdit для этих колонок **только фиксирует намерение** (снимок значения из `e.value`/`e.values`, без лока) и выходит;
- применение делает **пакетный слив** (`v12DrainPendingEdits`) — немедленно (если лок свободен) либо минутным триггером `v12ScheduledQueueDrain`;
- очередь — **первичный источник истины**: значение не теряется, даже если ячейку Сводки перезапишет пересборка проекции.

**Побочно устранён первопричинный «затиратель»:** функция `v12HarvestDeficitInput` больше **не подхватывает** `ORDERED_QTY`/`EXPECTED_DATE` из листа Сводки (см. §5). Раньше именно она могла записать `0` обратно в `POSITION_STATE` поверх только что применённого значения. Подхват «Реальной поставки» сохранён (он строго монотонный).

## 3. Как теперь работает ввод «Заказано»/«Ожидаемой» (быстрый путь)

```
v12OnEdit(e)  (Сводка дефицитов)
 └─ v12CaptureCheckboxEdit(e, name)
      └─ (Сводка) v12CaptureDeficitEdit(e):
           кол. 9  → FIELD=ORDERED_QTY,   право ORDERED_QTY
           кол.10  → FIELD=EXPECTED_DATE, право EXPECTED_DATE
           кол.12  → FIELD=REAL_DELIVERY, право REAL_DELIVERY   (как раньше)
           ├─ роль не даёт права → v12RevertEdit + лог, return true
           ├─ значение из e.value/e.values (снимок) → v12BuildPendingRow(...)
           └─ v12EnqueuePendingRows(...)   ← БЕЗ лока, append-only
      return true
 └─ v12TryInlineDrain()   (применить сейчас, если лок свободен; иначе минутный триггер)
```

Ключевое: **намерение фиксируется до любой тяжёлой работы** и хранит **снимок значения из события**, поэтому ни таймаут лока, ни перезапись ячейки пересборкой не приводят к потере ввода.

## 4. Слив очереди (пакетно)

`v12DrainPendingEdits` (без изменений в каркасе) теперь умеет применять типизированные поля:

```
intents = v12ResolvePendingIntents(...)   // last-wins по (SOURCE|POSITION_ID|FIELD), VALUE типизирован по FIELD
ctx = { index, materialIndex, warehouseDelta, positionWrites: [] }
для каждого намерения:
   для ЧЕКБОКС-полей (HANDOFF/REAL_DELIVERY): value=false → отмена (пропуск)
   v12WithActor(user) {
       HANDOFF         → v12MarkReceivedByProduction(..., skipRefresh=true, ctx)
       REAL_DELIVERY   → v12ApplyRealDeliveryIntent(ctx, ...)
       ORDERED_QTY     → v12ApplyOrderedIntent(value, ctx, ...)        ← новое
       EXPECTED_DATE   → v12ApplyExpectedDateIntent(value, ctx, ...)   ← новое
   }
применить ctx.positionWrites   → ОДИН batchWrite POSITION_STATE   ← новое (общий буфер)
применить ctx.warehouseDelta   → ОДИН batchWrite MATERIAL_STATE
ОДИН v12RefreshProjections()
пометить PENDING-строки DONE/FAILED
```

Пакетные применители (`v12ApplyOrderedIntent`, `v12ApplyExpectedDateIntent`) повторяют бизнес-логику `v12SetOrderedQty`/`v12SetExpectedDate` (расчёт, аудит, история, событие, проверка прав **от имени автора** через актор-контекст), но **не** пересобирают Сводку/СНАБЖЕНИЕ/Dashboard на каждую строку — записи копятся в `ctx.positionWrites`, а проекции пересчитываются **один раз** в конце слива.

## 5. Устранение первопричины: убран подхват типизированных полей

`v12HarvestDeficitInput` («страховка от пропущенного onEdit») трактовала **лист Сводки как авторитетный** над `POSITION_STATE`:

```
// БЫЛО:
orderedSheet = toNumber(сводка[i].ORDERED_QTY)
if (orderedSheet !== POSITION_STATE.ORDERED_QTY) POSITION_STATE.ORDERED_QTY = orderedSheet
```

После применения очереди это **вредило**: слив писал корректное значение в `POSITION_STATE`, а затем `v12RefreshProjections` вызывал harvest, который читал **устаревшую** ячейку Сводки (`0`) и записывал её обратно → сброс в `0.0`.

Теперь harvest для `ORDERED_QTY`/`EXPECTED_DATE` **ничего не делает** (эти поля полностью принадлежат очереди — очередь надёжно фиксирует любую правку, «пропустить onEdit» для них больше нельзя). Подхват «Реальной поставки» **сохранён** — он строго монотонный («только вверх») и не может затереть сохранённое значение.

Осознанное следствие: **снятие/очистка** заказа или даты выполняется **через очередь** (тип 0 в «Заказано»/пустая дата — это валидное намерение, а не отмена), а не через harvest.

## 6. Семантика отмены (важно)

| Поле | `VALUE = false/0/""` | Поведение |
|---|---|---|
| `HANDOFF` (чекбокс) | `false` | **отмена** (передача не выполняется) |
| `REAL_DELIVERY` (чекбокс) | `false` | **отмена** (поставка не отмечается) |
| `ORDERED_QTY` | `0` | **применяется** (заказ сбрасывается в 0) |
| `EXPECTED_DATE` | `""` | **применяется** (дата очищается) |

В сливе отмена применяется **только к чекбокс-полям** (`v12IsBooleanPendingField(field) && !it.value`), типизированные поля обрабатываются всегда. Покрыто тестами Z9 (сброс в 0) и Z10 (установка даты).

## 8. Поведение (осознанные изменения)

| Было | Стало |
|---|---|
| Быстрый ввод «Заказано» → сброс в `0.0` | Ввод **не теряется**: намерение фиксируется, применяется сливом |
| «Заказано»/«Ожидаемая» → тяжёлый onEdit под локом | onEdit пишет намерение (быстро), применение — пакетно |
| Подхват из листа мог затереть `POSITION_STATE` нулём | Для «Заказано»/«Ожидаемой» подхват отключён (очередь — истина) |
| Снятие заказа = убрать значение (и риск затирания) | Снятие = `0`/пустая дата как обычное намерение |
| N пересборок на N правок полей | **Один** пересчёт проекций на пачку намерений |

**Задержка применения.** При свободном локе правка применяется сразу (`QUEUE_INLINE_DRAIN=true`); иначе — ≤ 1 минуты (минутный триггер). Настройки в `V12_CONFIG.SETTINGS` (те же, что для чекбоксов): `QUEUE_DRAIN_MINUTES`, `QUEUE_INLINE_DRAIN`, `QUEUE_PURGE_DONE_DAYS`.

**Ограничение.** При «редких» правках инлайн-слив делает каждую правку близкой к прежней по длительности (полный пересчёт), но **без ошибок и потерь**. Радикальное ускорение — инкрементальные проекции (вне текущего объёма).

## 9. Установка и ручная приёмка (Apps Script)

1. `clasp push`.
2. Проверить наличие триггеров `v12OnEdit`, `v12ScheduledUpdate`, `v12ScheduledQueueDrain` (раз в минуту). Переустановка при необходимости — меню **BOM CONTROL V12 → ⚙ Установка V12**.

**Сценарии приёмки:**
1. Быстро ввести подряд несколько значений в «Заказано» (кол. 9) Сводки → значения **сохраняются**; при повторном открытии — на месте; в `POSITION_STATE.Заказано` те же числа.
2. Быстро ввести даты в «Ожидаемая поставка» → сохраняются в `POSITION_STATE.Ожидаемая поставка`.
3. Ввести «Заказано», затем в течение минуты очистить (0) → итог 0 (последнее значение выигрывает).
4. Ввести «Реальную поставку» (чекбокс, кол. 12) → работает как раньше (регресс).
5. `AUDIT_LOG` (действие `ORDERED_CHANGED` / `EXPECTED_DATE_CHANGED`): присутствует запись по каждому введённому значению.
6. `SYSTEM_LOG`: в `v12DrainPendingEdits`/`v12ScheduledQueueDrain` нет исключений.

## 10. Примечания

- Очередь `PENDING_EDITS` — **первичный источник истины** для правок чекбоксов (HANDOFF/REAL_DELIVERY) и типизированных полей Сводки (ORDERED_QTY/EXPECTED_DATE).
- `v12HandleDeficitEdit` / `v12HandleDeficitRangeEdit` **сохранены** как безопасный фолбэк для правок, не перехваченных захватом (например, вставка по нескольким колонкам сразу — она обрабатывается, но не типизированными намерениями).
- Пакетные применители проверяют права **от имени автора правки** (актор-контекст `v12WithActor`) — RBAC сохраняется и в фоновом сливе.
- Формат `0.0` в Сводке — следствие числового формата колонки; корректное значение (`0` как снятый заказ или число заказа) теперь пишется из очереди, а не из устаревшей ячейки.
