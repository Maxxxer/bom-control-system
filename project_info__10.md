# BOM CONTROL SYSTEM V12 — Анализ производительности и сценарий ускорения

## 1. Резюме

Основная проблема — **нелинейная деградация на кажущихся «мелких» операциях**.
Каждое действие (заказ, дата, поставка, передача, возврат, «Выполнено») вызывает
**полную пересборку всех 5 проекций** и **повторное чтение всех исходных листов
с нуля**. При росте количества позиций время операции растёт линейно от объёма,
а общий объём работы при чередовании операций — квадратично (N операций × N строк).

### Ключевые цифры (по коду)
- `v12RefreshProjections()` / `v12RefreshAllProjections()` вызываются после **каждой**
  операции: `v12SetOrderedQty`, `v12SetExpectedDate`, `v12SetRealDeliveryQty`,
  `v12MarkReceivedByProduction`, `v12ReturnFromArchive`, `v12HandleMaterialStateEdit`,
  `v12SetBomDone` (9 точек).
- Один такой вызов пересобирает 5 проекций. Каждая делает:
  `v12ReadSheet("POSITION_STATE")` → **полное чтение 30-колоночного листа**,
  `clearBody` (очистка всего тела), `writeRows` (запись всех строк).
- Итого на **одну операцию**: **5 полных чтений POSITION_STATE**, 5 очисток, 5 записей,
  3×`clearDataValidations`+`setDataValidation` (чекбоксы), 1×`setConditionalFormatRules`
  (дашборд, дорого), 1×`setNotes`.
- Для N=40 000 позиций одна операция ≈ 5×(40 000×30)=6 млн ячеек чтения + ~6 млн записи
  + форматирование → **секунды**, и это растёт линейно с N.

## 2. Горячие точки (в порядке убывания эффекта)

### Г1. Полный пересчёт всех 5 проекций на каждую операцию — O(N²)
- 5 функций (`v12RefreshDeficitSummary/Picking/WorkingBOM/Supply/Dashboard`) на каждый вызов:
  читают **весь POSITION_STATE**, очищают **весь лист**, пишут **все строки**.
- Дашборд дополнительно читает `BOM_REVISION` и `EXCLUDED_BOMS`, ставит
  `setConditionalFormatRules` (правила условного форматирования — одна из самых дорогих операций)
  и `setNotes` на каждую строку.
- **Решение**: перейти на инкрементальное обновление — обновлять **только затронутую строку**
  (по `positionId`) или только затронутый BOM; правила условного форматирования ставить
  **один раз при `v12Install`**, а не при каждом рефреше.

### Г2. Повторное чтение одних и тех же листов внутри одной операции
- `v12MarkReceivedByProduction` строит `v12BuildPositionIndex` (полное чтение POSITION_STATE),
  затем `v12GetPositionById` (та же), затем `v12AdjustWarehouseQty` → `v12BuildMaterialIndex`
  (полное чтение MATERIAL_STATE), затем `v12RefreshProjections` → ещё 5 чтений POSITION_STATE.
- `v12SetRealDeliveryQty` вызывает `v12GetWarehouseQty(materialKey)` (строит индекс MATERIAL_STATE)
  и `v12AdjustWarehouseQty` (строит индекс снова).
- **Решение**: читать каждый лист **один раз за операцию** в память (snapshot) и передавать
  общий `Map` во все функции — убрать дублирующие `getDataRange().getValues()`.

### Г3. Пересоздание индексов в циклах
- `v12BuildMaterialIndex` / `v12BuildPositionIndex` / `v12BuildBomRegistryIndex` при каждом
  вызове читают лист целиком. Если вызывать их внутри цикла по позициям — O(N) чтений листа.
- **Решение**: строить индексы один раз на операцию и передавать по цепочке.

### Г4. Полная синхронизация читает ВСЕ BOM-файлы каждый раз
- `v12RunFullSync` → `v12ListSourceBOMFiles()` (долгий обход Drive) → для каждого файла
  `SpreadsheetApp.openById(...).getSheets()[0].getDataRange().getValues()` — даже если хеш не изменился.
- **Решение**: сверять `LAST_HASH` из `BOM_REGISTRY` с текущим содержимым **до полного чтения**,
  пропускать неизменённые; для CSV — читать только при изменении по `lastUpdated`.

### Г5. Повторная установка чекбоксов и форматирования на каждом рефреше
- `v12InstallDeficitCheckboxes/Picking/Dashboard` вызываются при **каждом** обновлении проекций
  (`clearDataValidations` + `setDataValidation`).
- `v12ApplyDashboardColors` пересоздаёт правила условного форматирования **каждый раз**.
- **Решение**: кэшировать количество строк/идентификатор структуры; если структура не менялась —
  не трогать валидации и правила. Форматирование ставить на установке.

### Г6. Буфер аудита/логов
- `v12Audit`/`logSystem` буферизуют — это хорошо. Но `flushSystemLog`/`v12FlushAudit` вызываются
  в `finally` каждой операции, что, в общем, ок. При большом потоке — тоже одиночный `writeValues`,
  это нормально.

## 3. СЦЕНАРИЙ УСКОРЕНИЯ (поэтапный, с оценкой эффекта)

### Этап 1 — Убрать «полный пересчёт всё-на-всё» (эффект: ×5–×20)
- Заменить `v12RefreshProjections()` (полная пересборка 5 проекций) на
  **инкрементальные** обновления:
  - `v12UpdateDeficitRow(positionId)`, `v12UpdatePickingRow(positionId)`,
    `v12UpdateWorkingBomRow(positionId)`, `v12UpdateSupplyMaterial(key)`,
    `v12UpdateDashboardBom(bomId)` — точечные `batchWrite` по конкретным строкам.
  - Для «передачи/архива/возврата» — обновить строку дашборда этого BOM + убрать строку из
    ОТБОРКИ/сводки.
- **Замер**: до — 5×полное чтение+запись; после — 1×чтение затронутых строк, 1–2 batchWrite.

### Этап 2 — Один snapshot на операцию (эффект: ×2–×4)
- Ввести `v12BuildOperationContext()`: за **один** `readSheetValues` читает
  `POSITION_STATE`, `MATERIAL_STATE`, `BOM_REGISTRY`, `BOM_REVISION`, `EXCLUDED_BOMS` →
  возвращает `{ positions: Map, materials: Map, boms: Map, revisions: Map, excluded: Map }`.
- Все функции принимают `ctx` вместо повторных чтений.

### Этап 3 — Дублирующие индексы → один проход (эффект: ×2–×3)
- `v12BuildPositionIndex`/`v12BuildMaterialIndex`/`v12BuildBomRegistryIndex` строить **один раз**
  на операцию и передавать; внутри циклов не пересоздавать.

### Этап 4 — Ленивое форматирование (эффект: ×2–×5 на дашборде)
- `setConditionalFormatRules`, `setNotes`, `setDataValidation`, `clearDataValidations` —
  **только при изменении структуры** (rowCount/lastRow). Для этого хранить
  `PropertiesService`-ключ `V12_LAST_PROJECTION_SHAPE` и сравнивать.

### Этап 5 — Умная полная синхронизация (эффект: ×3–×10 на full sync)
- В `v12RunFullSync` перед чтением файла сравнивать **хеш содержимого** (или `lastUpdated`)
  с `BOM_REGISTRY.LAST_HASH`; неизменённые файлы **не читать повторно**.
- Читать исходный spreadsheets путём одного `openById` + `getDataRange()` (уже так), но не
  парсить строки, если хеш совпал.

### Этап 6 — Кэш для сессии/часового триггера
- Для `v12ScheduledUpdate` (каждый час) — не пересчитывать всё: обновлять только `dirty` BOM
  (по `BOM_REGISTRY.DIRTY`), как в ТЗ №98–99.

## 4. Целевые показатели (ТЗ №92)
| Сценарий | Сейчас (оценка, N=40k) | После этапов 1–4 | ТЗ №92 |
|---|---|---|---|
| Открытие Dashboard | несколько секунд | <1 с | <1 с |
| Изменение заказа/даты/поставки/передачи | секунды | <0.5 с | <2 с |
| Перерасчёт одного BOM | секунды | <1 с | <3 с |
| Полный sync | минуты | <30 с | <30 с |

## 5. Приоритет внедрения
1. **Этап 1** — инкрементальные проекции (главный выигрыш, убирает O(N²)).
2. **Этап 2** — operation-context snapshot (убирает дублирующие чтения).
3. **Этап 5** — skip по хешу в full sync + dirty-флаги (убирает лишние чтения BOM и Drive).
4. **Этап 4** — ленивое форматирование (убирает дорогие setConditionalFormatRules/setNotes).
5. **Этап 3** — переиспользование индексов.

> Важно: начать с **Этапа 1**, так как без него любое количество позиций делает
> приложение непредсказуемо медленным. Этапы 2–5 дают дополнительное ускорение
> и укладывают систему в тайминги ТЗ №92.
