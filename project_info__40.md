# BOM CONTROL SYSTEM V12 — Диагностика: сброс «Заказано» в Сводке дефицитов при быстром вводе

> **Статус:** анализ (Explore Mode). Правки НЕ вносились.
> **Предыдущие материалы:** `project_info__38.md` (диагностика чекбоксов), `project_info__39.md` (очередь правок `PENDING_EDITS`, Вариант D).
> **Проблема (репорт):** *«При вводе в сводку дефицита количества заказанного материала, если это делать быстро, значение сбрасывается и не сохраняется и сбрасывается на 0.0».*

---

## 1. Краткое резюме

«Заказано» в Сводке дефицитов (`Сводка дефицитов`, колонка `ORDERED_QTY` = 9) вводится в **проекцию**, которая полностью пересобирается из `POSITION_STATE`. Само значение хранится не в ячейке, а в `POSITION_STATE.Заказано` (кол. 12).

Ввод «Заказано» — это **не атомарная запись по месту**, а цепочка «onEdit → read-modify-write POSITION_STATE → синхронный перезапись строки/листа сводки из POSITION_STATE». Эта цепочка исполняется **асинхронно** относительно правки пользователя, сериализуется общим script-lock и удерживает его **секунды** (потому что при вводе даты дополнительно пересобираются целиком листы СНАБЖЕНИЕ и Dashboard).

Из-за этого возникает классический **lost update**: правка ячейки применяется Google Sheets мгновенно, а её «перенос» в `POSITION_STATE` может либо опоздать, либо быть отброшенным (не взят лок за 10 с), а любая следующая пересборка Сводки перезаписывает **всё тело листа** значением из `POSITION_STATE` — где для незаказанной позиции стоит `0`. Ячейка показывает `0`, отформатированное как `0.0`. Ввод теряется.

Существующие «страховки» (`v12HarvestDeficitInput`, снимок `e.value`, `tryLock(10 c)`) **не закрывают окно гонки** — они сужают его, но не устраняют. Это ровно тот же класс дефекта, что описан в `project_info__38.md` для чекбоксов и был решён **очередью намерений** там, но **не применён** к типизированным полям Сводки (Заказано / Ожидаемая дата).

## 2. Как устроена запись «Заказано» (карта пути)

### 2.1. Точка входа — `v12OnEdit` (`v12_trigger.js`)

```
v12OnEdit(e)
 ├─ лист = «Сводка дефицитов»? да → isActionable
 ├─ v12CaptureCheckboxEdit(e, name)  → для колонки 9 (Заказано) возвращает FALSE
 │     (перехватываются ТОЛЬКО ячейки/диапазоны колонки 12 «Реальная поставка»,
 │      exactColumnOnly = true)
 ├─ одиночная ячейка → isSummaryRange = false
 ├─ lock = acquireScriptLock({ tryOnly: true, timeoutMs: 10000 })
 │     └─ ЛОКА НЕТ → logSystem(...) + if (isSingleCell) v12RevertEdit(e); return;   ◄── (A)
 └─ lock взят → v12HandleDeficitEdit(e)
      └─ column === D.ORDERED_QTY (9) → v12SetOrderedQty(positionId, e.value, posIndex)
```

Ключевая деталь (строка комментария в коде): `v12RevertEdit` **не откатывает**, если нет `e.oldValue`, а для ячейки, которая была пустой/ещё не редактировалась, `oldValue` часто `undefined`. То есть ветка (A) в общем случае **молча теряет ввод** (пишет только WARNING в `SYSTEM_LOG`), а не восстанавливает прежнее значение.

### 2.2. Коммит — `v12SetOrderedQty` (`v12_operations.js`)

```
v12SetOrderedQty(positionId, qty, index):
  role = v12GetCurrentUserRole(); v12RequireRole(role, "ORDERED_QTY")
  newQty = max(0, toNumber(qty))
  pos = idx.get(positionId)                     // снимок POSITION_STATE на начало правки
  oldQty = pos.ORDERED_QTY
  если oldQty === newQty → harvest(skip ORDERED) + flush + v12RefreshDeficitSummaryRow  // путь «уже совпадает»
  иначе:
     v12UpdatePosition(... ORDERED_QTY=newQty + производные SUPPLY_STATE/DEFICIT_QTY/... )   // запись в POSITION_STATE
     v12Audit(...); v12LogHistory(...); v12LogEvent(...)
     v12HarvestDeficitInput({ positionId, key: "ORDERED_QTY" })   // подхват ТОЛЬКО соседних незакоммиченных ячеек
     SpreadsheetApp.flush()
     posData = v12ReadSheet("POSITION_STATE")
     v12RefreshDeficitSummaryRow(positionId, "ORDERED_QTY", posData)   // перезапись ОДНОЙ строки сводки
     если pos.EXPECTED_DATE → v12RefreshSupply(posData) + v12RefreshDashboard(posData)   ◄── (B) ТЯЖЕЛО
     v12FlushAudit()
```

`v12RefreshSupply` и `v12RefreshDashboard` (`v12_projections.js`) — это **полная пересборка** двух листов: `v12ClearBody` + `v12WriteRows` + переустановка чекбоксов/цветов/фильтра. Это занимает секунды и происходит **под удержанием script-lock**.

### 2.3. Подхват — `v12HarvestDeficitInput` (`v12_projections.js`)

Вызывается (1) в начале `v12RefreshProjections` (каждый минутный слив очереди и полный синк), (2) внутри операций как «страховка». Логика по колонке `Заказано`:

```
orderedSheet = toNumber(сводка[i][ORDERED_QTY])
if (!skipOrdered && orderedSheet !== toNumber(POSITION_STATE.ORDERED_QTY)) {
    POSITION_STATE.ORDERED_QTY = orderedSheet    // СВОДКА считается источником истины над ПОЗИЦИЕЙ
}
```

Идея: если пользователь успел ввести значение в ячейку, но onEdit не успел — «подобрать» его из листа перед перезаписью. **Это не атомарная операция и не блокировка ячейки.**

## 3. Корневая причина (класс: lost update через неатомарный read-modify-write проекции)

Сводка дефицитов — **проекция**, но содержит редактируемые поля, которые на самом деле живут в `POSITION_STATE`. Между двумя источниками (ячейка листа ↔ колонка `POSITION_STATE`) нет единого владельца и нет блокировки на уровне ячейки. Синхронизация — «догоняющая» и не атомарная, поэтому при быстром вводе побеждает пересборка.

### 3.1. Механизм A — пересборка затирает ещё не закоммиченную правку

1. Идёт (или запускается) **полная пересборка Сводки** — это делает `v12RefreshDeficitSummary`, которая вызывается из:
   - `v12RefreshProjections` ← минутный `v12ScheduledQueueDrain` (`v12DrainPendingEdits`), инлайн-слив `v12TryInlineDrain` после каждого клика по чекбоксу, `v12HandlePickingRangeEdit`, `v12HandleMaterialStateEdit`, `v12SetBomDone`;
   - `v12RefreshAllProjections` ← часовой `v12ScheduledUpdate` → `v12RunFullSync`.
2. Пересборка: `v12HarvestDeficitInput` читает лист **в момент T0** (в ячейке ещё старое `0`), затем `v12ClearBody` + `v12WriteRows` пишет тело из `POSITION_STATE` (тоже `0`).
3. Пользователь вводит значение **в момент T1 > T0** (ячейка мгновенно становится `100`).
4. Перезапись тела (шаг 2) происходит после T1 → ячейка снова `0`. **Ввод исчез.**
5. Если onEdit для этой правки затем отработает — снимок `e.value` (см. 3.3) его спасёт. Но если onEdit к этому моменту **уже был отброшен по таймауту лока** (см. 3.2) — значение не всплывёт никогда.

### 3.2. Механизм B — отбрасывание правки по таймауту script-lock

- `v12OnEdit` берёт лок через `acquireScriptLock({ tryOnly: true, timeoutMs: 10000 })`.
- Каждой правке «Заказано» (при заполненной дате) сопутствует тяжёлая пересборка СНАБЖЕНИЕ + Dashboard **(B)** под локом → удержание лока порядка секунд.
- При быстром вводе (несколько ячеек подряд) вторая/третья правка **не успевает взять лок за 10 с** → ветка (A): правка пользователя **не обрабатывается**. `v12RevertEdit` при отсутствии `oldValue` не восстанавливает ячейку, только пишет WARNING.
- Значение остаётся в ячейке как «висячее» и живёт до ближайшей пересборки, которая перепишет его из `POSITION_STATE` (`0`) → `0.0`.

> Важно: **script-lock сериализует только исполнения Apps Script между собой.** Он не мешает ни Google Sheets мгновенно применять правку в ячейку, ни человеку печатать во время исполнения. Поэтому лок — не защита от этого класса гонок.

### 3.3. Механизм C — снимок `e.value` помогает не всегда

Единственная надёжная защита для самой редактируемой ячейки — использование `e.value` (снимок правки) вместо `e.range.getValue()`:

```js
// v12_trigger.js, v12HandleDeficitEdit
const newValue = (e.value !== undefined) ? e.value : e.range.getValue();
```

и в диапазонном обработчике — `e.values`. Но:

- если `v12HandleDeficitEdit` вообще не вызван (ветка (A) по таймауту лока) — снимок не используется;
- снимок защищает **только ту строку/тот столбец**, который правил пользователь. Соседние незакоммиченные правки в той же строке (например, «Заказано» ввели раньше «Ожидаемой даты») защищены отдельно и слабее — через `v12HarvestDeficitInput(skip)`.

### 3.4. Почему именно `0.0`

`ORDERED_QTY` — числовая колонка; формат ячейки отображает её как `0.0`. Пересборка (`v12BuildDeficitRow`) пишет `r[P.ORDERED_QTY - 1]` из `POSITION_STATE`, где для незаказанной позиции это ровно число `0` (см. `v12BuildPositionRow`, дефолт `orderedQty || 0`). Поэтому симптом — именно `0.0`, а не пустая ячейка: это **запись нуля из состояния**, а не очистка.

## 4. Сопутствующие наблюдения (усиливают дефект)

- **«Догоняющий» harvest сам может откатить состояние.** `v12HarvestDeficitInput` считает Сводку источником истины над `POSITION_STATE`. Если по какой-то причине ячейка уже сброшена в `0`, а состояние расходится — harvest может закрепить `0`. Симметричная ошибка возможна и в обратную сторону.
- **Целевой путь не harvest’ит.** `v12RefreshDeficitSummaryRow(positionId, key, posData)` при переданном `posData` **не вызывает** harvest — он перезаписывает всю строку (14 колонок) из состояния. Если соседняя ячейка строки ещё не закоммичена, она затирается (отчасти закрыто `skip`-логикой в вызывающей операции, но не полностью).
- **Переустановка чекбокса строки.** `v12RefreshDeficitSummaryRow` → `v12InstallDeficitCheckboxForRow` + запись `REAL_DELIVERY=false` из `v12BuildDeficitRow`. Побочный эффект для других полей строки.
- **Тяжёлые пересборки на каждую правку.** Пересборка СНАБЖЕНИЕ + Dashboard при заполненной дате (пункт (B)) — основная причина, почему серия быстрых вводов доходит до 10-секундного таймаута лока. Это тот же дефект производительности, что мотивировал Вариант D для чекбоксов.
- **Oдин лист — много писателей.** Сводку перезаписывают: `v12RefreshDeficitSummary` (полный), `v12RefreshDeficitSummaryRow` (точечный), `v12HarvestDeficitInput` (правки POSITION_STATE), `v12SetBomDone`/передачи (через `v12RefreshProjections`). Общего «владения ячейкой» нет.

## 5. Почему правки в проект не попали (контекст)

Репозиторий уже дважды решал ровно этот класс проблем:

- `project_info__38.md` — диагностика потери галочек;
- `project_info__39.md` — **Вариант D**: для чекбоксов правка перестала выполняться в onEdit; фиксируется намерение в листе `PENDING_EDITS` (быстро, без лока), а применение делает минутный триггер/инлайн-слив **пакетно, одним пересчётом**.

## 7. Что подтвердить в «живой» таблице (диагностика)

Так как дефект — временнáя гонка, для подтверждения на реальном листе:

1. Воспроизвести: быстро ввести подряд несколько значений в «Заказано» в Сводке.
2. Открыть `SYSTEM_LOG` и найти записи `v12OnEdit` с уровнем `WARNING` — «Лок занят, правка отложена/откатана...». Их наличие прямо подтверждает Механизм B (отбрасывание по таймауту лока).
3. В `AUDIT_LOG` (действие `ORDERED_CHANGED`): если по введённой строке **нет** записи — правка не дошла до `v12SetOrderedQty` (потеряна). Если запись есть, но в Сводке `0.0` — сработала последующая пересборка (Механизм A).
4. Сверить `POSITION_STATE.Заказано` (кол. 12) и `Сводка дефицитов.Заказано` (кол. 9): расхождение = незакоммиченный/затёртый ввод.

## 8. Направления исправления (для Act Mode — здесь НЕ реализуются)

Ниже — варианты, а не готовое решение; выбор и реализация — в Act Mode.

- **A. Распространить Вариант D (очередь намерений) на типизированные поля Сводки.** `v12CaptureCheckboxEdit` перехватывает не только колонку 12, но и колонки «Заказано»/«Ожидаемая» (`FIELD = ORDERED_QTY / EXPECTED_DATE`, значение — из `e.value`/`e.values`). onEdit пишет намерение в `PENDING_EDITS` без лока, применение — пакетно. Это устраняет гонку «ячейка ↔ пересборка» тем же способом, что уже принят для чекбоксов. Требует расширения `PENDING_EDIT_COLUMNS.VALUE` (сейчас `v12IsChecked` → boolean) под числовые/датовые значения.
- **B. Сделать `v12HarvestDeficitInput` полноценно надёжным**: подхватывать обе колонки (ORDERED + EXPECTED) для **всех** строк при **любой** пересборке, и не считать Сводку авторитетной над POSITION_STATE при уже подтверждённом совпадении — иначе остаётся «догоняющая» логика.
- **C. Убрать тяжёлые пересборки (B) из пути одной правки.** После установки «Заказано» не пересобирать целиком СНАБЖЕНИЕ/Dashboard синхронно; отложить их в минутный триггер (инкрементально). Это радикально сократит время удержания лока и вероятность таймаута.
- **D. Инкрементальные проекции (Вариант C из `project_info__39.md`)** — точечно обновлять только затронутые строки СНАБЖЕНИЯ/Dashboard вместо полного пересбора; уже реализовано для Сводки (`v12RefreshDeficitSummaryRow`), нужен аналог для остальных.
- **E. Не отбрасывать правку по таймауту лока.** Вместо `return` при неудаче `tryLock` — фиксировать намерение (в очередь) и применять позже, либо увеличивать ожидание. (Прямая параллель с решением для чекбоксов.)

Наиболее «родной» для текущей архитектуры путь — **A** (расширение очереди на поля Сводки) в сочетании с **C** (снятие тяжёлых пересборок с горячего пути).

## 9. Быстрый указатель по коду (для того, кто будет исправлять)

1. `v12_trigger.js` → `v12OnEdit` — гейт лока и ветка отбрасывания.
2. `v12_trigger.js` → `v12CaptureCheckboxEdit` (`v12_queue.js`) — сейчас пропускает колонки 9/10 Сводки дальше.
3. `v12_trigger.js` → `v12HandleDeficitEdit` — снимок `e.value`, вызов `v12SetOrderedQty`.
4. `v12_operations.js` → `v12SetOrderedQty` / `v12SetExpectedDate` — read-modify-write и тяжёлые пересборки.
5. `v12_projections.js` → `v12RefreshDeficitSummary` (полная перезапись) и `v12HarvestDeficitInput` (подхват).
6. `v12_queue.js` → `v12DrainPendingEdits` / `v12TryInlineDrain` — источник фоновых полных пересборок.
