# Почему после всех правок «Отметка получено» фиксируется не полностью: 38 галочек ↔ 29 строк в PENDING_EDITS

> Вопрос: после всех исправлений (Fix 1–4 из `54`, сканирующий захват из `56`, точный захват + пересборка из `57`/`58`) чекбоксы «получено» отмечаются некорректно: в листах стоит **38** галочек, а в листе очереди (`PENDING_EDITS`, пользователь называет его «edit_pending») — только **29** задач.

## ЗАКЛЮЧЕНИЕ (коротко)

Это **не единичный баг, а регресс, внесённый последним исправлением (отчёт `58`)**.

Последний фикс сознательно вернул захват к режиму «**точный захват**»: `v12CaptureCheckboxEdit` пишет в очередь **только те строки, по которым реально пришло событие `onEdit`**. А «самовосстанавливающееся» сканирование всех отмеченных галочек (`v12RebuildPendingFromChecked`) теперь выполняется **ровно в одном месте — при нажатии «Применить изменения»**, внутри `v12DrainPendingEdits()`.

Следствие: **до нажатия «Применить» лист `PENDING_EDITS` содержит столько строк, сколько событий `onEdit` «доехало» — 29 из 38.** Оставшиеся 9 доберутся не в момент отметки, а только в момент применения (и тут же уйдут в статус `DONE`). Поэтому пользователь никогда не видит «38 в очереди» — он видит 29, и это ровно то поведение, которое заложено текущим кодом.

Иными словами: **Fix `58` убрал дубли ценой того, что лист очереди перестал отражать фактическое число отмеченных галочек до применения.** Тесты (`F10`/`F11` в `v12_queue_capture_fix_test.js`) проходят, потому что проверяют саму функцию пересборки, а не «видимое число строк в очереди между отметкой и применением».

## Как устроен путь отметки сейчас (по коду)

### 1. Событие отметки
`v12OnEdit(e)` (`v12_trigger.js`) для листов `S.PICKING` («ОТБОРКА») и `S.WORKING_BOM` вызывает быстрый путь:

```js
if (v12CaptureCheckboxEdit(e, name)) {
  return;   // намерение зафиксировано; применение — по кнопке
}
```

Никакого автоприменения и периодического слива в модели V3 **нет** (минутный триггер `v12ScheduledQueueDrain` удалён из состава триггеров, см. `v12InstallTriggers` / `removeV11Triggers`).

### 2. Точный захват — только строки события
`v12CaptureCheckboxEdit(e, sheetName)` (`v12_queue.js`):

- проверяет, что диапазон задевает колонку `CHECKBOX` (`PICKING_COLUMNS.CHECKBOX = 12`, `WORKING_BOM_COLUMNS.CHECKBOX = 14`);
- проверяет роль (`PICKING_CHECKBOX` / `WORKING_BOM_CHECKBOX`);
- берёт значения галочек **из самого события** (`e.value` / `e.values`, иначе `range.getValues()`);
- читает `Position ID` строк диапазона **одной выборкой**;
- для каждой строки события с непустым `Position ID` строит намерение `HANDOFF` и отправляет пачку в `v12EnqueuePendingRows`.

Ключевая строка-комментарий здесь прямо фиксирует новую модель:

> «Фиксируем СТРОГО строки этого события… Пропущенные события (Google „глотает“ всплески) восстанавливаются пересборкой очереди по галочкам — `v12RebuildPendingFromChecked`.»

То есть **восстановление вынесено в отдельную, более позднюю стадию**, а не выполняется на каждое событие.

### 3. Запись в очередь — upsert + лок + flush
`v12EnqueuePendingRows(rowArrays)`:

- берёт короткий общескриптовый лок `acquireScriptLock({ tryOnly: true, timeoutMs: 10000 })`;
- **при неудаче лок держат >10 с — пачка молча отбрасывается** (только запись `WARNING` в `SYSTEM_LOG`, без сообщения пользователю):

  ```js
  if (!lock) {
    logSystem("v12EnqueuePendingRows",
      "Очередь занята (идёт применение/синхронизация) — намерение не зафиксировано", "WARNING");
    flushSystemLog();
    return;   // ← намерения ТЕРЯЮТСЯ
  }
  ```

- под локом читает весь `PENDING_EDITS`, строит `byKey` (только строки со статусом `PENDING`), схлопывает дубли внутри пачки и делает **upsert** по ключу `SOURCE|POSITION_ID|FIELD` (`v12PendingKey`): существующую `PENDING`-строку обновляет, иначе `appends` и `sheet.getLastRow() + 1` (уже под локом);
- `SpreadsheetApp.flush()` под локом;
- **после** снятия лока ещё раз читает лист в `v12UpdatePendingIndicator()` (считает `PENDING`).

Итого на каждое событие уходит несколько листовых RPC: чтение всей очереди, запись/обновление, `flush`, повторное чтение для индикатора.

### 4. Пересборка — ТОЛЬКО на «Применить»
`v12RebuildPendingFromChecked()` сканирует **фактические** галочки `ОТБОРКА`/`WORKING BOM` (`v12CollectCheckedHandoffs`), схлопывает дубли `PENDING` (лишние → `DONE` с пометкой «дубль») и добирает отмеченные без строки. Но вызывается она **ровно в одном месте**:

```js
function v12DrainPendingEdits() {
  if (!v12HasPendingEdits() && !v12HasCheckedHandoffs()) { return { drained: 0 }; }
  ...
  v12RebuildPendingFromChecked();   // ← единственный вызов во всём проекте
  ...
}
```

(Проверено поиском: `v12RebuildPendingFromChecked` вызывается только здесь; в меню/триггерах/`onEdit` его нет.)

Единственные входы `v12DrainPendingEdits`: кнопка «ПРИМЕНИТЬ» (`v12ApplyChangesUI` из `v12_ui.js`) и пункт меню «Применить изменения» (`v12_controller.js`). Обе — **ручное действие пользователя**.

## Почему именно 38 ↔ 29 (разбор причин по значимости)

### Причина №1 (главная, архитектурная). Очередь теперь отражает «доехавшие события», а не «стоящие галочки»
Apps Script **не гарантирует вызов `onEdit` на каждую быструю правку**: при массовой отметке события идут потоком и часть из них отбрасывается платформой. Это уже зафиксировано в отчёте `56` как корневая причина «38 → 30».

- Сканирующий захват (`56`) эту проблему закрывал (писал все галочки) — **но плодил дубли** при перекрывающихся событиях (`57`).
- После Fix `58` захват стал точным, а «добор всех галочек» отложен до Apply.
- Поэтому **между отметкой и «Применить» видимое число строк = число доехавших событий ≈ 29 из 38**. До Apply лист физически не может показать 38 — соответствующий код (`v12RebuildPendingFromChecked`) в этот момент не вызывается.

Разница «30 → 29» по сравнению с прежним замером — это просто run-to-run вариация того, сколько событий Google доставил за конкретный всплеск; стабильно ожидать «все доедут» нельзя.

### Причина №2 (вторичная, но реальная). Молчаливый сброс пачки при занятом локе
`v12EnqueuePendingRows` при `tryLock(10000) === false` **не делает ни ретрая, ни резервной записи** — пачка пропадает, пользователь этого не видит (только `WARNING` в `SYSTEM_LOG`). Лок может быть занят другим `onEdit`, идущим «Применить изменения» или часовым `v12ScheduledUpdate` (полный синк — операция долгая). Каждое такое попадание уменьшает счётчик очереди.

### Причина №3 (вторичная, «усилитель» причины №1). Захват долгий → больше перекрытий → больше потерянных событий
На каждое событие `v12EnqueuePendingRows` делает полное чтение `PENDING_EDITS` (под локом), запись, `SpreadsheetApp.flush()`, а затем `v12UpdatePendingIndicator()` ещё раз читает лист. Чем длиннее обработчик, тем больше перекрытий исполнений `onEdit` (лимит одновременных исполнений скрипта в Apps Script — порядка 30), тем больше событий «проглатывается». Фикс `58` добавил `flush()` в путь захвата — это защита от дублей, но она **удлиняет** захват и работает против доставки событий.

### Причина №4 (фоновый риск). Часовой полный синк может обнулить визуальные галочки
`v12ScheduledUpdate → v12RunFullSync → v12RefreshAllProjections → v12RefreshPicking / v12RefreshWorkingBOM` **пересобирают листы и жёстко пишут `false` в колонку чекбокса** (`false // CHECKBOX` в массиве строк). Если полный синк сработает между отметкой и Apply:
- визуально галочки сбросятся (пользователь увидит не 38, а 0/меньше);
- при последующем Apply `v12CollectCheckedHandoffs` уже не увидит эти галочки → **не сможет их добрать** (нет ни события, ни отметки).

Это не текущее наблюдение (пользователь видит 38), но объясняет, почему стратегия «добор по факту галочек» не является надёжной страховкой: она зависит от того, что листы не были пересобраны после отметки.

### Причина №5 (потенциальная, проверить на живых данных). Строки без `Position ID` и «фантомные» чекбоксы
`v12CaptureCheckboxEdit` пропускает строки с пустым `Position ID` (`if (!positionId) continue;`). По отчёту `54` при протяжке/заполнении диапазона галочка может стоять на пограничной/пустой строке — тогда намерения нет. Обычно это единичные случаи, но на 38 отметках вклад может быть.

> **Важно:** Причина №1 объясняет расхождение **системно** (лист очереди по построению не равен числу галочек до Apply), а №2–№5 — то, почему «доехавших» событий заметно меньше 38. Проверка журнала `SYSTEM_LOG` на `WARNING "Очередь занята … намерение не зафиксировано"` отличит вклад №2 от №1.

## Что подтверждено прямым чтением кода

| Факт | Где |
|---|---|
| Захват пишет только строки события (не сканирует лист) | `v12_queue.js` → `v12CaptureCheckboxEdit` |
| Пересборка по фактическим галочкам вызывается **только** на Apply | `v12_queue.js` → `v12RebuildPendingFromChecked` вызывается в `v12DrainPendingEdits`; поиск по проекту не находит других вызовов |
| Периодического/автоматического слива нет (V3) | `v12_trigger.js` → `v12InstallTriggers` (только `onEdit` + часовой `v12ScheduledUpdate`); `v12ScheduledQueueDrain` существует лишь как совместимый алиас |
| В быстром пути `onEdit` лок не берётся (только на запись строки в enqueue) | `v12_trigger.js` → `v12OnEdit` |
| При занятом локе пачка отбрасывается молча (WARNING) | `v12_queue.js` → `v12EnqueuePendingRows` |
| Upsert по `SOURCE|POSITION_ID|FIELD` матчит **только** `PENDING` | `v12_queue.js` → `v12EnqueuePendingRows` (`byKey` строится по `PENDING`) |
| Ключ намерения — `SOURCE|POSITION_ID|FIELD` | `v12_queue.js` → `v12PendingKey` |
| Apply идемпотентен (повтор передачи → `already`) | `v12_handoff.js` → `v12MarkReceivedByProduction` |
| Проекции пишут чекбоксы в `false` при пересборке | `v12_projections.js` → `v12RefreshPicking`, `v12RefreshWorkingBOM` |
| Применение доступно только вручную (кнопка/меню) | `v12_ui.js` → `v12ApplyChangesUI`; `v12_controller.js` → `v12OnOpen` |

## Инварианты и где они нарушены

- **Инвариант «галочка стоит ⇒ позиция будет передана»** — сохраняется, но **только в момент Apply** (через `v12RebuildPendingFromChecked` + идемпотентное `v12MarkReceivedByProduction`). До Apply он не выполняется глазами пользователя.
- **Инвариант «строка в `PENDING_EDITS` ⇔ отмеченная галочка»** — **нарушен**: количество строк равно числу доехавших событий. Это и есть наблюдаемые 29 вместо 38.
- **Инвариант «очередь — источник истины»** — верен для уже записанных намерений, но если событие не доехало, в очереди ничего нет, поэтому сам по себе этот инвариант «пропажу» не ловит.

## Как проверить гипотезу (в Google Sheets, без правки кода)

1. Отметить 38 галочек в ОТБОРКЕ.
2. Сравнить число строк со статусом `PENDING` в `PENDING_EDITS` (это делает `v12CountPendingEdits`) с числом стоящих галочек (`v12CollectCheckedHandoffs`).
3. Открыть `SYSTEM_LOG` и поискать:
   - `v12EnqueuePendingRows` уровня `WARNING` с текстом «Очередь занята … намерение не зафиксировано» — подтверждает Причину №2;
   - обилие записей о захвате при близких таймстампах — подтверждает перекрытие событий.
4. **Не** запускать полную синхронизацию (`🔄 Полная синхронизация`, `📊 Обновить проекции`) между отметкой и Apply — иначе Причина №4 обнулит визуальные галочки и добор станет невозможен.
5. Нажать «Применить изменения» **до** любой пересборки — в этот момент `v12RebuildPendingFromChecked` доберёт оставшиеся 9, и передадутся все 38 (по инварианту Apply). После Apply строки уйдут в `DONE`, а листы-проекции сбросят чекбоксы в `false` — это ожидаемо.

## Рекомендации (для режима Act)

Ниже — варианты, как вернуть наглядное соответствие «галочка ⇔ строка очереди» без возврата дублей. Выбрать нужно один основной.

1. **Явная «Пересборка очереди» по кнопке/триггеру.** Добавить пункт меню/кнопку, вызывающий `v12RebuildPendingFromChecked()` (и/или пересобирать очередь в начале каждого `v12DrainPendingEdits` — уже так — **плюс** по короткому таймеру или по onEdit с троттлингом). Это даёт пользователю видимую «все галочки в очереди» детерминированно.
2. **Сканирующий захват — но с replace-семантикой, а не append.** При каждом событии чекбокс-колонки вызывать идемпотентную пересборку (replace множества `PENDING` по ключу) под локом с `flush`. Дубли по построению не появятся, если пересборка именно **заменяет** множество, а не добавляет строки. Это возвращает 38↔38 без задвоения (риск — больший объём работы на событие).
3. **Убрать молчаливый сброс при занятом локе.** В `v12EnqueuePendingRows` при `tryLock=false` — короткий ретрай, а при повторной неудаче **не терять** пачку (например, отложенная запись/флаг на повторную попытку), с записью в `SYSTEM_LOG`. Иначе часть «29» — это именно потерянные при перекрытии события.
4. **Развести индикаторы.** Показывать пользователю **два** числа: «отмечено галочек: N» и «в очереди: M», чтобы расхождение было явным и ожидаемым, а не выглядело как баг.
5. **Защитить визуальные галочки от фоновой пересборки.** Либо не запускать `v12RefreshPicking`/`v12RefreshWorkingBOM` при непустой очереди, либо восстанавливать отмеченное состояние из очереди при пересборке (перерисовывать чекбоксы по `PENDING` HANDOFF-намерениям).
6. **(Опционально) Подтверждать добор.** После `v12RebuildPendingFromChecked` можно логировать в `SYSTEM_LOG` число добавленных строк (`возвращаемое appends.length`) — это даст наблюдаемость, сколько галочек не доехало событиями.

---

## Что НЕ делать

- Не полагаться на то, что лист `PENDING_EDITS` до Apply равен числу галочек — по текущему коду это не так.
- Не запускать полную синхронизацию/обновление проекций между массовой отметкой и Apply.
- Не возвращать «полный скан + append на каждое событие» — это источник дублей (`56`/`57`); если возвращать скан, то только с replace-семантикой под локом и `flush`.
