# Разбор дефекта захвата «Отметки получено» в ОТБОРКЕ (PENDING_EDITS)

> Жалоба: при одиночной и массовой отметке чекбокса «Отметка получено» (ОТБОРКА) **не все позиции попадают в лист `PENDING_EDITS`** (чекбокс стоит, а строки намерения нет). При повторном «снял → поставил» позиция фиксируется **и как снятие, и как постановка**.
>
> Вывод: это дефекты **этапа захвата намерения** (`v12OnEdit` → `v12CaptureCheckboxEdit` → `v12EnqueuePendingRows`). Мои оптимизации применяются на этапе ПРИМЕНЕНИЯ и на захват не влияют.

## Как работает захват (ТЗ-путь)

1. Пользователь ставит чекбокс(ы) в ОТБОРКЕ (колонка `CHECKBOX` = 12) → `v12OnEdit` (`v12_trigger.js`).
2. `v12CaptureCheckboxEdit(e, "ОТБОРКА")` (`v12_queue.js`):
   - проверяет, что диапазон задевает колонку 12;
   - проверяет роль;
   - берёт значения чекбоксов из `e.value` (одна ячейка) или `e.values`/`range.getValues()` (диапазон);
   - читает `Position ID` (кол. 1) **отдельным** `sheet.getRange(firstRow, 1, numRows, 1).getValues()`;
   - по каждой непустой позиции строит строку намерения (`v12BuildPendingRow`) и зовёт `v12EnqueuePendingRows`.
3. `v12EnqueuePendingRows` дописывает пачку:
   ```js
   const sheet = v12GetSheetByKey("PENDING_EDITS");
   const startRow = sheet.getLastRow() + 1;   // ← ГОНКА
   writeValues(sheet, startRow, 1, rowArrays);
   v12UpdatePendingIndicator();               // читает лист ещё раз
   ```

## Первопричины

### Причина 1 (главная, «не все позиции»): потеря строк из-за гонки записи в `PENDING_EDITS`
`v12EnqueuePendingRows` **не сериализован** и вычисляет `startRow = getLastRow() + 1`. При быстрых одиночных/массовых отметках Google запускает `onEdit` **несколько раз практически одновременно** (плюс повторные клики по чекбоксам, протяжка, заполнение). Две параллельные исполняемые среды читают **один и тот же** `getLastRow()` и пишут в **одну и ту же** строку `K+1` — вторая запись **перезатирает первую**. Часть позиций бесследно «пропадает»: чекбокс пользователь поставил, а строки намерения нет.

Усугубляющие факторы:
- **В быстром пути onEdit нет лока** (так задумано в модели V3 — «быстро, без лока»). Именно это открывает гонку на записи в очередь.
- **`v12BuildPendingRow` вызывает `generateEventId()` = `Utilities.getUuid()` на КАЖДУЮ строку.** Это RPC: захват пачки из десятков строк выполняется долго, окно перекрытия исполнений растёт, частота потерь увеличивается.
- `v12UpdatePendingIndicator()` сразу после записи **снова читает весь лист** — ещё один RPC, удлиняющий окно.

### Причина 2 («off и on сразу»): очередь append-only + «последний побеждает» применяется только при Apply
`v12EnqueuePendingRows` **только добавляет** строки и **не схлопывает** прежние намерения по тому же ключу `(SOURCE, POSITION_ID, FIELD)`.
- Пользователь снял галочку → строка со `VALUE=false`.
- Пользователь снова поставил → добавляется ЕЩЁ строка со `VALUE=true`.

Обе строки лежат в `PENDING_EDITS` до применения. Итоговое решение принимает `v12ResolvePendingIntents` (last-wins) — но «последняя» определяется **порядком строк**, а порядок при гонке (Причина 1) может оказаться **перепутанным**: снятие может попасть физически ниже постановки → позиция решится как ОТМЕНА, хотя галочка стоит. Отсюда и ощущение «отмечается и на выключение, и на включение».

### Причина 3 (вторичная, «чекбокс есть — позиции нет»): строки без Position ID и «фантомные» чекбоксы
`v12CaptureCheckboxEdit` **пропускает** строки с пустым `Position ID` (`if (!positionId) continue;`). Если пользователь задел строку, где колонка A пуста (пустая строка-разделитель, пограничная строка при протяжке), чекбокс визуально стоит, а намерения нет. Само по себе это редкость, но при протяжке диапазона вниз за пределы данных — реально.

### Причина 4 (вторичная): потенциальное расхождение «значение чекбокса» ↔ «Position ID»
Значения чекбоксов берутся из события (`e.values`/`e.value`), а `Position ID` — **отдельным живым чтением** уже после события. Если между правкой и обработчиком лист успел перестроиться (например, другой пользовательский Apply пересобрал ОТБОРКУ — `v12RefreshPicking` очищает тело и пишет чекбоксы = `false`, строки могут переупорядочиться), то `idColumn[r]` может **не соответствовать** строке `firstRow+r`. Тогда намерение записывается на «соседнюю» позицию, а нужная — отсутствует.

## Предлагаемое исправление

### Fix 1. Сериализовать дописывание очереди (устраняет потерю строк)
Обернуть запись в `PENDING_EDITS` коротким общескриптовым локом и **перечитывать `getLastRow()` уже под локом**:
```js
function v12EnqueuePendingRows(rowArrays) {
  if (!rowArrays || !rowArrays.length) return;
  const lock = acquireScriptLock({ tryOnly: true, timeoutMs: 10000 });
  if (!lock) {
    // Лок занят (идёт Apply/полный синк): сообщаем, а не теряем молча.
    logSystem("v12EnqueuePendingRows", "Очередь занята, намерение не зафиксировано", "WARNING");
    flushSystemLog();
    return;
  }
  try {
    const sheet = v12GetSheetByKey("PENDING_EDITS");
    const startRow = sheet.getLastRow() + 1;   // читаем ПОД локом
    writeValues(sheet, startRow, 1, rowArrays);
  } finally {
    lock.releaseLock();
  }
  v12UpdatePendingIndicator();
}
```
Лок короткий (только запись строки), проекции не пересобираются — гонку с пересборкой он не возвращает.

### Fix 2. Upsert намерения вместо append (устраняет «off+on», стабилизирует last-wins)
Перед добавлением — искать существующую `PENDING`-строку по `(SOURCE, POSITION_ID, FIELD)` и **обновлять** её (`VALUE`, `USER`, `DATE`) вместо создания новой. Если нет — дописывать. Тогда на ключ всегда ровно одно актуальное намерение:
- «снял → поставил» = одна строка со значением `true`;
- применение однозначно, независимо от порядка.

Требуется один предварительный `readSheetValues(PENDING_EDITS)` в захвате (под тем же локом). Приемлемо: захват одиночный, очереди обычно небольшие; надёжность важнее.

### Fix 3 (страховка). Реконсиляция при Apply: подхватывать «поставленные, но не зафиксированные» чекбоксы
В `v12DrainPendingEdits` (или перед ним) — просканировать колонку `CHECKBOX` листов ОТБОРКА/WORKING BOM: строки с `true`, для которых нет `PENDING`/`DONE`-намерения HANDOFF в очереди, трактовать как намерение передачи. Это гарантирует инвариант **«галочка стоит ⇒ позиция будет передана»**, даже если `onEdit` был потерян/пропущен (Google может «глотать» всплески событий). Реконсиляция выполняется один раз на пачку — дёшево.

### Fix 4 (ускорение захвата). Не генерировать UUID на каждую строку очереди
`EDIT_ID` в `v12BuildPendingRow` — не критичен для идентичности намерения. Можно:
- генерировать один `Edit ID` на пачку и добавлять локальный суффикс; либо
- делать `EDIT_ID` лениво (только при записи), либо
- заменить `Utilities.getUuid()` на локальный счётчик+timestamp.
Это сокращает время захвата и окно гонки.

### Fix 5 (устойчивость к рассинхрону, Причина 4). Читать Position ID и значения чекбоксов из ОДНОГО снимка
Брать весь нужный диапазон (`getRange(firstRow, 1, numRows, numCols).getValues()`) один раз и использовать его и для `Position ID`, и для значения чекбокса — тогда значения и ключи гарантированно из одного состояния листа (без промежуточного перестроения).

## Рекомендуемый минимальный набор
- **Fix 1** (лок + `getLastRow()` под локом) — обязателен, устраняет пропажу строк.
- **Fix 2** (upsert) — устраняет дубли «off+on» и делает last-wins однозначным.
- **Fix 3** (реконсиляция) — страховка от потерянных событий; закрывает инвариант «галочка ⇒ передача».
- **Fix 4/5** — ускорение/устойчивость, применяются попутно.

## Что важно НЕ сломать
- Быстрый путь onEdit не должен заново тянуть пересборку проекций: лок только на запись строки.
- Идемпотентность применения (`v12MarkReceivedByProduction`), «передача только вверх», last-wins — сохраняются; Fix 2 делает очередь детерминированной.
- Если в очередь пишет и `v12CaptureDeficitEdit` (Сводка), upsert и лок должны применяться и к нему единообразно.

# РЕАЛИЗОВАНО (исправления внесены и проверены)

> Все правки — в `v12_queue.js`, без изменения схем листов и публичных сигнатур. Одиночный режим передачи не затронут.

## Внесённые изменения

### Fix 1 — сериализация записи в PENDING_EDITS (устранение «пропажи» строк)
`v12EnqueuePendingRows` теперь берёт короткий общескриптовый лок и вычисляет `getLastRow() + 1` **под локом**. Параллельные `onEdit` больше не перезатирают строки друг друга. При занятом локе — безопасный отказ с записью в системный лог (без гоночной перезаписи).

### Fix 2 — UPSERT намерения по ключу (устранение дублей «off+on»)
`v12EnqueuePendingRows` ищет существующую `PENDING`-строку по ключу `SOURCE|POSITION_ID|FIELD` и **обновляет** её (`DATE`/`VALUE`/`USER`/`EDIT_ID`, сбрасывает `PROCESSED_AT`/`ERROR`), иначе добавляет. Итог: в очереди максимум одно актуальное намерение на ключ → применение детерминировано. Добавлена функция `v12PendingKey`. Уже обработанные (`DONE`/`FAILED`) строки не воскрешаются — по тому же ключу добавляется свежая `PENDING`.

### Fix 3 — реконсиляция потерянных галочек (инвариант «галочка ⇒ передача»)
Добавлены `v12HasCheckedHandoffs()` и `v12ReconcileCheckedHandoffs(queueData)`:
- `v12DrainPendingEdits` запускается, если есть очередь **ИЛИ** стоят галочки передачи;
- перед применением читаются колонки `CHECKBOX` ОТБОРКИ и WORKING BOM; любая строка с установленной галочкой, для которой в очереди **нет** намерения HANDOFF, добавляется синтетическим намерением передачи (`row: 0`, применять идемпотентно);
- синтетические намерения не пишутся в `failed` (нет строки очереди).

### Fix 4 — один Edit ID на захват
`v12BuildPendingRow(..., editId)` принимает необязательный ID; `v12CaptureCheckboxEdit`/`v12CaptureDeficitEdit` генерируют **один** `editIdBase = generateEventId()` на захват, а строки получают `editIdBase + "-N"` (без RPC `Utilities.getUuid()` на каждую строку).
