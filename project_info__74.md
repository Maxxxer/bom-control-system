# BOM CONTROL SYSTEM V12 — Отчёт: экономист не мог поставить галочку «Реальная поставка»

> Задача: «исправь — экономист сейчас не может ставить галочку «Реальная поставка» в «Сводке дефицитов»».

---

## 1. Диагностика (что именно было не так)

Матрица прав (`v12_roles.js::v12CanEditField`) для роли `ECONOMIST` **уже** разрешала `REAL_DELIVERY`, а
`_local_tests/v12_roles_test.js` (R1/R3) это подтверждал — то есть право есть, а в бою галочка не ставилась.

Причина — **не RBAC-матрица, а определение пользователя на момент правки**:

1. Захват правки (`v12CaptureDeficitEdit`) делал вывод «прав нет» из пустого результата
   `v12GetCurrentUserRole()` и **откатывал галочку** (`v12RevertEdit`).
2. `v12GetCurrentUserRole()` считает роль по e-mail, а e-mail берётся из `Session.getActiveUser().getEmail()`.
   Это **документированное ограничение платформы**: адрес «доступен только в контексте, где скрипт исполняется
   ПО АВТОРИЗАЦИИ этого пользователя» — в исполнении по установленному `onEdit`-триггеру чужого (не владельца)
   аккаунта метод возвращает **пустую строку** (docs: `Session.getActiveUser()` →
   «the user's email address is not available in any context that allows a script to run without that user's
   authorization, like a simple onOpen(e) or onEdit(e) trigger»).
3. Запасной путь «пользователь указал e-mail сам» (`V12_USER_EMAIL` в свойствах ПОЛЬЗОВАТЕЛЯ) в триггере тоже
   не работает: свойства пользователя доступны «текущему **ИЛИ ЭФФЕКТИВНОМУ** пользователю»
   (docs: `PropertiesService.getUserProperties()`), а эффективный пользователь установленного триггера —
   владелец таблицы. Поэтому сохранённый экономистом адрес в триггере не виден.

Итог для пользователя: галочка визуально ставилась и тут же «сама снималась» (правка откатывалась как
запрещённая), хотя право у роли есть. Тот же дефект касался любой правки любых ролей в таблице-мастере
(снабженец, кладовщик, производство), если владелец таблицы и исполнитель — разные аккаунты.

---

## 2. Почему нельзя просто «отдать адрес» триггеру

Единственные сущности, которые платформа отдаёт в исполнении без авторизации пользователя, — **анонимные**:

* `Session.getTemporaryActiveUserKey()` — «temporary key that is unique to the active user but does not reveal
  the user identity» (меняется раз в 30 дней, уникален для скрипта).

Поэтому архитектурное решение состоит из двух частей: **право проверяется там, где личность достоверно
известна** (при нажатии «ПРИМЕНИТЬ» — действие от имени пользователя), а для удобства добавлен **общий реестр
«анонимный ключ → e-mail»**, который заполняется один раз из меню «🔑 Мой доступ».

### Итоговое поведение

1. Экономист ставит галочку «Реальная поставка» — **правка больше не откатывается**, даже если платформа
   не раскрыла её e-mail: намерение фиксируется в очереди (автор — пусто).
2. Экономист нажимает **«ПРИМЕНИТЬ»** под своим аккаунтом — действие исполняется по его авторизации,
   роль определяется достоверно, намерение применяется (поставка = требуется, материал уходит на склад).
3. Если «ПРИМЕНИТЬ» нажал пользователь без права на это поле — намерение **не теряется** и не помечается
   ошибкой: оно остаётся в очереди, а в сообщении видно «Ждут применения под своим аккаунтом: N».
4. Фоновые сливы (полная синхронизация, дежурный триггер) намерения без автора **не применяют** — иначе
   правку коммитил бы владелец скрипта, и любой пользователь мог бы «протащить» изменение чужими руками.
5. Пользователь, который один раз указал e-mail в «🔑 Мой доступ», определяется и в триггере (через общий
   реестр по анонимному ключу) — тогда его правки проверяются сразу на захвате, как и раньше.

## 5. Что нужно сделать владельцу (в Google Apps Script)

1. `clasp push` — выгрузить изменённые файлы мастера (`_local_tests/**`, `_tmp_*`, `sat_*` исключены `.claspignore`).
2. Ничего дополнительно настраивать не требуется: экономист ставит галочки и нажимает **«ПРИМЕНИТЬ»**.
3. По желанию (ускоряет проверку прав прямо на захвате): пусть каждый пользователь один раз выберет
   меню **«BOM CONTROL V12» → «🔑 Мой доступ»** и укажет свой рабочий e-mail — он сохранится и в личных
   настройках, и в общем реестре по анонимному ключу (реестр хранится 30 дней, как и сам ключ).
4. Если всплывает «Ждут применения под своим аккаунтом: N» — применить должен тот, у кого есть право на эту
   колонку (экономист — «Реальная поставка», снабженец — «Заказано»/«Ожидаемая поставка» и т. д.).
