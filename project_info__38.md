# BOM CONTROL SYSTEM V12 — Разбор дефекта: окно «Система занята обновлением» при быстрой отметке чекбоксов

> **Режим:** Explore (только чтение). Изменения в коде не вносились.
> **Область исследования:** `v12_trigger.js`, `lock.js`, `v12_handoff.js`, `v12_projections.js`, `v12_sheet_service.js`, `sheet_service.js`, `v12_events.js`, `v12_audit.js` + история решений в `project_info__30/33/34/35`.
> **Цель:** объяснить причину появления модального окна, оценить последствия (сброс отметки) и предложить варианты устранения без слома бизнес-логики.

---

## 1. Суть проблемы (TL;DR)

При быстрой простановке галочек в листе **ОТБОРКА** (и в **WORKING BOM**) появляется модальное окно:

> «Система занята обновлением. Повторите ввод через несколько секунд.»

**Причина.** `v12OnEdit` пытается взять **скриптовую** блокировку (`LockService.getScriptLock()`) в режиме `tryOnly` с таймаутом 10 с. Блокировка — **общескриптовая** (одна на всех пользователей и все запуски), а одна отметка чекбокса выполняет **очень много** работы (полная передача производству + **пересборка всех 5 проекций целиком**). Пока идёт обработка первой галочки, она держит лок; каждая следующая правка не дожидается освобождения за 10 с → `null` → окно.

**Вторая, более вредная часть.** В ветке «лок не взят» для одиночной ячейки вызывается `v12RevertEdit(e)` — **галочка принудительно снимается**. Т.е. отметка не просто «не применилась», а визуально **откатывается**, и пользователь должен ставить её заново, снова попадая в ту же гонку.

**Главная мысль.** Само окно и сброс — это одна ветка кода (`if (!lock)`). Убрать окно и сброс технически просто; но чтобы отметка при этом **гарантированно** сохранялась, нужен «подхват» отложенных отметок (он в системе **уже есть** — `v12HarvestPickingInput`), и желательно сократить время удержания лока.

## 2. Что это за проект (в двух абзацах)

**BOM CONTROL SYSTEM V12** — система управления спецификациями (BOM) и снабжением на **Google Apps Script** (runtime V8), без сборки и внешних зависимостей: все функции — глобальные, деплой через `clasp` (`.clasp.json`). Данные — в Google Sheets.

Архитектура строго разделяет три уровня (зафиксировано в `v12_config.js`):

```
ORIGINAL BOM (источник в Drive, read-only)
  → BOM_REGISTRY (реестр: ревизии, dirty-флаг)
    → POSITION_STATE (центральное операционное состояние, 31 колонка)
      → MATERIAL_STATE (физический склад, 9 колонок)
      → проекции: DEFICIT_SUMMARY / ОТБОРКА / WORKING BOM / СНАБЖЕНИЕ / DASHBOARD
```

Точки входа: `onOpen()` → меню «BOM CONTROL V12» (`v12_controller.js`), `v12OnEdit` (установленный onEdit-триггер) и `v12ScheduledUpdate` (**раз в час**). RBAC — `v12_roles.js`, аудит — `v12_audit.js` (буферизованный), журналы — `v12_events.js`.

Замечу: система **исторически и осознанно** боролась с производительностью (`project_info__30/33/34`), и текущее поведение с окном — это **следствие** ранее рекомендованного исправления (`tryLock` + уведомление, см. §6).

## 3. Где именно возникает окно (точная точка)

**Файл `v12_trigger.js`, функция `v12OnEdit(e)`**, блок:

```js
const lock = acquireScriptLock({ tryOnly: true, timeoutMs: 10000 });
if (!lock) {
  // Блокировку не удалось взять за 10 с — вероятно идёт полная синхронизация.
  try {
    SpreadsheetApp.getUi().alert("Система занята обновлением. Повторите ввод через несколько секунд.");
  } catch (e2) { /* нет UI — просто выходим */ }
  if (isSingleCell) {
    v12RevertEdit(e);   // ← ЭТО СНИМАЕТ ГАЛОЧКУ
  }
  return;
}
```

Единственное место в проекте с этим текстом (проверено поиском по всему репозиторию). Рядом — комментарий, прямо объясняющий мотивацию:

```js
// ВАЖНО: правка не отбрасывается по флагу занятости — при плановом
// обновлении она дождётся освобождения блокировки и будет обработана.
```

Т.е. **намерение** было «не терять правку», но фактически для одиночной ячейки правка как раз **теряется** (галочка снимается, применение не происходит).

**Механизм лока — `lock.js`, `acquireScriptLock(options)`:**

```js
function acquireScriptLock(options) {
  if (_lockDepth > 0) { _lockDepth++; return { releaseLock: ... }; }  // реентрантность
  const lock = LockService.getScriptLock();                            // ← ОДИН на весь скрипт
  if (opts.tryOnly) {
    if (!lock.tryLock(timeoutMs)) return null;   // ← ждёт до timeoutMs, потом null
  } else {
    lock.waitLock(timeoutMs);                     // ← по умолчанию бросает исключение
  }
  ...
}
```

`LockService.getScriptLock()` — **общескриптовая** блокировка: она одна и на всех пользователей, и на все параллельные исполнения (onEdit, часовой синк, меню). Значит, окно может появиться даже у **одного** пользователя, который кликает быстро, и **тем более** при одновременной работе двух кладовщиков.

## 4. Почему лок держится так долго (стоимость ОДНОЙ галочки)

Путь одной одиночной отметки в ОТБОРКЕ:

```
v12OnEdit (захват лока)
 └ v12HandlePickingEdit
    └ v12MarkReceivedByProduction(positionId, PICKING)   // skipRefresh = false!
       ├ v12BuildPositionIndex()            → ПОЛНОЕ чтение POSITION_STATE
       ├ v12UpdatePosition(...)             → batchWrite
       ├ v12ArchivePosition(...)
       │   ├ v12GetPositionHistory()        → ПОЛНОЕ чтение MATERIAL_HISTORY (растёт со временем!)
       │   └ appendRow(ARCHIVE) + v12UpdatePosition(...)
       ├ v12AdjustWarehouseQty()            → ПОЛНОЕ чтение MATERIAL_STATE + batchWrite
       ├ v12Audit() + v12LogHistory() (appendRow→MATERIAL_HISTORY)
       │            + v12LogEvent() (appendRow→EVENT_LOG)
       └ v12RefreshProjections()            ← ГЛАВНЫЙ ЦЕННИК ВРЕМЕНИ
          ├ чтение POSITION_STATE
          ├ v12HarvestDeficitInput()        → чтение «Сводки» (+ возможно перезапись POSITION_STATE/MATERIAL_STATE)
          ├ v12HarvestPickingInput()        → чтение ОТБОРКИ + индексы POSITION_STATE/MATERIAL_STATE
          ├ v12RefreshDeficitSummary()      → clearBody + setValues + clearDataValidations(вся высота) + setDataValidation + setBackgrounds
          ├ v12RefreshPicking()             → clearBody + setValues + валидации + setBackgrounds + фильтр B1
          ├ v12RefreshWorkingBOM()          → clearBody + setValues + валидации
          ├ v12RefreshSupply()              → clearBody + setValues + автофильтр
          └ v12RefreshDashboard()           → clearBody + setValues + валидации + условное форматирование + notes
```

Итого на **одну** галочку: **8+ листов**, десятки обращений к SpreadsheetApp, несколько **полных** чтений/записей больших листов и, что особенно дорого, `clearDataValidations()` + `setDataValidation()` **на всю высоту колонки** в 5 листах и `setBackgrounds()` по всем строкам.

> Время исполнения одного onEdit в Apps Script на реальных объёмах легко достигает **десятков секунд**. Это и есть источник «занятости».

Отдельно: `v12GetPositionHistory()` внутри архивации читает **весь** `MATERIAL_HISTORY`, который монотонно растёт с каждой операцией (каждый заказ/дата/поставка/передача пишет строку). Это плохо масштабируется и удлиняет удержание лока.

## 5. Сценарий воспроизведения (таймлайн)

1. `t=0` — пользователь ставит галочку в строке №1 ОТБОРКИ.
   → Google применяет значение в ячейку, затем запускает `v12OnEdit_A`. Тот **берёт лок** и уходит в тяжёлую обработку (~10–30 с).
2. `t=1–2` — пользователь ставит галочку в строке №2.
   → запускается `v12OnEdit_B`; `tryLock(10000)` **ждёт** освобождения.
3. `t≈12` — `v12OnEdit_B` **не дождался** за 10 с → `lock === null` →
   показывается **окно** «Система занята обновлением…»,
   затем `v12RevertEdit` **снимает галочку** в строке №2.
4. `t=2…30` — галочки №3…№10 повторяют судьбу №2 (окно, сброс).
5. `t≈15–30` — `v12OnEdit_A` завершается: позиция №1 передана, заархивирована, пересобраны все проекции, лок освобождён.
6. Итог для пользователя: одна отметка «прошла», остальные **сброшены**, и всё это сопровождалось серией раздражающих окон.

Дополнительный риск: `v12RefreshPicking()` в конце каждого пересчёта **перезаписывает колонку чекбоксов значением `false`** для всех активных строк. Значит, любая отметка, «оставленная» на листе, но не обработанная до пересборки, будет стёрта. Именно поэтому подхват отложенных отметок (`v12HarvestPickingInput`) в `v12RefreshProjections` выполняется **до** перезаписи листов — это ключевой инвариант (см. §8).

## 6. История: «предыдущий вариант» и почему простой откат не решает задачу

По отчётам `project_info__30` (пункт **P8**), `project_info__33/34` (пункт **C-2**):

- **Ранее** `acquireScriptLock()` использовал `lock.waitLock(LOCK_TIMEOUT = 30000)`. При тайм-ауте `waitLock` **бросает исключение**, `v12OnEdit` его перехватывал и писал в лог — **правка не применялась молча**, окна не было.
- Рекомендация аудита была дословно: *«в onEdit использовать `tryLock`/короткий тайм-аут + понятное уведомление пользователю»* (C-2), и *«`waitLock(30000)` → `tryLock` + очередь через time-driven триггер»* (P8).
- В результате появился текущий код: `tryLock(10000)` + `alert` + `v12RevertEdit`.

**Вывод:** «предыдущий вариант» (`waitLock(30000)`) **тоже терял** отметку — просто без окна. Откат к нему вернёт «тихую потерю» и потенциальные 30-секундные зависания. **Правильный путь — не откат, а реализация второй половины рекомендации P8 — «очереди/подхвата», без сброса галочки.**

Значение `LOCK_TIMEOUT = 30000` живёт в `v12_config.js → SETTINGS.LOCK_TIMEOUT` и используется как дефолт для `v12ScheduledUpdate` / `v12RunFullSync`.

## 7. Варианты решения

### Вариант A. Убрать окно и убрать сброс (минимальное вмешательство)
В ветке `if (!lock)` — не показывать `alert`, не вызывать `v12RevertEdit`, просто `logSystem(...)` + `return`. Значение галочки **остаётся** в ячейке (Google применил правку до вызова onEdit).

- ➕ Минимальная правка одной ветки, риск слома бизнес-логики близок к нулю.
- ➖ Отложенные отметки применятся только при **следующем** `v12RefreshProjections` — а ближайший гарантированный триггер это **часовой** `v12ScheduledUpdate`. То есть возможна задержка до часа.
- ➖ Сброс перестаёт быть мгновенным, но перезапись чекбоксов при пересборке ОТБОРКИ всё равно обнулит необработанную галочку (нужен подхват).

### Вариант B. A + «догоняющий» 1-минутный триггер (рекомендуемый минимум)
К варианту A добавить новый триггер `v12ScheduledCatchUp` (раз в 1 минуту), который:
- сначала **дешёво** проверяет без лока, есть ли необработанные отметки (есть ли в ОТБОРКЕ/WORKING BOM/Сводке `true` в чекбокс-колонке);
- только если есть — берёт лок и вызывает `v12RefreshProjections()` (который **сам** подберёт отложенные отметки через `v12HarvestPickingInput` / `v12HarvestDeficitInput`) и освобождает лок.

- ➕ Отметка **гарантированно** применяется в пределах ≤1 минуты, без окон и без сброса.
- ➕ Переиспользует уже существующий и протестированный механизм harvest (см. тест S8/S9 в `_local_tests/v12_delivery_test.js`).
- ➖ Даёт небольшую задержку применения (до 1 мин) — состояние «На складе»/списки обновятся с запозданием.
- ➖ +1 триггер к квоте проекта.

### Вариант C. Уменьшить время удержания лока (чтобы гонки почти не возникало)
Сократить стоимость одного пересчёта:
- не пересобирать **все** проекции из одиночного onEdit; помечать `BOM_REGISTRY.DIRTY` и откладывать пересборку на фоновый триггер (направление K7 «инкрементальное обновление проекций»);
- валидации чекбоксов переустанавливать **только при изменении числа строк** (как сделано для условного форматирования DASHBOARD), а не на каждом пересчёте;
- в `v12GetPositionHistory()` не читать весь `MATERIAL_HISTORY`, а фильтровать по позиции одним запросом/индексом;
- в одиночном пути ОТБОРКИ переиспользовать общий `ctx` с индексами (как в диапазонном пути `v12HandlePickingRangeEdit`).

- ➕ Лечит первопричину: лок удерживается ~1–2 с, окно становится практически недостижимым.
- ➖ Наибольший объём изменений; затрагивает несколько модулей; требует повторной проверки инвариантов.

### Вариант D. Полноценная очередь правок (архитектурный, «как в P8»)
onEdit для чекбокса **не выполняет** операцию: быстро пишет строку в служебный лист `PENDING_EDITS` и выходит. Триггер раз в 1 минуту **пакетно** разбирает очередь (батч-обработка, один лок, один пересчёт). Это самая масштабируемая схема.

- ➕ Максимально быстрый onEdit, идеальная пакетная обработка, нет окон/сбросов.
- ➖ Новый лист, миграция, больше кода; избыточно, если достаточно B/C.

**Рекомендация:** поэтапно — **сначала B** (снять раздражение и гарантировать сохранение отметки), затем при желании **C** (убрать первопричину по производительности). D — опционально на будущее.

## 8. Скрытые инварианты, которые нельзя ломать

Это самая важная часть для реализации — соответствие существующей бизнес-логике.

1. **Harvest обязан идти ДО перезаписи листов.** В `v12RefreshProjections` порядок:
   ```
   read POSITION_STATE
   → v12HarvestDeficitInput()   // подбирает введённые значения из «Сводки»
   → v12HarvestPickingInput()   // подбирает отметки из ОТБОРКИ  ← СНАЧАЛА
   → затем v12RefreshDeficitSummary/Picking/...  ← перезапись
   ```
   Если поменять порядок (сначала перезаписать проекцию), отметки будут стёрты. Любая доработка должна сохранять этот порядок.

2. **`v12MarkReceivedByProduction` идемпотентна.** Повторный вызов для уже переданной позиции возвращает `{status:"already"}` и ничего не делает. Это делает безопасным многократный подхват одной и той же галочки. Не нарушать.

3. **Передача уменьшает склад и архивирует позицию — операция необратима из листа** (только через меню «↩ Вернуть из архива»). Пункт **B-2** отчёта №34: чекбокс работает **в одну сторону** (снятие галочки ничего не делает). Значит, «откладывание» отметки на минуту — не потеря, но и не повод обрабатывать её дважды.

4. **Валидации чекбоксов — зона риска.** `sheet_service.js :: clearRange` больше **не** вызывает `clearDataValidations()` (специально — см. комментарий и историю P7 в отчётах №33/34), а каждый владелец валидации (`v12InstallPickingCheckboxes`, `v12InstallDeficitCheckboxes`, `v12InstallDashboardCheckboxes`, `v12InstallWorkingBomCheckboxes`, `v12InstallPickingBomFilter`) восстанавливает свою. Любая правка, добавляющая `clearDataValidations` в generic-очистку, снова «убьёт» чекбоксы.

5. **Глобалы в Apps Script НЕ переживают запуски.** `_v12ProjectionUiState`, `_lockDepth`, `_v12AuditBuffer` существуют только внутри одного исполнения. Поэтому кэш-гварды (напр. `_v12ProjectionUiState.dashboardColorRows`) почти бесполезны между запусками — это уже отмечено в отчётах (P-9). Если делать «изменять валидации только при смене числа строк», состояние надо хранить в **PropertiesService**, а не в глобале.

6. **`e.value` vs живое чтение.** В обработчиках используется снимок `e.value` (надёжнее при быстром вводе). Не заменять обратно на `e.range.getValue()`.

7. **Реентрантность лока.** `v12OnEdit` берёт лок, а операции внутри (`v12MarkReceivedByProduction`) вызывают `acquireScriptLock()` повторно — это **no-op** благодаря `_lockDepth`. Не использовать `LockService` напрямую в обход `acquireScriptLock`.

8. **Буферизованный аудит.** `v12FlushAudit()` вызывается в `finally` на нескольких уровнях; при сокращении путей следить, чтобы накопленный буфер **не остался не сброшенным** (иначе записи аудита потеряются).

## 9. Ключевые абстракции (участвующие в дефекте)

### `v12OnEdit(e)` — `v12_trigger.js`
- **Ответственность:** входная точка всех правок; маршрутизация по листу/колонке; **сериализация правок через ScriptLock**.
- **Ключевая логика:** ранний выход для незначащих листов (до захвата лока), выбор пути single-cell vs range, `tryOnly:true, timeoutMs:10000`, ветка «лок не взят» (§3).
- **Точка правки для задачи.**

### `acquireScriptLock(options)` — `lock.js`
- **Ответственность:** единая реентрантная обёртка над `LockService.getScriptLock()`.
- **Режимы:** `tryOnly` → `tryLock(timeoutMs)`, иначе → `waitLock(LOCK_TIMEOUT)`.
- **Замечание:** лок общескриптовый → конкуренция даже между разными пользователями.

### `v12MarkReceivedByProduction(positionId, sourceUI, skipRefresh, ctx)` — `v12_handoff.js`
- **Ответственность:** идемпотентная передача позиции производству (валидация, архивация, списание склада, аудит/история/событие).
- **Параметры производительности:** `skipRefresh` (не пересчитывать проекции — для пакетного пути) и `ctx` (переиспользование индексов POSITION_STATE/MATERIAL_STATE и накопление складских дельт).
- **Важно:** одиночный путь из ОТБОРКИ вызывает его **без** `ctx` и **без** `skipRefresh` → максимум работы.

### `v12RefreshProjections()` — `v12_projections.js`
- **Ответственность:** один раз читает POSITION_STATE, выполняет harvest, строит map-ы ревизий/исключений и **пересобирает все 5 проекций**.
- **Роль в дефекте:** главный потребитель времени внутри лока. Содержит защиту `_v12Harvesting` / `_v12HarvestingPicking` от рекурсии.

### `v12HarvestPickingInput(posData)` — `v12_projections.js`
- **Ответственность:** подобрать **уже проставленные, но не обработанные** галочки ОТБОРКИ и выполнить передачу (идемпотентно, `skipRefresh=true`, с общим `ctx`).
- **Роль:** это и есть готовый механизм «страховки от потерянных отметок». Именно его стоит использовать в варианте B.
- **Нюанс:** результат передачи (`blocked`) здесь игнорируется (в отличие от диапазонного пути, где галочка снимается при `blocked`) — при пересборке ОТБОРКИ ячейка всё равно обнулится.

### `v12HandlePickingRangeEdit(e)` — `v12_trigger.js`
- **Ответственность:** обработка **диапазона** галочек (вставка/автозаполнение) — читает Position ID одним `getValues()`, накапливает `wharehouseDelta`, пересчитывает проекции **один раз** в конце.
- **Роль:** это уже оптимизированный «эталон» того, как должна выглядеть пакетная обработка; одиночный путь стоит приблизить к нему.

## 10. Поток данных (путь быстрой отметки — как есть)

1. Пользователь ставит галочку → Sheets применяет значение → Google вызывает `v12OnEdit(e)`.
2. `v12OnEdit`: определяет лист `ОТБОРКА`, одиночная ячейка, колонка `CHECKBOX` (12).
3. `acquireScriptLock({tryOnly:true, timeoutMs:10000})`:
   - **взял** → `v12HandlePickingEdit` → `v12MarkReceivedByProduction` → … → `v12RefreshProjections()` (пересборка 5 листов) → `finally`: `releaseLock`, `v12FlushAudit`.
   - **не взял** → окно + `v12RevertEdit` (снятие галочки) + `return`.
4. Внутри `v12RefreshProjections` — harvest подхватывает все «висящие» галочки из ОТБОРКИ (и значения из «Сводки») **до** перезаписи листов.

**Целевой поток (вариант B):** шаг 3 «не взял» → тихий `return` **без сброса**; отложенная галочка применяется ближайшим запуском `v12ScheduledCatchUp` (≤1 мин) через тот же harvest.
