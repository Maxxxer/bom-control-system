# BOM CONTROL SYSTEM

Веб-приложение управления обеспечением сборочного производства: спецификации,
потребность в материалах, заказы и поставки, склад, отборка и передача материалов
производству.

Приложение реализует те же правила расчёта и те же формулировки статусов, что и
прежняя система на Google Sheets: сотрудники видят привычные статусы и цвета строк,
но работают в обычном браузере с серверной базой данных, сессиями и журналом
изменений.

## Что умеет система

- **Спецификации (BOM).** Импорт перетаскиванием файла или через выбор: `.xls`,
  `.xlsx` и `.csv, можно несколько файлов за раз; список, карточка с позициями
  (детали и сборочные единицы), удаление, отметка «Выполнено».
- **Сводка дефицитов.** По каждой позиции: потребность, заказано, ожидаемая
  поставка, фактический приход, крайний срок и статус. Правка прямо в строке —
  снабженец и экономист меняют свои поля, не переходя в другие окна.
- **Снабжение.** Свод по материалам: строка материала и все проекты, где он нужен.
- **Склад.** Фактический остаток вводит кладовщик; резерв складывается из
  потребностей активных спецификаций, свободный остаток = остаток − резерв.
  Строки, где резерв больше остатка, выделяются как требующие внимания.
- **Отборка.** Строки «на складе» отмечаются и передаются производству одним
  нажатием; строки без остатка передать нельзя — система объясняет причину.
- **WORKING BOM.** Доступность материала: резерв, фактический приход, уже
  переданное; передача по одной строке.
- **Дашборд.** Состояние спецификаций: передано, ждёт отборки, ждёт поставки,
  ближайший срок; отметка «Выполнено». Спецификации, отмеченные выполненными,
  в рабочий список не попадают.
- **Архив передач.** Каждая передача фиксируется; запись можно вернуть в работу
  с обязательной причиной.
- **Пользователи и доступы.** Роли, включение и отключение доступа, смена пароля.
  Смена роли или пароля немедленно закрывает сессии этого пользователя.
- **Журнал действий.** Кто, когда и что изменил: заказы, сроки, поставки,
  складские остатки, передачи, импорт и удаление спецификаций, возвраты из архива.

## Требования

- Node.js 20 или новее.
- npm 10 или новее (используются рабочие пространства npm).
- PostgreSQL не обязателен: по умолчанию используется встроенная в приложение
  PGlite (PostgreSQL в WebAssembly), данные лежат в каталоге `server/data`.

## Быстрый старт

```bash
# 1. Зависимости (из корня репозитория)
npm install

# 2. Сборка интерфейса и сервера
npm run build

# 3. Запуск: сервер раздаёт и API, и собранный интерфейс
npm start
```

Откройте `http://localhost:8080`. При первом запуске, пока в базе нет ни одной
учётной записи, создаётся администратор:

- логин — `admin`;
- пароль — `admin12345` (значение по умолчанию; смените его после входа).

Если использован пароль по умолчанию, сервер пишет об этом предупреждение в журнал.

### Режим разработки

Два процесса: API на 8080 и Vite с горячей перезагрузкой на 5173 (Vite
проксирует `/api` на сервер, поэтому cookie сессии работают без настройки).

```bash
npm run dev       # сервер (API)
npm run dev:web   # интерфейс, http://localhost:5173
```

## Как считаются состояния

Расчёт перенесён из прежней системы без изменения смысла и проверен автотестами
(`server/test`).

- **Обеспечение позиции (`SupplyState`).** «Потребности нет» → «Закрыто резервом»
  → «Не заказано» → «Заказано частично» → «Заказано» → «Поставлено частично» →
  «Поставлено».
- **Состояние производства (`ProductionState`).** «Нет в наличии» → «Частично
  доступно» → «На складе» → «Передано». Доступно = резерв + приход, но не больше
  потребности.
- **Статус спецификации (`BomStatus`).** «Ошибка данных», «Скомплектован, готов к
  работе», «На складе, ждет отборки», «Есть незаказанные компоненты»,
  «Ожидается поставка (Опаздывает)», «Ожидается поставка (В срок)». Формулировки
  хранятся на сервере (`BOM_STATUS_LABEL`) и приходят в интерфейс готовым текстом.
- **Позиция без обязательных полей** (нет наименования, номера по спецификации или
  количества) получает состояние «Ошибка данных» и цвет серый — такие строки видно
  на дашборде и в карточке.
- **Цвета строк** перенесены из прежней системы без изменений (`COLORS`).

Даты вводятся и показываются как `ДД.ММ.ГГГГ`. Пустая ожидаемая дата означает
«срок ещё не сообщён поставщиком».

## Импорт спецификаций

Файл Excel или CSV передаётся содержимым в base64; имя файла без расширения
становится кодом спецификации, поэтому повторная загрузка файла с тем же именем
обновляет ту же спецификацию, а не создаёт вторую.

Поддерживаемые форматы:

| Формат | Когда используется |
| --- | --- |
| `.xls` | старый бинарный Excel (BIFF8) — архив спецификаций предприятия |
| `.xlsx`, `.xlsm` | обычная форма ведения спецификаций |
| `.csv`, `.txt` | выгрузка из таблицы; разделитель определяется автоматически |

Форматы читаются одинаково: один и тот же файл, сохранённый как `.xls` или как
`.xlsx`, даёт в системе одинаковые позиции — отдельной логики для старого Excel
нет. Даты в настоящих ячейках Excel (включая `.xls`) распознаются как даты, а не
как порядковые номера дней.

Файл с чужим содержимым, переименованный в `.xls`, отклоняется с объяснением:
сигнатура формата проверяется до разбора.

Требования к файлу:

- **обязательна одна колонка — наименование.** Колонка «№ п/п» не нужна: если её
  нет, номер строки берётся по порядку в файле;
- остальные колонки распознаются по заголовкам: количество, единица измерения,
  модель или артикул, производитель, крайний срок и другие;
- ограничения: размер файла — до 5 МБ, число строк — до 20 000 (`LIMITS`).

### Как распознаются заголовки

Боевые файлы написаны людьми и годами, поэтому заголовки в них исторически разные.
Распознавание рассчитано на это:

| В файле | Как понимается |
| --- | --- |
| `Наименование`, `Название`, `Описание`, `Номенклатура` | наименование |
| `Наименование 2206` | наименование (суффикс с номером проекта не мешает) |
| `Модель`, `Обозначение`, `Тип` | модель |
| `Производитель`, `Произв-тель`, `Произв.`, `Бренд` | производитель |
| `Кол-во`, `К-во`, `К-ВО`, `Количество` | количество |
| `Ед.изм`, `Ед. изм`, `ЕД.ИЗМ`, `Ед изм`, `Единица измерения`, `Ед` | единица измерения |
| `№ п/п`, `№`, `Строка` | номер строки (необязателен) |

Разделители в словах не учитываются, регистр не важен: `К-ВО`, `К-во` и `Кол-во` —
одна и та же колонка. `Ед.изм` и `Ед. изм` — тоже одна и та же колонка: точка,
пробел, регистр и лишняя точка в конце значения не имеют значения. Шапка ищется **во
всех первых 20 строках файла**: если перед таблицей стоит титул, он не мешает
импорту.

Если в файле встретились обе записи (`Ед.изм` и `Ед. изм`), это одна и та же
колонка: значение берётся из заголовка, написанного точно как синоним, а второй
столбец показывается в отчёте как **повтор колонки**. Такой повтор не является
потерянными данными — в отчёте об импорта он вынесен отдельно от нераспознанных
столбцов.

Если под один заголовок подходят сразу две колонки («Наименование» и
«Наименование позиции производителя»), система не угадывает — берёт первую, а
вторую перечисляет в отчёте.

### Отчёт об импорте

Отчёт показывает, сколько позиций создано, обновлено и пропущено, какие колонки
распознаны и какие строки требуют правки. Отдельно перечисляются **нераспознанные
колонки** — те, которым не сопоставлено ни одно поле:

> Не сопоставлено с полями (данные этих столбцов не импортированы): Примечание

Так потеря данных видна сразу, а не обнаруживается через месяц в отчёте.

Отчёт перечисляет только то, что человек дозаполняет руками: модель, единицу
измерения, количество. **Крайнего срока поставки в нём нет** — для него есть
отдельный шаг сразу после импорта, где срок вводится один раз для всей
спецификации. Позиция, которой не хватает только срока, в список замечаний не
попадает вовсе, но учитывается в счётчике безсрочных позиций.

Правило «без срока передать производству нельзя» при этом остаётся: срок
по-прежнему обязателен для передачи, просто спрашивается отдельно, а не
перечисляется в отчёте.

Отдельно перечисляются **повторы колонок** — `Ед.изм` и `Ед. изм` в одном файле:

> Повтор одной колонки (используется первая): Ед. изм = Ед.изм

### Как проходит импорт: от файла до работы

После перетаскивания файла система проводит спецификацию по шагам. Каждый шаг
показывается тем же способом — и человеку не нужно запоминать порядок.

1. **Отчёт об импорте.** Сколько позиций создано и обновлено, какие колонки
   распознаны, какие строки требуют правки.
2. **Крайний срок поставки.** Если в файле нет колонки со сроком, появляется окно
   «Введите требуемую дату поставки». Дата проставляется всем незаполненным
   позициям одной командой; позиции со сроком не меняются. Окно можно пропустить.
3. **Резерв из потребности.** Потребность копируется в резерв, но **только там,
   где резерв ещё пуст**. Если в файле есть своя колонка «Зарезервировано», её
   значения остаются: без резерва склад не может показать свободный остаток.
4. **«Все материалы доступны?»** — развилка:
   - **Да** — все позиции заполнены, спецификация принимается в работу и идёт по
     обычному пути: дефицит → заказ → склад → отборка → передача производству;
   - **Ввести отсутствующие позиции** — открывается карточка спецификации на
     правку. Экономист заполняет пропущенные поля и нажимает
     **«Сохранить и продолжить»**; кнопка активна, только когда незаполненных
     позиций не осталось, и показывает их количество. После неё спецификация
     идёт по тому же процессу.

Отметка «Выполнено» на этом шаге **не ставится**: она означает, что материалы уже
переданы производству, и ставится на дашборде производством в самом конце. Если
поставить её сразу после импорта, свежая спецификация исчезла бы из рабочего
списка и её материалы никто бы не заказал.

### Карточка спецификации

Карточка показывает только то, чем занимается экономист: описание позиции,
количество, резерв и крайний срок. Операционные поля («Заказано», «Поставлено»,
«Ожидаемая поставка») и служебные («Состояние», «Жизненный цикл») убраны — у них
свои рабочие экраны и свои роли. Состояние позиции видно по строке: цветом и
значком «Ошибка данных» с перечнем незаполненных полей.

**Номер строки («№ п/п») не редактируется** и не участвует в массовом вводе. Он
задаётся файлом, а если колонки «№ п/п» в файле нет — порядком строк в нём.
Правило поддержано и на сервере: поле не принимается ни одиночной правкой, ни
массовой вставкой (`Неизвестное поле: rowNo`). Нужно это для того, чтобы
нумерация всегда совпадала с источником: сдвинутые вручную номера рассинхронизировали
бы журнал и архив, а строки в отчётах ссылались бы на номера, которых в файле нет.

Поэтому импорт никогда не оставляет битый номер: если в колонке «№ п/п» файла
оказался ноль или пустая ячейка, позиция получает порядковый номер. Иначе она
навсегда осталась бы «Ошибкой данных» без возможности починить.

### Если в файле нет срока поставки

Крайний срок — обязательное поле: без него позицию нельзя передать производству.
В боевых спецификациях колонки срока часто нет вовсе, поэтому после импорта, если
остались позиции без срока, система показывает окно **«Введите требуемую дату
поставки»**.

Достаточно ввести дату один раз: она проставляется всем незаполненным позициям
спецификации одной командой. Позиции, у которых срок уже заполнен, не
изменяются. Команда видна в журнале действий как одно действие со своим
идентификатором, поэтому её можно вернуть целиком.

Карточка решает задачу правки спецификации: экономист видит, что именно не
заполнено, и дополняет прямо в строке, а затем подтверждает готовность кнопкой
«Сохранить и продолжить».

### Как загрузить файл

На экране «Спецификации» есть область для перетаскивания:

- **перетащите** файлы в область — при наведении она подсвечивается;
- **или нажмите** на область и выберите файлы диалогом (нужно с телефона и
  планшета, а также для работы одной рукой с клавиатуры);
- за один раз можно отпустить **несколько файлов** — они загружаются по очереди и
  дают отдельный отчёт по каждому.

Файлы неподходящего типа не отправляются на сервер: интерфейс сразу называет их и
показывает, какие форматы поддерживаются.

## Массовый ввод из Excel и возврат операции

Снабженец и экономист обычно ведут свои поля не по одной ячейке, а блоком: выгрузили
строки в Excel, поправили, вставили обратно. Поэтому в таблицах дефицитов, склада и
карточки спецификации работает выделение диапазона и вставка блока — как в самой
таблице.

| Действие | Как сделать | Что происходит |
| --- | --- | --- |
| Войти в ячейку | обычный щелчок | Правка одного поля, как раньше; вставка из другого окна работает штатно |
| Выделить блок | Shift+щелчок или Shift+стрелки | Ячейки подсвечиваются, появляется подсказка с размером выделения |
| Вставить из Excel | Ctrl+V при выделенном блоке | Данные ложатся от левого верхнего угла выделения |
| Скопировать в Excel | Ctrl+C при выделенном блоке | В буфер уходит текст с разделителями-табуляциями |
| Очистить ячейки | Delete | Количества становятся нулями, даты снимаются |
| Заполнить вниз / вправо | Ctrl+D / Ctrl+R | Значение верхней строки (или левой колонки) расходится по выделению |
| Снять выделение | Escape | Возврат к обычной правке в ячейке |

Как это устроено и почему так:

- **Значения разбирает сервер.** Клиент передаёт текст «как в ячейке» (`1 234,5`,
  `20.09.2026`, пустая строка), а правила разбора те же, что при обычной правке,
  поэтому один и тот же текст на разных экранах понимается одинаково.
- **Частичный успех.** Одна запрещённая полем или неразбираемая ячейка не отменяет
  остальные: сервер отвечает отчётом «применено / без изменений / отклонено» с
  причиной по каждой строке. Код 409 приходит только тогда, когда не применилось
  НИЧЕГО, — тогда интерфейс показывает причину вместо «успеха без изменений».
- **Одна команда на всю вставку.** Все ячейки применяются одной транзакцией и
  получают один идентификатор операции, поэтому в журнале вставка блока выглядит
  как одна команда, а не как сотня независимых правок.
- **Ячейки без массового ввода пропускаются и считаются.** Потребность, состояние,
  «Заказано» в карточке спецификации — это не поля ввода: сервер сообщает, сколько
  ячеек пропущено, а не «съедает» их молча.
- **Крупная вставка спрашивает подтверждение.** Начиная с 50 ячеек показывается
  диалог с числом изменений: случайная вставка на сотни строк не должна менять
  данные без спроса.
- **Правка описания не пересчитывает ключ материала.** Наименование, модель,
  артикул, производитель и единица измерения образуют ключ, к которому привязаны
  склад и снабжение. При вставке в эти колонки показывается одно предупреждение на
  всю команду: ключ останется прежним, а изменения вступят в силу при следующем
  импорте спецификации.

**Возврат операции.** В журнале действий у каждой команды есть кнопка «Вернуть»:
она записывает обратно прежние значения всех записей команды и требует причину.
Возврат — тоже одна команда со своим идентификатором и действием
(`OPERATION_ROLLBACK`), поэтому он виден в журнале и, при необходимости, сам может
быть возвращён. Строка, которую изменили ПОСЛЕ откатываемой команды, не трогается —
такая ячейка получает отказ с причиной, остальные возвращаются. Действия, у которых
правила возврата нет (передача производству, складской остаток, отметка
«Выполнено»), возвращаются вручную на своём экране: система честно отказывает, а не
делает вид, что вернула.

## Работа с PostgreSQL

Для небольшой установки достаточно PGlite: ничего устанавливать не нужно, данные
лежат в `server/data`. Для производственной установки задайте `DATABASE_URL`:

```bash
DATABASE_URL=postgresql://bom:пароль@localhost:5432/bom
```

Схема создаётся при запуске (`server/src/db/schema.ts`) одинаково для обоих
вариантов, поэтому перенос данных сводится к переносу таблиц. Различие только в
драйвере: `pgDatabase.ts` (сетевой PostgreSQL) и `pgliteDatabase.ts` (локальный
файл).

## Маршруты API

Все маршруты, кроме `/api/health`, требуют действующей сессии (cookie `bom_sid`).
Ошибки возвращаются в едином виде: код и текст, пригодный для показа пользователю.

**Вход и доступ**

| Метод и адрес | Назначение |
| --- | --- |
| `POST /api/auth/login` | Войти (ставит cookie сессии) |
| `POST /api/auth/logout` | Выйти |
| `GET /api/auth/me` | Кто я: данные пользователя и права роли |
| `POST /api/auth/password` | Сменить свой пароль |
| `GET /api/meta` | Справочники: роли и подписи прав |
| `GET /api/health` | Проверка живости сервера |

**Витрины рабочих экранов**

| Метод и адрес | Назначение |
| --- | --- |
| `GET /api/overview` | Данные главного экрана |
| `GET /api/deficit` | Сводка дефицитов (фильтр `project`) |
| `GET /api/supply` | Снабжение по материалам |
| `GET /api/picking` | Отборка (фильтр `project`) |
| `GET /api/working-bom` | WORKING BOM (фильтр `project`) |
| `GET /api/dashboard` | Дашборд спецификаций |
| `GET /api/projects` | Коды проектов для фильтров |

**Позиция (правка прямо в строке)**

| Метод и адрес | Право | Назначение |
| --- | --- | --- |
| `GET /api/positions/:positionId` | — | Карточка позиции |
| `GET /api/positions/:positionId/history` | — | История изменений позиции |
| `POST /api/positions/:positionId/ordered` | `ORDERED_QTY` | Изменить «Заказано» |
| `POST /api/positions/:positionId/expected-date` | `EXPECTED_DATE` | Изменить ожидаемую поставку |
| `POST /api/positions/:positionId/real-delivery` | `REAL_DELIVERY` | Отметить фактический приход |
| `POST /api/positions/:positionId/deadline` | `DEADLINE` | Изменить крайний срок |
| `POST /api/positions/bulk` | по полю каждой ячейки | Массовая правка: блок ячеек одной командой |
| `POST /api/operations/:operationId/rollback` | по полю каждой записи | Вернуть значения команды (причина обязательна) |

**Передача производству и архив**

| Метод и адрес | Назначение |
| --- | --- |
| `POST /api/handoff` | Передать позиции производству (списком) |
| `POST /api/handoff/readiness` | Проверить, какие строки можно передать |
| `GET /api/archive` | Архив передач |
| `POST /api/return-from-archive` | Вернуть позиции в работу (с причиной) |

**Склад**

| Метод и адрес | Назначение |
| --- | --- |
| `GET /api/warehouse` | Остатки, резервы, свободный остаток, несоответствия |
| `GET /api/warehouse/summary` | Короткая сводка склада |
| `POST /api/warehouse/:materialKey` | Установить фактический остаток |
| `POST /api/warehouse/bulk` | Массовый ввод остатков: блок ячеек одной командой |

**Спецификации**

| Метод и адрес | Назначение |
| --- | --- |
| `GET /api/boms` | Список спецификаций с числом позиций |
| `GET /api/boms/:code` | Карточка спецификации с позициями |
| `POST /api/boms/import` | Импорт из Excel (`.xls`, `.xlsx`) или CSV (файл в base64) |
| `POST /api/boms/:code/done` | Отметка «Выполнено» и возврат в работу |
| `DELETE /api/boms/:code` | Удалить спецификацию с позициями |

**Администратор** (требует права `USER_ADMIN`)

| Метод и адрес | Назначение |
| --- | --- |
| `GET /api/admin/users` | Учётные записи с правами |
| `POST /api/admin/users` | Создать учётную запись |
| `PATCH /api/admin/users/:id` | Роль, ФИО, доступ, пароль |
| `GET /api/admin/audit` | Журнал действий (фильтры `limit`, `bomId`, `positionId`) |

Идентификаторы позиций и материалов содержат двоеточие, `#`, вертикальную черту и
кириллицу, поэтому клиент кодирует их через `encodeURIComponent` — иначе символ `#`
обрезал бы адрес.

## Структура кода

```
.
  server/                     Сервер (Fastify + TypeScript)
    src/
      domain/                 Правила: расчёт состояний, права, константы, подписи
      repositories/           Доступ к таблицам (SQL)
      services/               Операции: импорт, передача, склад, пользователи, аудит
      http/                   HTTP-слой: маршруты, проверка сессии, ответы об ошибках
      db/                     Схема и драйверы (PGlite / PostgreSQL)
      config.ts               Настройки из окружения
      index.ts                Точка входа: база, сервер, первый администратор
    test/                     Автотесты: домен и сервисы на PGlite в памяти, без сети
  web/                        Интерфейс (React + Vite)
    src/
      pages/                  Экраны (по одному файлу на экран и на панель)
      ui/                     Общие элементы: таблица, поля правки, значки, диалоги,
                              область перетаскивания файлов, окно ввода срока
      api/                    Типы ответов и функции обращений к API
      app/                    Маршрутизация, навигация, хуки загрузки и действий
      session/                Сессия: вход, выход, смена пароля
      styles/                 Токены оформления и стили
```

Правила расчёта живут только на сервере: интерфейс показывает то, что пришло, и
отправляет изменения. Поэтому состояние позиции в списке, в карточке и в отчётах
не может разойтись.

## Тесты и проверки

```bash
npm test          # автотесты: домен, права, витрины, сервисы на PGlite
npm run typecheck # строгая проверка типов сервера и интерфейса
npm run build     # сборка сервера и интерфейса
```

Тесты проверяют предметную область (расчёт состояний, статусы, ключи материалов,
права) и работу сервисов на настоящей базе: для массового ввода и возврата операции
поднимается PGlite в памяти и схема, поэтому проверяется одна транзакция на команду,
влияние на склад и то, что откат не затирает более поздние правки. Отдельно
проверяется чтение старого `.xls`: настоящий бинарный файл собирается прямо в
тесте и должен давать те же позиции, что и тот же файл в `.xlsx`. Отдельно
закреплены боевые заголовки предприятия (`Описание №2208-2211`, `Произв-тель`,
`К-во`, `Наименование 2206`, `Обозначение`, `К-ВО`) и файл с титулом перед
таблицей. Отдельно закреплены боевые заголовки предприятия (`Описание №2208-2211`, `Произв-тель`,
`К-во`, `Наименование 2206`, `Обозначение`, `К-ВО`), файл с титулом перед
таблицей, подсчёт позиций без срока поставки, равнозначность написаний единицы
измерения и запрет упоминать срок поставки в замечаниях отчёта. Отдельно
закреплено, что номер строки не редактируется, а битое значение из файла
заменяется порядковым. Всего 106 проверок; они не требуют сети и внешней базы.

## История и журнал

Изменения не перезаписывают историю:

- **Журнал действий** (`audit_log`) хранит каждое изменение с автором, временем,
  прежним и новым значением. Операции, сделанные одним нажатием (например,
  передача нескольких позиций), получают один идентификатор операции — по нему
  видно, что строки изменены вместе.
- **История позиции** (`position_history`) показывает изменения конкретной строки.
- **Архив передач** хранит, кто и когда передал материал, из какого экрана и с
  каким комментарием, а также причину возврата в работу.

Записи не удаляются вместе со спецификацией: удаление помечает позиции как
удалённые, поэтому журнал и архив остаются читаемыми.

## Ограничения

- Отборка и передача рассчитаны на ручную работу кладовщика: система объясняет,
  почему строку нельзя передать, но не подбирает замену материала.
- Ожидаемая дата поставки не приходит от поставщиков автоматически: её вносит
  снабженец.
- Спецификации импортируются файлом; интеграции с внешними системами
  проектирования и ERP нет.
