# BOM CONTROL SYSTEM V12 — Анализ логики «дефицит → Сводка / без дефицита → Отборка»

## Целевая логика (по требованию)

При сканировании BOM-файлов:

1. Для каждой позиции проверяется разница между **Требуется** (`required`) и **Зарезервировано** (`reserved`).
2. `required > reserved` → возникает дефицит → **позиция попадает в «Сводку дефицитов»** (`DEFICIT_SUMMARY`).
3. `deficit <= 0` (`required <= reserved`) → позиции присваивается статус «на складе», она **не попадает** в Сводку дефицитов, но **попадает в лист «Отборка»** (`PICKING`) и ждёт, пока кладовщик отметит галочку «получено» → `v12MarkReceivedByProduction(positionId, PICKING)`.

## Фактическое поведение (текущий код)

Обе проекции строятся из `POSITION_STATE` и **не фильтруют по дефициту**:

### `v12RefreshDeficitSummary()` — `v12_projections.js`
Исключает только:
- `LIFECYCLE_STATE` = `ARCHIVED` или `REMOVED`
- `RECEIVED_BY_PRODUCTION === true`

Условия `deficit > 0` **нет**. Поэтому активная не-полученная позиция с `DEFICIT_QTY = 0` попадает в Сводку.

### `v12RefreshPicking()` — `v12_projections.js`
Исключает только:
- `LIFECYCLE_STATE !== ACTIVE`
- `RECEIVED_BY_PRODUCTION === true`

Фильтра по дефициту **нет**. Поэтому позиции с дефицитом > 0 тоже попадают в Отборку.

**Следствие:** позиции с дефицитом > 0 присутствуют **одновременно** и в Сводке, и в Отборке. Именно отсутствие отсечения по дефициту — корень попадания дефицит-0 позиций в Сводку.

## Архитектурные конфликты

### Конфликт 1 — Пересечение (дефицит > 0 в обоих листах)
Обе проекции включают дефицит > 0. По целевой модели они должны быть разъединены: `дефицит > 0 → только Сводка`; `дефицит <= 0 → только Отборка`.

### Конфликт 2 — Несовпадение предикатов: `дефицит` vs `availableForProduction` / `readyForHandoff`
Маршрутизация по `дефицит = required − reserved` конфликтует с готовностью к передаче:
- `availableForProduction = reserved + realDelivery` (`v12_calculate.js`)
- `readyForHandoff = valid && !received && availableForProduction >= required && required > 0`

**Пример:** `required=10, reserved=3, realDelivery=7` → `дефицит=7` (по правилу → Сводка), но `available=10 >= required` → фактически готова к передаче (должна быть в Отборке). По правилу «дефицит>0 → Сводка» она не попадёт в Отборку, хотя её можно отобрать.

**Обратный случай:** `дефицит <= 0` (reserved ≥ required), но позиция невалидна по ТЗ №8 (нет Модели/Ед.изм) или есть физическое несоответствие `reserved > warehouse` (ТЗ №30) → попадёт в Отборку, но `v12MarkReceivedByProduction` вернёт `blocked`.

### Конфликт 3 — Нет буквального статуса «на складе»
В коде нет значения статуса «на складе». Ближайшие соответствия:
- `supplyState = RESERVED` (reserved ≥ required) — потребность покрыта резервом;
- `productionState = READY_FOR_HANDOFF` (valid && !received && available >= required && required > 0) — готово к передаче.

Статус «на складе» нужно явно сопоставить одному из них. Неопределённость влияет на колонку `PRODUCTION_STATE` в Отборке и на будущие ветвления по «на складе».

### Конфликт 4 — Отборка содержит неотбираемые строки
Раз Отборка не фильтруется по готовности, в неё попадают строки с `VALIDATION_STATUS=ERROR` или `available < required`. Их чекбокс → `v12MarkReceivedByProduction` → алерт «Не удалось передать». Шум и плохой UX.

### Конфликт 5 — Сводка дефицитов — редакционный лист снабжения
`v12HandleDeficitEdit` разрешает править `ORDERED_QTY`, `EXPECTED_DATE`, `REAL_DELIVERY`, `RECEIVED`. Если ограничить Сводку только дефицит > 0, то при дефицит <= 0 строка исчезает, и снабженец не сможет вести заказ/дату/поставку с этого листа.

Важно: по ТЗ `дефицит = required − reserved` — заказ/поставка **не уменьшают** дефицит. Дефицит-0 строки возникают только когда источник полностью резервирует потребность. Но если позиция станет дефицит-0 после изменения источника, её поставка «выпадет» из Сводки.

### Конфликт 6 — Передача не проверяет физический склад
`v12MarkReceivedByProduction` проверяет `available >= required` (`available = reserved + realDelivery`), затем уменьшает склад `v12AdjustWarehouseQty(materialKey, -required)` через `Math.max(0, current + delta)`. Реальный `warehouseQty >= required` **не проверяется**. Если `reserved > warehouse` (несоответствие ТЗ №30), передача всё равно происходит, склад уходит в 0 — теряется физическая картина.

## Решения

### S1 — Немедленное (чинит заявленную проблему): Сводка только с дефицитом > 0
В `v12RefreshDeficitSummary` после проверки «передано производству»:
```js
if (toNumber(r[P.DEFICIT_QTY - 1]) <= 0) {
  continue;   // нет дефицита — в сводку не берём
}
```

### S2 — Маршрутизация Отборки (выбрать один вариант)
- **Вариант A (строгий разрыв, по целевой логике):** в `v12RefreshPicking` добавить `if (toNumber(r[P.DEFICIT_QTY - 1]) > 0) continue;`. Просто, но остаётся Конфликт 2.
- **Вариант B (по готовности — рекомендуется):** Отборка = `required > 0 && readyForHandoff === true` (т.е. `valid && !received && available >= required`). Тогда Отборка = реально отбираемые позиции, независимо от дефицита. Допускается перекрытие со Сводкой (разные цели).
- **Вариант C (строгий разрыв + гарантия отбираемости):** Отборка = `deficit <= 0 && readyForHandoff`. Полностью покрытые И готовые. Минус: частично поставленные, но готовые позиции (`deficit>0, available>=required`) в Отборку не попадут.

### S3 — Маппинг «на складе»
Сопоставить `productionState = READY_FOR_HANDOFF` (релевантно отборке) или `supplyState = RESERVED`. Рекомендуется не вводить новый статус, а использовать `readyForHandoff`/`availableForProduction` как критерий попадания в Отборку.

### S4 — Только отбираемые строки
Добавить в Отборку фильтр `readyForHandoff` (или `valid && available >= required && required > 0`) в дополнение к `дефицит <= 0`, чтобы каждая строка была фактически отбираемой. Защита `v12MarkReceivedByProduction` остаётся.

### S5 — Сводка как лист закупки
Оставить Сводку редакционным листом для `дефицит > 0`. Для управления поставкой дефицит-0 позиций добавить колонки заказа/поставки в Отборку либо управлять через `MATERIAL_STATE`. Минорный компромисс.

### S6 — Валидация склада при передаче (упрочнение)
В `v12MarkReceivedByProduction` перед архивацией проверить `v12GetWarehouseQty(materialKey) >= required`; при недостатке — `{status: "blocked"}`. Это не даст «обнулить» склад при несоответствии. Проверка ТЗ №30 уже флагует `reserved > warehouse`.

## Вывод

- **Непосредственная причина** попадания дефицит-0 в Сводку — отсутствие фильтра `deficit > 0` в `v12RefreshDeficitSummary`.
- **Главный архитектурный конфликт** — разрыв «по дефициту» не совпадает с готовностью к отборке («по availableForProduction»), плюс нет статуса «на складе» и нет валидации физического склада при передаче.
- **Рекомендуемое решение:** S1 (Сводка = дефицит>0) + Вариант B для Отборки (по готовности) + S6 (валидация склада).
