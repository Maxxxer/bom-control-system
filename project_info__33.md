# BOM CONTROL SYSTEM V12 — Повторный аудит: быстродействие, конфликты, бизнес-логика

> Отчёт №33. Повторный независимый аудит ПОСЛЕ отката регрессии P7 (гварды чекбоксов Сводки/ОТБОРКИ убраны; гвард `v12ApplyDashboardColors` оставлен).
> Метод: сплошное чтение всех 19 production-файлов + конфиг/манифест + 2 локальных теста; анализ путей исполнения, стоимости I/O, гонок блокировок и бизнес-правил.
> Вывод в одном предложении: **откат P7 корректен и подтверждён; остаются реальные (но не блокирующие) узкие места по I/O на интерактивном пути, несколько гонок вокруг часового полного синка и одна бизнес-лакуна — недостижимый статус Dashboard «Ожидание поставки (опаздывает)».**

## 0. Что подтверждено по последнему изменению (откат P7)

- `v12InstallDeficitCheckboxes` (Сводка, «Реальная поставка») и `v12InstallPickingCheckboxes` (ОТБОРКА, «Отметка получено») теперь **безусловно** делают `clearDataValidations()` + `setDataValidation(requireCheckbox())` — см. `v12_projections.js`.
- Гвард в `v12ApplyDashboardColors` оставлен: он сравнивает `_v12ProjectionUiState.dashboardColorRows === lastRow`. Это **безопасно**, т.к. `clearRange` (и `clearBody`) сбрасывают только `clearContent()` и `clearDataValidations()`, но **не** условное форматирование. Правка корректна.
- Локальные тесты зелёные (39/0 и 73/0), синтаксис OK.
- **Важное уточнение по природе бага:** дело не только в гварде. Корневая причина — `sheet_service.js :: clearRange` вызывает `range.clearDataValidations()`, а `v12ClearBody` применяется во **всех** проекциях. То есть любое условное «не пересоздавать валидации» после `clearBody` гарантированно ломает чекбоксы. Это системный риск (см. §2, C-2).

## 1. Быстродействие (Performance)

### P-1 🔴 `v12BuildRevisionDateMap()` вызывается дважды за один полный пересчёт
`v12RefreshProjections()` (`v12_projections.js`) читает `POSITION_STATE` **один раз** (ускорение P1 из отчёта №31), но:
- `v12RefreshPicking` → `v12BuildRevisionDateMap()` → полное чтение `BOM_REVISION`;
- `v12RefreshDashboard` → `v12BuildRevisionDateMap()` → **повторное** полное чтение `BOM_REVISION`.

Аналогично `v12BuildExcludedMap()` читает `EXCLUDED_BOMS` внутри `v12RefreshDashboard`.
**Рекомендация:** строить `revDates` и `excluded` **один раз** в `v12RefreshProjections` и передавать параметром (как уже сделано с `posData`). Экономия — 1 полное чтение листа на каждый пересчёт; `BOM_REVISION` растёт с каждой ревизией, так что выигрыш со временем увеличивается.

### P-2 🔴 Интерактивный путь (одна правка `onEdit`) читает `POSITION_STATE` 4–5 раз
Путь «Заказано/Ожидаемая дата» (`v12_trigger.js :: v12HandleDeficitEdit` → `v12_operations.js :: v12SetOrderedQty`/`v12SetExpectedDate`):
1. `v12BuildPositionIndex()` — чтение #1 (полное);
2. `v12UpdatePosition` — запись;
3. `v12RefreshDeficitSummaryRow` → `v12HarvestDeficitInput` строит индекс — чтение #2 + чтение листа Сводки; затем внутри `v12ReadSheet("POSITION_STATE")` — чтение #3;
4. `v12RefreshSupply()` — чтение #4 (полное), полная перезапись СНАБЖЕНИЯ;
5. `v12RefreshDashboard()` — чтение #5 (полное) + `EXCLUDED_BOMS` + `BOM_REVISION`, полная перезапись Dashboard.

Путь «Реальная поставка» (`v12HandleDeficitEdit`, кол. 12): `v12GetDeficitRequiredQty(positionId)` строит индекс (#1), `v12SetRealDeliveryQty` строит индекс (#2), затем `v12RefreshProjections()` → harvest строит индекс (#3) + `v12ReadSheet("POSITION_STATE")` (#4).

**Рекомендация:** в `v12HandleDeficitEdit` строить индекс один раз и прокидывать вниз (`v12SetOrderedQty/...`, `v12GetDeficitRequiredQty`, `v12UpdatePosition`); для `v12RefreshSupply`/`v12RefreshDashboard` передавать уже прочитанный `posData`. Это самое дешёвое крупное ускорение интерактивного пути.

### P-3 🔴 Пакетная передача (ОТБОРКА, диапазон) — O(N) полных чтений листов
`v12_trigger.js :: v12HandlePickingRangeEdit` перебирает N отмеченных строк и для каждой вызывает `v12MarkReceivedByProduction(..., skipRefresh=true)`. Внутри `v12_handoff.js :: v12MarkReceivedByProduction`:
- `v12BuildPositionIndex()` — полное чтение `POSITION_STATE` **на каждую строку**;
- `v12AdjustWarehouseQty()` → `v12BuildMaterialIndex()` — полное чтение `MATERIAL_STATE` **на каждую строку**.

Итого ~2·N полных чтений на одну операцию массовой передачи. На больших BOM это прямой риск лимита исполнения (6 мин) и 30-сек окна срабатывания триггера.
**Рекомендация:** передавать в `v12MarkReceivedByProduction` общий `index` (и кэш Material-индекса) при пакетной обработке; строить оба индекса один раз в начале range-обработчика.

### P-4 🟠 `v12GetPositionsByBom(bomId, index)` — линейный проход по всему индексу на каждый BOM
`v12_position_state.js`: перебирает **всю** карту позиций и фильтрует по `BOM_ID`. В `v12RunFullSync` → `v12SyncBOM` → `v12GetPositionsByBom` это **O(BOMs × positions)**. Индекс не перечитывается (цель P6 достигнута), но скан остаётся.
**Рекомендация:** заранее сгруппировать позиции по `BOM_ID` (`Map<bomId, Map<pid, m>>`) и в `v12SyncBOM` брать готовую ветку.

### P-5 🟠 Одиночные `setValues` при применении ревизии
`v12_change_engine.js :: v12ApplySourceRevision` вызывает `v12UpdatePosition` **по одной позиции**, а тот делает `batchWrite` (отдельный `Range.setValues` на каждый непрерывный отрезок строки). При большом diff — это сотни вызовов Sheets API.
**Рекомендация:** агрегировать изменения по строкам в один `batchWrite` на весь ChangeSet (для изменённых строк).

### P-6 🟠 `v12HandleDeficitRangeEdit` читает Position ID по одной ячейке
`v12_trigger.js`: `sheet.getRange(sheetRow, D.POSITION_ID).getValue()` в цикле по N строкам — N одиночных чтений. Дешевле прочитать колонку Position ID одним `getValues()`.

### P-7 🟡 Harvest подрывает обещанное «одно чтение POSITION_STATE»
`v12RefreshProjections()` сначала вызывает `v12HarvestDeficitInput()` и `v12HarvestPickingInput()`, и **каждый из них строит свой индекс `POSITION_STATE`** (плюс `v12HarvestPickingInput` может вызывать `v12MarkReceivedByProduction`, который снова строит индекс на каждую отмеченную строку ОТБОРКИ). Затем проекции читают `POSITION_STATE` ещё раз. «Одно чтение» из отчёта №31 относится только к самим проекциям, а не к полному пути пересчёта.
**Не баг**, но важно для честной оценки стоимости пересчёта.

### P-8 🟡 Множественные `SpreadsheetApp.flush()`
Flush вызывается в операциях, в обоих range-обработчиках, в harvest. Каждый flush форсирует пересчёт — это дорого. Flush нужен для корректности «чтение после записи» при быстром вводе (см. §2, C-3), но число вызовов на одну правку можно сократить (один flush перед «опасным» чтением).

### P-9 🟡 Гвард `v12ApplyDashboardColors` в реальности почти всегда не срабатывает
`_v12ProjectionUiState` — модуль-глобал. В Google Apps Script **глобальные переменные не переживают отдельные запуски** (каждый триггер/меню — новый контекст). Значит `_v12ProjectionUiState` всегда пуст на старте, и гвард помогает лишь при повторном вызове `v12ApplyDashboardColors()` в рамках **одного** исполнения (что редко). Это не ошибка (гвард безопасен и дёшев), но его польза переоценена — ровно та же механика ранее и создала регрессию P7 при повторном вызове проекции в одном запуске.

## 2. Конфликты и гонки (Conflicts)

### C-1 🔴 `clearRange` уничтожает ВСЕ data-validation тела листа
`sheet_service.js :: clearRange` → `range.clearDataValidations()`. `clearBody`/`v12ClearBody` вызывается во **всех** проекциях. После пересчёта восстанавливаются только: чекбокс-колонка проекции (Сводка/ОТБОРКА/WORKING BOM/Dashboard) и выпадающий фильтр B1 ОТБОРКИ. Любая **другая** валидация (например, вручную добавленный раскрывающийся список или уже настроенное правило в пользовательской колонке) будет молча стёрта при каждом пересчёте.
**Рекомендация:** либо убрать `clearDataValidations()` из `clearRange` (оставить только `clearContent()`), либо ввести явный список «валидаций, поддерживаемых системой» и восстанавливать их централизованно.

### C-2 🔴 Часовая полная синхронизация vs пользовательские правки (тайм-аут блокировки)
`lock.js :: acquireScriptLock` использует `waitLock(V12_CONFIG.SETTINGS.LOCK_TIMEOUT = 30000)`. `v12ScheduledUpdate` (каждый час) держит ScriptLock на **всё** время `v12RunFullSync` (чтение Drive + синк + `v12RecalculateWarehouseConsistency` + полный пересчёт 5 проекций). Если полный синк длится дольше 30 с (вероятно на больших листах из-за полных перезаписей проекций), параллельная правка не получит блокировку → `waitLock` бросает исключение → `v12OnEdit` ловит и логирует, **правка не применяется** (остаётся только сырое значение ячейки; частично спасёт harvest, но не гарантированно).
**Рекомендация:** в onEdit использовать `tryLock`/короткий тайм-аут + понятное уведомление пользователю; полный синк — по возможности вне пиковых окон; уменьшить длительность синка (см. §1).

### C-3 🟠 Реентрантность лока построена на модуль-глобалах — корректна, но хрупка
`lock.js`: `_lockDepth`/`_heldLock` в глобальной области. Внутри одного исполнения вложенный `acquireScriptLock` (например, `v12OnEdit` → `v12MarkReceivedByProduction`) корректно инкрементирует счётчик и не берёт лок повторно. Release всегда в `finally`. Работает, но подразумевает, что все вложенные вызовы происходят в одном исполнении — при добавлении новых асинхронных путей это легко нарушить.

### C-4 🟠 `v12RevertEdit` не умеет откатывать диапазон
`v12_trigger.js :: v12RevertEdit` откатывает только если `e.oldValue !== undefined`. Для диапазонных событий `oldValue` нет → откат — no-op (молча). Сейчас диапазоны обрабатываются только в Сводке/ОТБОРКЕ (где откат не вызывается), но как только диапазонный откат понадобится (например, защита read-only колонок ОТБОРКИ), он не сработает.

### C-5 🟠 Несогласованный источник значения правки
`v12HandleDeficitEdit` намеренно берёт **снимок** `e.value` (защита от «живого» чтения уже откатанной ячейки), а `v12HandlePickingEdit` берёт **живое** `e.range.getValue()`. Для ОТБОРКИ это менее критично (чекбокс), но расхождение подходов — потенциальная ловушка при быстром вводе.

### C-6 🟠 Ручное изменение склада «расводит» контрольные колонки MATERIAL_STATE
`v12HandleMaterialStateEdit` при правке `WAREHOUSE_QTY` пересчитывает проекции, но **не** вызывает `v12RecalculateWarehouseConsistency()`. Колонки `MATERIAL_STATE.RESERVED_QTY`/`FREE_QTY` остаются устаревшими до ближайшего полного синка. Проекции их не читают (используют POSITION_STATE), поэтому влияние низкое, но «контроль резерва ≤ склада (ТЗ №30)» между синками фактически не действует.

### C-7 🟠 Диапазонная правка Сводки вызывает полный пересчёт даже при отсутствии изменений
`v12HandleDeficitRangeEdit` в конце **безусловно** вызывает `v12RefreshProjections()`, даже если ничего не изменилось (например, вставка в read-only колонку/превышение прав). Лишняя тяжёлая работа на каждый диапазонный ввод.

### C-8 🟡 Дубликат-защита от повторного применения «реальной поставки»
Потенциального двойного начисления склада **нет**: harvest (`v12HarvestDeficitInput`) начисляет склад только если `currentReal < required`, а `v12SetRealDeliveryQty` уже поднял `REAL_DELIVERY_QTY` до `required` — повторного дельта-эффекта не возникает. Механизм согласован (это стоит держать в голове при будущей переработке harvest).

## 3. Бизнес-логика (Business logic)

### B-1 🔴 Статус Dashboard «Ожидание поставки (опаздывает)» недостижим
`v12_projections.js :: v12AggregateBomStates` инициализирует `late: 0`, но **нигде его не инкрементирует** (в switch по `supplyState` заполняются только `notOrdered`, `partial`, `onTime`). При этом `v12ComputeBomStatus` содержит ветку `if (agg.late > 0) return BS.WAITING_LATE;` — она **мертва**. Крайний срок (`minDeadline`) считается, но для определения «опаздывает» не используется.
**Итог:** BOM-статус «Ожидание поставки (опаздывает)» никогда не появляется в Dashboard (и его цвет в `BOM_STATUS_COLOR` не используется). Бизнес-следствие: снабжение не видит «просроченные» BOM отдельным статусом.
**Рекомендация:** вычислять `late` при `supply ∈ {ORDERED, PARTIALLY_DELIVERED}` и `expectedDate > deadline` (или `deadline < now` и не собрано).

### B-2 🟠 Чекбокс ОТБОРКИ срабатывает только в одну сторону (необратимая передача из UI)
`v12HandlePickingEdit`: действие выполняется **только** при `v12IsChecked(checked)`. Снятие галочки ничего не делает. При этом успешная передача **архивирует** позицию и вычитает склад на `required`. Итог: случайная/ошибочная отметка в ОТБОРКЕ необратима из листа (нужно меню «↩ Вернуть из архива», которое к тому же проверяет право `PICKING_CHECKBOX`). Это осознанная, но опасная механика для быстрого массового ввода.

### B-3 🟠 Валидация по ТЗ №8 (обязателен Срок) может навсегда блокировать передачу
`v12_utils.js :: v12ValidatePosition` считает позицию невалидной без `DEADLINE` (и без Модели/Ед.изм/Наименования/Строки/Требуется>0). `v12MarkReceivedByProduction` блокирует передачу невалидной позиции, а `productionState` для невалидной = `PARTIALLY_AVAILABLE` (не READY). Значит позиция с пришедшим материалом, но пустым «Крайний срок», не может быть передана производству — пока кто-то не проставит срок. Для «реальной поставки» гейт по заказу снят осознанно, но гейт по валидности остаётся.

### B-4 🟠 Остаток склада при передаче уменьшается на `required` независимо от источника покрытия
`v12MarkReceivedByProduction` → `v12AdjustWarehouseQty(materialKey, -required)`. Если покрытие шло из `reservedQty` (резерв BOM), физический склад всё равно уменьшается (с клампом `Math.max(0, …)`). При неполном фактическом остатке это занижает склад или обнуляет его. Логика согласуется с моделью «резерв = складское удержание», но граничные случаи (резерв без физического прихода) дают расхождение с реальным складом.

### B-5 🟠 Чекбокс Сводки «Реальная поставка» = только ПОЛНАЯ поставка
`v12HandleDeficitEdit` при отметке вызывает `v12SetRealDeliveryQty(positionId, v12GetDeficitRequiredQty(positionId))` — то есть фиксирует полную потребность, а не фактически принятое количество. Частичные поставки через Сводку невозможны (только программно через `v12SetRealDeliveryQty`). Это упрощение заложено в UI.

### B-6 🟡 Harvest реальной поставки работает только «вверх»
`v12HarvestDeficitInput` фиксирует поставку, только если чекбокс в листе отмечен и `currentReal < required`. Он **никогда не понижает** уже сохранённую поставку. Следствие: если пользователь снял галочку, но `onEdit` был пропущен/задержан, поставка в POSITION_STATE останется. Явное снятие возможно только через `v12SetRealDeliveryQty(...,0)` (одиночный путь). Осознанный компромисс, но стоит знать.

### B-7 🟡 «Мёртвые» листы: EVENT_LOG и MATERIAL_HISTORY не пишутся
Проверено по всем 19 файлам: нет ни одной записи (`appendRow`/`writeValues`) в `EVENT_LOG` и `MATERIAL_HISTORY`.
- `MATERIAL_HISTORY` только **читается** (`v12_handoff.js :: v12GetPositionHistory`) → в ARCHIVE колонка «История» **всегда пуста** (`[]`).
- `EVENT_LOG` не читается и не пишется вообще; константы `EVENTS`/`EVENT_COLUMNS` фактически не используются в потоках.
Это «листы-призраки» (отмечено ещё в отчёте №30) — их либо надо наполнять, либо убрать.

### B-8 🟡 `v12GetWarehouseQty` — мёртвая функция
`v12_material_state.js :: v12GetWarehouseQty(materialKey, index)` больше нигде не вызывается (операции используют `v12AdjustWarehouseQty`, контроль — `v12RecalculateWarehouseConsistency`). Кандидат на удаление (подтверждено сплошным чтением — вызовов нет).

### B-9 🟡 `v12ConsistencyCheck` даёт ложные «ошибки» для пустых BOM
`v12_controller.js`: BOM из реестра без позиций помечается как ошибка («BOM есть в BOM_REGISTRY, но нет позиций»). Это нормально для только что заведённого BOM или BOM без распарсенных материалов → ложные срабатывания.

### B-10 🟡 СНАБЖЕНИЕ/Dashboard обновляются «по половине пары»
В `v12SetOrderedQty` агрегаты (`v12RefreshSupply`+`v12RefreshDashboard`) пересчитываются только если уже задана `EXPECTED_DATE`; в `v12SetExpectedDate` — только если уже задан `ORDERED_QTY`. Значит при вводе одного из двух полей агрегаты остаются устаревшими до второго. Историческое поведение; при желании — пересчитывать всегда.

### B-11 🟡 RBAC «из коробки» выключен
`v12_roles.js :: v12GetCurrentUserRole` при пустом `V12_ROLE_MAP` возвращает всем `ADMIN`. То есть до заполнения карты ролей ограничений нет (защищает только `webapp.access = MYSELF`). Плюс: как только карта заполнена, пользователь **не** из карты получает роль `""` → `v12RequireRole` бросает на любом действии. Заполняйте карту полностью, иначе часть пользователей потеряет доступ.

### B-12 🟡 `toNumber` разбирает не идеально
`utils.js`: заменяет только **первую** запятую на точку и берёт первое числовое совпадение. «1 234,56» → 1234.56 (ок), но «1,234.56» (англ. формат) → 1.234. Для локали РФ обычно ок, но стоит знать при импорте внешних данных.

## 4. Приоритизированный список действий

**Критично (влияет на ключевые сценарии / стабильность):**
1. B-1 — реализовать `late` и статус Dashboard «Ожидание поставки (опаздывает)».
2. C-2 — снизить окно удержания блокировки часовым синком (tryLock + уведомление; сократить длительность синка).
3. P-2 / P-3 — убрать повторные полные чтения `POSITION_STATE`/`MATERIAL_STATE` на интерактивном и пакетном путях (передавать общие индексы).

## 5. Что НЕ проверяется локальными тестами (слепые зоны)
`_local_tests/*` — это Node-скрипты с моками `SpreadsheetApp`, в которых `clearDataValidations()` и `setDataValidation()` — **пустышки** (`return this`). Поэтому:
- тесты проверяют **значения** ячеек, но **не** наличие чекбокс-валидаций → именно поэтому регрессия P7 не была поймана;
- тесты не моделируют ограничения блокировок, тайм-ауты `waitLock`, сброс глобалов между запусками и лимиты исполнения;
- тесты не покрывают Dashboard-статусы (`v12ComputeBomStatus`/`late`), поэтому B-1 незамечен.
**Рекомендация:** добавить в моки учёт `setDataValidation`/`clearDataValidations` (счётчики вызовов) и хотя бы один тест «пересчёт дважды при неизменном числе строк → валидации восстановлены».
