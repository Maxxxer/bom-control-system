# BOM CONTROL SYSTEM V12 — Подсистема «ОТБОРКА»: архитектура, анализ конфликтов одновременной работы и стратегия независимых файлов отборщиков

> Документ отвечает на два вопроса: **(1)** какие конфликты возникают, когда несколько отборщиков работают одновременно, и **(2)** как внедрить стратегию «отдельный spreadsheet на каждого отборщика» так, чтобы эти конфликты были решены, а не перенесены.
>
> Всё ниже — про **существующий код** (V12, «модель Применить»), с точными именами функций, листов и колонок.

---

## 0. Резюме (TL;DR)

- Система — это **Google Apps Script, привязанный к ОДНОЙ Google-таблице** (`container-bound`; `.clasp.json` → `scriptId 1PluBzC6...`). Все проекции (ОТБОРКА, Сводка дефицитов, WORKING BOM, СНАБЖЕНИЕ, Dashboard) — **листы внутри этой одной таблицы**.
- Правки пользователей **не применяются сразу**. `onEdit` только пишет «намерение» в служебный лист `PENDING_EDITS`. Расчёт и пересборка всех проекций происходят **только** по нажатию «ПРИМЕНИТЬ» (`v12ApplyChanges` → `v12DrainPendingEdits` → `v12RefreshProjections`).
- `v12RefreshPicking()` **полностью очищает тело листа ОТБОРКА** (`v12ClearBody`) и перерисовывает его из `POSITION_STATE`, всегда проставляя чекбокс в `false`. Поэтому любая пересборка проекции **стирает все неприменённые галочки у всех отборщиков сразу**.
- Фильтр проекта на листе ОТБОРКА — **одна общая ячейка B1** на всю таблицу. Два отборщика физически не могут работать с разными фильтрами одновременно.
- Очередь `PENDING_EDITS` — **общая**. Кнопка «ПРИМЕНИТЬ», нажатая любым пользователем, сливает **ВСЕ** PENDING-намерения, включая чужие незавершённые.
- Единственный механизм сериализации — `LockService.getScriptLock()` (один лок на весь проект). Он **не даёт очереди** для ожидающих: при занятом локе `v12EnqueuePendingRows` делает 2 попытки (10 с → пауза 300 мс → 5 с) и, если не взял, **молча теряет намерение** (только `WARNING` в `SYSTEM_LOG`; пользователь ничего не видит — `v12Toast` из триггера не работает).
- Сателлитные файлы **не могут напрямую вызывать функции мастер-скрипта** и **не получат `onEdit`-события** от правок в мастер-файле. Нужен явный транспорт: **веб-приложение (`doPost`)** — основной вариант, **лист-«инбокс» + триггер** — резервный.
- Ключевая идея безопасного внедрения: сателлит **никогда не перезаписывает колонку галочек у себя** (обновляет только колонки 1…12), а применение идёт **по номеру партии (BATCH_ID)**, а не «по всему, что накопилось».

## 4. Ключевые абстракции

### `V12_CONFIG` (`v12_config.js`)
- **Ответственность**: единственное место, где описаны имена листов, номера колонок, заголовки, статусы, цвета, роли, настройки.
- **Критичное для отборки**:
  - `SHEETS.PICKING = "ОТБОРКА"`, `COLUMN_COUNT.PICKING = 13`.
  - `PICKING_COLUMNS`: `POSITION_ID 1, BOM_NAME 2, BOM_ROW 3, MATERIAL_CODE 4, MANUFACTURER 5, MATERIAL_NAME 6, MODEL 7, UNIT 8, REQUIRED_QTY 9, AVAILABLE_FOR_PRODUCTION 10, PRODUCTION_STATE 11, EXPECTED_DATE 12, CHECKBOX 13`.
  - `PICKING_FILTER = { CELL_ROW: 1, CELL_COL: 2, ALL: "(Все проекты)" }` — фильтр живёт **в ячейке B1**.
  - `PENDING_EDIT_COLUMNS` (10): `DATE 1, EDIT_ID 2, SOURCE 3, POSITION_ID 4, FIELD 5, VALUE 6, USER 7, STATUS 8, PROCESSED_AT 9, ERROR 10`.
  - `PENDING_FIELD.HANDOFF = "HANDOFF"` — именно это поле пишет отборщик из ОТБОРКИ.
  - `SETTINGS.LOCK_TIMEOUT = 30000`.
- **Замечание**: комментарии в конфиге местами рассинхронизированы с кодом (описывают ОТБОРКУ как «12 колонок», `CHECKBOX` = 13). Верить массивам `*_COLUMNS`, а не комментариям.

### `POSITION_STATE` — центральное состояние
- **Файл**: `v12_position_state.js`, `v12_config.js:POSITION_COLUMNS`
- **Ответственность**: одна строка = одна позиция BOM. Хранит сырые поля (кол-во, резерв, заказ, реальная поставка, даты, флаги передачи) и **производные** (supplyState, productionState, дефицит, доступно для производства).
- **Производные считает** `v12ApplyComputedToRow(row)` → `v12CalculatePositionState(input)` (чистая функция).
- **Ключевой инвариант (К1)**: `availableForProduction = reservedQty + realDeliveryQty` — **склад в этом расчёте не участвует**. `MATERIAL_STATE` — «контрольный» лист, система не резервирует из склада автоматически (ТЗ №204/211).

### `v12MarkReceivedByProduction(positionId, sourceUI, skipRefresh, ctx)` — передача производству
- **Файл**: `v12_handoff.js`
- **Ответственность**: идемпотентно зафиксировать передачу позиции в производство.
- **Что проверяет перед записью**:
  - `v12RequireRole(role, "PICKING_CHECKBOX" | "WORKING_BOM_CHECKBOX")` — RBAC;
  - позиция существует; `validation === VALID`;
  - `availableForProduction >= requiredQty` — **иначе `{status:"blocked", reason:"Не хватает доступного количества..."}`**;
  - идемпотентность: если уже передано полностью → `{status:"already"}`.
- **Что делает**: пишет `RECEIVED_BY_PRODUCTION/QTY/AT/USER`, архивирует (строка в `ARCHIVE`), ставит `LIFECYCLE_STATE = ARCHIVED`, пересчитывает производные, **вычитает `requiredQty` из складского остатка** (`warehouseDelta = -required`), пишет аудит/историю/событие.
- **Пакетный режим**: при переданном `ctx` записи копятся в `ctx.positionWrites`, дельты — в `ctx.warehouseDelta`, проекции пересобираются один раз в конце.

### `PENDING_EDITS` — очередь намерений
- **Файл**: `v12_queue.js`
- **Ответственность**: быть авторитетным источником правок. `onEdit` только пишет строку намерения; применение — по кнопке.
- **Ключ намерения**: `SOURCE | POSITION_ID | FIELD` (`v12PendingKey`). Upsert: одна PENDING-строка на ключ.
- **Правило интерпретации `VALUE`** (`v12NormalizePendingValue`): для `HANDOFF`/`REAL_DELIVERY`/`DASHBOARD_DONE` — boolean; для `ORDERED_QTY` — число ≥ 0; для `EXPECTED_DATE` — `Date` либо `""`.
- **last-wins**: побеждает последняя строка по ключу; для чекбокс-полей `VALUE=false` означает **отмену** намерения.
- **Реконсиляция** (`v12RebuildPendingFromChecked`): приводить очередь к виду «что реально отмечено галочками», добирая потерянные `onEdit`. **Читает физические галочки в мастер-листах ОТБОРКА / WORKING BOM / Сводка / Dashboard.**

### `v12DrainPendingEdits()` / `v12ApplyChanges()` — применение
- **Файл**: `v12_queue.js`
- **Ответственность**: пакетно применить **все** PENDING-намерения.
- **Порядок**:
  1. Предфильтр `v12HasPendingEdits() || v12HasCheckedHandoffs()`;
  2. `acquireScriptLock({ tryOnly: true, timeoutMs: 5000 })` — если лок занят, вернуть `{drained:0, skipped:true}`;
  3. `v12RebuildPendingFromChecked()` — привести очередь к каноническому виду;
  4. собрать `intents` (`v12ResolvePendingIntents`) и `pendingRows`;
  5. один `posIndex`, один `materialIndex`, один `historyIndex`, один `operationId` на всю пачку;
  6. по каждому намерению — `v12WithActor(it.user, () => v12ApplyPendingIntent(it, ctx, posIndex))`;
  7. применить складские дельты, записать POSITION_STATE (`v12WritePositionBatch`), слить буферы ARCHIVE / MATERIAL_HISTORY / EVENT_LOG;
  8. **ОДИН** `v12RefreshProjections()`;
  9. пометить строки DONE/FAILED, почистить старые, сбросить индикатор.

### `v12RefreshPicking(posData, revDates)` — проекция ОТБОРКИ
- **Файл**: `v12_projections.js`
- **Ответственность**: собрать лист ОТБОРКИ из `POSITION_STATE`.
- **Фильтр строк**: `LIFECYCLE_STATE === ACTIVE`, ещё не передано, и (если задан) код проекта = `v12ExtractBomProjectCode(BOM_NAME)` === значение B1.
- **Сортировка**: по BOM → «На складе» (READY_FOR_HANDOFF) вверх → по `BOM_ROW`.
- **Цвет строки** (`v12PickingRowColor`): `STOCK` (голубой) / `RED` / `YELLOW` / `ORANGE` / `WHITE`.
- **КРИТИЧНО**: вызывает `v12ClearBody("PICKING")`, пишет строки, затем `v12InstallPickingCheckboxes(rows.length)` (сначала `clearDataValidations()` на всю высоту листа, затем чекбоксы на `rows.length`), `v12ApplyPickingColors`, `v12InstallPickingBomFilter(codes)`.
- **Чекбокс всегда записывается как `false`** — проекция не знает о неприменённых отметках.
- **«Дата поставки»** (`v12PickingDeliveryDate`): приоритет — дата создания BOM (если резерв BOM ≥ потребности) → `REAL_DELIVERY_DATE` (для «На складе») → `EXPECTED_DATE`.

### `acquireScriptLock(options)` (`lock.js`)
- Реентрантный: `_lockDepth` в модульной переменной; повторный вызов внутри того же исполнения не блокируется.
- `{tryOnly:true, timeoutMs:N}` → `lock.tryLock(N)` → `null` при неудаче (вызывающий сам решает).
- Без опций → `lock.waitLock(V12_CONFIG.SETTINGS.LOCK_TIMEOUT = 30000)`.
- **Один лок на весь скрипт-проект** (не на пользователя, не на лист).

## 5. Поток данных: как сегодня проходит одна отборка

1. **Кладовщик** открывает лист «ОТБОРКА», выбирает проект в B1 (или «(Все проекты)»).
2. Сортировка/фильтрация строк — **не нативный фильтр Sheets**, а пересборка листа:
   `onEdit` (B1, кол. 2, стр. 1) → `v12WithEditLock(e, () => v12RefreshPicking())` → лист пересобирается под выбранный проект.
3. Кладовщик ставит галочку в колонке 13 («Отметка получено»), возможно, сразу на диапазон.
4. `v12OnEdit` → **быстрый путь** `v12CaptureCheckboxEdit(e, "ОТБОРКА")`:
   - `action = PICKING_CHECKBOX`, `field = HANDOFF`, `sourceKey = PICKING`;
   - проверка RBAC **на этапе захвата** (роль `WAREHOUSE`/`PRODUCTION`/`ADMIN`);
   - значения берутся из события (`e.value`/`e.values`) — снимок на момент правки;
   - для каждой строки диапазона → `v12BuildPendingRow(...)` → `v12EnqueuePendingRows(pendingRows)`;
   - затем `v12ReconcilePendingHandoffs()` — **идемпотентная пересборка очереди по фактическим галочкам** (добирает то, что Google «проглотил» при массовой отметке).
5. `v12EnqueuePendingRows`: берёт лок (`tryOnly` 10 с → `sleep(300)` → `tryOnly` 5 с), читает `PENDING_EDITS`, upsert по ключу, `writeValues` для новых, `batchWrite` для обновлений, `SpreadsheetApp.flush()`, затем `v12UpdatePendingIndicator()`.
6. Кладовщик жмёт **«ПРИМЕНИТЬ»** (картинка-кнопка A1, назначен скрипт `v12ApplyChangesUI`) или меню → `v12ApplyChanges()`.
7. `v12DrainPendingEdits()` — см. §4. Каждое HANDOFF-намерение → `v12MarkReceivedByProduction(pid, "PICKING", true, ctx)`.
8. Один `v12RefreshProjections()` пересобирает **все пять** проекций. Переданные позиции уходят из ОТБОРКИ (они `ARCHIVED`), галочки уходят вместе со строками.
9. Если позиция не прошла проверку (`available < required`), строка очереди помечается `FAILED` с текстом в колонке «Ошибка»; пользователю показывается toast «Применено: N, не применено: M».

## 6. Карта мутаций: кто и что перезаписывает

Это самая важная таблица для понимания конфликтов.

| Триггер | Под локом? | Что пересобирает | Что при этом теряется |
|---|---|---|---|
| Чекбокс ОТБОРКА/WORKING BOM/Сводка/Dashboard | Да (короткий, только на запись очереди) | **ничего** | ничего (только строка очереди) |
| Смена фильтра B1 в ОТБОРКЕ | Да | **вся ОТБОРКА** (`v12RefreshPicking`) | галочки **всех** отборщиков, чужой фильтр |
| `MATERIAL_STATE` (склад, одиночная ячейка) | Да | **все проекции** (`v12RecalculateWarehouseConsistency` + `v12RefreshProjections`) | галочки всех, фильтр B1 ОТБОРКИ |
| Dashboard: «Выполнено» | Да (медленный путь) | откат правки; реально применяется очередью | — |
| POSITION_STATE: любая правка (кроме ADMIN) | — | откат (`v12RevertEdit`) | — |
| «ПРИМЕНИТЬ» | Да (tryOnly 5 с) | **все проекции** | галочки всех, фильтр B1 (переустановка списка) |
| «🔻 Полная синхронизация» / часовой триггер | Да (`waitLock` до 30 с) | POSITION_STATE (добавление/удаление/обновление) + все проекции | галочки всех; намерения по удалённым позициям → `blocked` |
| «♻ Пересобрать очередь (по галочкам)» | Да | только `PENDING_EDITS` | — |

**Вывод**: в текущей архитектуре «лист ОТБОРКА» — это **не рабочее место**, а **проекция-витрина**, которая целиком перерисовывается. Работать в ней вдвоём физически нельзя: любое чужое действие, приводящее к пересборке, уничтожает ваш незавершённый ввод.

## 7. КОНФЛИКТЫ

### 7.1. Конфликты в текущей однофайловой схеме

| № | Конфликт | Механизм в коде | Последствие |
|---|---|---|---|
| **A1** | **Общий фильтр проекта** | `V12_CONFIG.PICKING_FILTER` — одна ячейка `B1` на всю таблицу | Второй отборщик меняет фильтр первому; лист пересобирается под чужим отбором |
| **A2** | **Стирание неприменённых галочек** | `v12RefreshPicking` → `v12ClearBody("PICKING")` + `v12InstallPickingCheckboxes` (проекция всегда пишет `false`) | Отборщик A отметил 30 строк; B нажал «Применить» / сменил фильтр / поправил склад → у A всё снято |
| **A3** | **Общая очередь: «Применить» сливает чужое** | `v12DrainPendingEdits` берёт **все** PENDING-строки, без учёта автора | Отборщик B коммитит незавершённую (и, возможно, ошибочную) работу A. Снять её можно только возвратом из архива по одной позиции |
| **A4** | **Молчаливая потеря намерения при занятом локе** | `v12EnqueuePendingRows`: 2 попытки (10 с + 5 с) → `logSystem(... "Очередь занята ... намерение не зафиксировано", "WARNING")` и `return` | Галочка поставлена, но в очередь не попала; через несколько секунд проекция её сотрёт. Пользователь **не уведомлён** (`v12Toast` из триггера не работает). Спасает только реконсиляция — но она тоже требует лока |
| **A5** | **Реконсиляция тоже под локом** | `v12ReconcilePendingHandoffs` → `tryOnly 10 с` → при неудаче `"пересборка отложена"` | Окно, когда потерянные `onEdit` не добираются |
| **A6** | **Склад вне очереди** | `v12HandleMaterialStateEdit` → `v12RecalculateWarehouseConsistency()` + `v12RefreshProjections()` **немедленно** | Кладовщик, правящий `MATERIAL_STATE`, стирает галочки всех отборщиков и сбрасывает фильтр B1 |
| **A7** | **Двойная выдача одного материала** | `availableForProduction = reservedQty + realDeliveryQty` — **склад не проверяется**; `v12MarkReceivedByProduction` проверяет `available >= required` и списывает склад `warehouseDelta = -required`, но `Math.max(0, current + delta)` **прячет уход в минус** | Двое отборщиков выдают один и тот же физический материал по двум разным BOM. Оба применения проходят «успешно». Дефицит на складе остаётся незамеченным до ручной сверки |
| **A8** | **Аудит с чужим актором** | `v12RebuildPendingFromChecked` создаёт синтетические намерения с `actor = v12CurrentActor()` | Если реконсиляцию запустил не автор отметки, история запишется на него |
| **A9** | **Коллизия по одному Position ID** | Ключ очереди `SOURCE|POSITION_ID|FIELD`; дубли схлопываются в DONE с пометкой `"дубль (схлопнуто пересборкой)"` | Двое работают по одной позиции из одного источника → побеждает последний, первый молча теряет |
| **A10** | **Гонка «Применить» ↔ «Полная синхронизация»** | Обе под одним локом, но синк может удалить/пересоздать позиции | Намерения по исчезнувшим Position ID становятся `blocked` |
| **A11** | **Задержка «Применить» до 30 с** | `waitLock(30000)` в полной синхронизации держит лок весь прогон (при большом числе BOM — минуты) | Долгое окно, в котором чужие `onEdit` теряются (A4) |
| **A12** | **Часовой триггер синка конкурирует с рабочим днём** | `v12ScheduledUpdate` каждый час `v12RunFullSync()` | Раз в час — окно блокировки и полная пересборка листов |

### 7.2. Конфликты, которые останутся/появятся при переходе на сателлиты

| № | Конфликт | Почему возникает | Решение (см. §8) |
|---|---|---|---|
| **B1** | **Сателлит не может вызвать функции мастер-скрипта** | Apps Script: невозможно импортировать функцию из другого проекта напрямую | Веб-приложение (`doPost`) или лист-инбокс |
| **B2** | **В сателлите не будет `onEdit`-события, релевантного мастеру** | Триггер `onEdit` видит только свою таблицу; программные записи вообще не порождают `onEdit` | Пишем намерения **явно**, по нажатию кнопки (батч), а не через `onEdit` |
| **B3** | **Устаревание снимка** | Отборщик 20 минут отбирает по данным на момент загрузки; за это время склад/заказы изменились | Перепроверка на мастере **уже есть**: `available < required` → `blocked`. Плюс колонка «Обновлено» и авто-обновление |
| **B4** | **Двое взяли один проект** | Сателлиты не знают друг о друге | Лист `PICKING_CLAIMS` (мягкий захват проекта) |
| **B5** | **Повторная отправка одной партии** | Повторное нажатие кнопки, ретрай сети | `BATCH_ID` + проверка статуса партии; обработка идемпотентна |
| **B6** | **N пересборок всех проекций на N применений** | `v12RefreshProjections` вызывается на каждую партию | Дебаунс/сериализация: один прогон на пачку; опционально — очередь партий с отложенным применением |
| **B7** | **Отборщик не узнает результат** | `v12Toast` работает только в UI мастера | Результат партии вернуть в ответе `doPost` и/или записать в `PICKING_BATCHES` |
| **B8** | **Определение актора при вызове веб-приложения** | Web app `executeAs: USER_DEPLOYING` → `Session.getActiveUser()` может вернуть не того | Актор передаётся в payload и валидируется против `V12_ROLE_MAP`; транспорт защищён общим токеном |
| **B9** | **Рассинхрон версий/схем** | Сателлит — отдельный скрипт с копией логики | Читать заголовки из мастера и мапить колонки **по имени**, а не по индексу; проверять `V12_CONFIG.VERSION` |
| **B10** | **Права доступа к мастер-таблице** | Сателлит читает (`openById`) и/или пишет (инбокс) | Минимум — «Просмотр» на мастер; при инбокс-варианте — «Редактирование» |
| **B11** | **А7 остаётся** | Сателлиты разделяют **рабочее место**, но не **физический материал** | Нужна явная политика выдачи (см. §8.9) |

## 8. Стратегия внедрения: независимые файлы отборщиков

### 8.1. Целевая архитектура

```
┌────────────────────────────────────────────────────────────────┐
│ МАСТЕР-ТАБЛИЦА (единственный источник правды)                  │
│                                                                │
│  POSITION_STATE ──► v12RefreshProjections() ──► проекции       │
│                                                                │
│  ОТБОРКА (read-only, «витрина администратора»)                 │
│  PENDING_EDITS (+ BATCH_ID)   ◄── входящие намерения           │
│  PICKING_BATCHES              ◄── журнал партий                │
│  PICKING_CLAIMS               ◄── захват проектов              │
│                                                                │
│  doPost(e) — API приёма партий (единственный писатель)         │
│  v12ApplyBatch(batchId) — применение ТОЛЬКО своей партии        │
└────────────────────────────────────────────────────────────────┘
              ▲                              ▲
              │ POST {token, actor,          │ POST
              │  batchId, project, items}    │
              │                              │
   ┌──────────┴───────────┐      ┌───────────┴──────────┐
   │ САТЕЛЛИТ «Отборщик 1»│      │ САТЕЛЛИТ «Отборщик 2»│
   │  лист ОТБОРКА:       │      │  лист ОТБОРКА:       │
   │   B1 — СВОЙ фильтр   │      │   B1 — СВОЙ фильтр   │
   │   кол. 1..12 — pull  │      │   кол. 1..12 — pull  │
   │   кол. 13 — галочки  │      │   кол. 13 — галочки  │
   │   нативный фильтр    │      │   нативный фильтр    │
   │   кнопка ПРИМЕНИТЬ   │      │   кнопка ПРИМЕНИТЬ   │
   └──────────────────────┘      └──────────────────────┘
```

**Три принципиальных правила, которые и убирают конфликты A1/A2/A3:**

1. **Обновление сателлита никогда не трогает колонку галочек.** `satRefresh()` пишет только колонки `1 … CHECKBOX-1` (1…12) и **не вызывает** `clearDataValidations` по колонке 13. Переотрисовываются только строки, а не вся таблица (по `POSITION_ID`, с удалением выпавших).
2. **Фильтр — своя ячейка B1 в своём файле** + нативный автофильтр Sheets (`createFilter`), а не пересборка листа. Это даёт нормальную сортировку/фильтрацию по любому столбцу без пересборки.
3. **Применение — по BATCH_ID.** Кнопка «ПРИМЕНИТЬ» в сателлите отправляет **только свои** отметки и сливает **только свою** партию.

### 8.2. Почему «просто скопировать файл» не работает (технические ограничения Apps Script)

Это надо понимать до начала внедрения:

1. **`onEdit` в сателлите бесполезен для мастера.** Простой триггер `onEdit` не может вызывать сервисы, требующие авторизации (`UrlFetchApp`, `LockService`); установленный триггер требует, чтобы **каждый отборщик** его авторизовал. Значит захват намерений через `onEdit` не подходит — пишем **по кнопке**.
2. **Вызвать чужую функцию напрямую нельзя.** Нет `import`. Варианты: веб-приложение, Apps Script Library, либо общий лист-канал.
3. **Программная запись не порождает `onEdit`.** Значит запись из сателлита в мастер **не** попадёт в очередь автоматически — её нужно либо записывать сразу в `PENDING_EDITS` (инбокс-вариант), либо обрабатывать в `doPost` (веб-приложение).
4. **`ScriptLock` — на проект, а не на таблицу.** Лок мастера **не** защитит одновременную запись из двух сателлитов. Для инбокс-варианта нужен `appendRow` (один атомарный `values.append`), а не `getLastRow()+1` + `setValues`.

### 8.3. Транспорт: два варианта

#### Вариант 1 — Web App (`doPost`) — **рекомендуемый**

**Мастер-скрипт:**
```js
// appsscript.json: access → "ANYONE_WITH_GOOGLE_ACCOUNT" (executeAs остаётся USER_DEPLOYING)
function doPost(e) {
  const req = JSON.parse(e.postData.contents);
  const check = v12VerifyBatchRequest(req);           // токен + актор + роль
  if (!check.ok) return v12JsonResponse({ ok: false, error: check.reason });
  const res = v12SubmitPickingBatch(req);             // идемпотентная регистрация партии
  if (!res.ok) return v12JsonResponse(res);
  const applied = v12ApplyBatch(res.batchId);         // слив ТОЛЬКО этой партии
  return v12JsonResponse({ ok: true, batchId: res.batchId, ...applied });
}
```

- **Плюсы**: явный контракт, есть ответ (можно показать результат отборщику), идемпотентность по `BATCH_ID`, не зависит от структуры листов мастера.
- **Минусы**: нужно развернуть веб-приложение и **изменить `access`** в манифесте (сейчас `MYSELF` — никто, кроме владельца, не сможет вызвать). Обязателен общий секрет (Script Properties) + явная валидация актора, т.к. `executeAs: USER_DEPLOYING`.
- **Таймаут**: вызов `UrlFetchApp.fetch` из сателлита ждёт ответа; при большой пачке применение может не уложиться. Решение: `doPost` **регистрирует** партию и возвращает `batchId` + `status: PENDING`; применение выполняет `v12ApplyBatch` либо сразу (если уложились), либо по короткому триггеру (каждые 1–5 мин). Сателлит затем опрашивает статус партии.

#### Вариант 2 — Лист-«инбокс» + триггер — **резервный**

- В мастер-таблице — лист `PICKING_INBOX` (BATCH_ID, SUBMITTED_AT, ACTOR, PROJECT, SPREADSHEET_ID, PAYLOAD_JSON, STATUS).
- Сателлит делает `SpreadsheetApp.openById(MASTER_ID).getSheetByName("PICKING_INBOX").appendRow([...])` — **одним атомарным вызовом**.
- Мастер разбирает инбокс: пунктом меню **или** новым триггером `v12ScheduledBatchDrain` (каждые 1–5 минут).
- **Плюсы**: не нужен web app, не нужен `UrlFetchApp`, минимум новой инфраструктуры. Запись атомарна.
- **Минусы**: сателлиту нужны **права редактирования** мастер-таблицы; результат партии отборщик видит только «прочитав» её статус из инбокса; задержка применения.

**Правило выбора**:
- Если администратор Google Workspace разрешает развёртывание веб-приложения с доступом «любой пользователь Google» → **вариант 1**.
- Если нет (жёсткие политики, запрет веб-приложений) → **вариант 2**.
- Оба варианта реализуются через **один и тот же** внутренний API: `v12SubmitPickingBatch(req)` + `v12ApplyBatch(batchId)`. Транспорт — сменный слой.

1. **`PENDING_EDIT_COLUMNS`** — добавить в конец (чтобы не сдвигать существующие индексы 1..10):

   BATCH_ID: 11,

### 8.5. Изменения в функциях мастера

| Функция | Что меняется |
|---|---|
| **`v12DrainPendingEdits(batchId)`** | Новый опциональный параметр. Если задан — берутся только PENDING-строки с этим `BATCH_ID` (`v12CollectPendingRowNumbers(data, batchId)`, `v12ResolvePendingIntents(data, batchId)`). Без параметра — прежнее поведение («слить всё»), это кнопка в мастере для админа. |
| **`v12ApplyChanges(batchId)`** | Пробрасывает `batchId`; остальное без изменений. |
| **`v12ApplyBatch(batchId)`** | **Новая.** Обёртка: `v12SubmitPickingBatch` уже записал намерения → вызвать `v12DrainPendingEdits(batchId)` → обновить статус партии в `PICKING_BATCHES`. |
| **`v12SubmitPickingBatch(req)`** | **Новая.** Валидация (см. §8.6), идемпотентность, `v12EnqueuePendingRows` с `BATCH_ID`/`PROJECT`, запись шапки партии. |
| **`v12EnqueuePendingRows(rowArrays)`** | Дописать в upsert-ветку обновление колонок `BATCH_ID`/`PROJECT`. Ключ upsert (`SOURCE|POSITION_ID|FIELD`) **не меняется** — это и есть защита от дублей. |
| **`v12BuildPendingRow(sourceKey, positionId, field, value, actor, editId, batchId, project)`** | Два новых опциональных параметра. |
| **`v12RebuildPendingFromChecked()`** | **Разделить.** Для ручного режима мастера — оставить как есть. Для партий — новая `v12ReconcileBatchFromPayload(batchId, items)`, которая добирает/схлопывает намерения **партии** по присланному payload, а не по чужим галочкам в мастер-листах. |
| **`v12HasCheckedHandoffs()` / `v12ReconcileCheckedHandoffs()` / `v12CollectCheckedHandoffs()`** | В новом режиме читают только лист ОТБОРКА мастера, который становится read-only → фактически перестают срабатывать. Оставлять для совместимости. |
| **`v12RefreshPicking`** | **Рефакторинг: вынести чистую часть.** Новая `v12BuildPickingRecords(posData, filterCode, readyLabel)` возвращает `[{row, color}]`. `v12RefreshPicking` = `clearBody` + `v12BuildPickingRecords` + запись + чекбоксы + цвета + фильтр. **Эту же чистую функцию переиспользует генератор payload для сателлита.** |
| **`v12InstallPickingCheckboxes`** | Без изменений (в мастере). |
| **`v12OnOpen()`** | Добавить пункты меню: «📦 Обработать партии отборщиков», «🧾 Журнал партий», «🔓 Освободить захваты проектов». |
| **`v12InstallTriggers()`** | Добавить (при варианте 2) `v12ScheduledBatchDrain` каждые 5 минут. |
| **`v12ConsistencyCheck()`** | Добавить проверки: партии в статусе PENDING старше N минут; захваты с истёкшим `EXPIRES_AT`; намерения, ссылающиеся на отсутствующие Position ID. |
| **`v12_roles.js`** | Новое право `PICKING_BATCH_SUBMIT` (для `WAREHOUSE`, `PRODUCTION`, `ADMIN`). Опционально `PICKING_CLAIM` (только `WAREHOUSE`). |

### 8.6. Протокол партии

**Payload (сателлит → мастер):**
```json
{
  "token": "<общий секрет из Script Properties>",
  "actor": "balalaikina79@gmail.com",
  "spreadsheetId": "<ID файла отборщика>",
  "batchId": "BATCH-<uuid>",
  "project": "1234.АБВ",
  "submittedAt": "2026-09-16T10:55:00+03:00",
  "items": [
    { "positionId": "BOM-0001:ART-77|Siemens", "checked": true },
    { "positionId": "BOM-0001:ART-91|ABB",     "checked": false }
  ]
}
```

**Правила обработки на мастере:**

1. **Токен** — сравнить с `PropertiesService.getScriptProperties().getProperty("PICKING_BATCH_TOKEN")`. Несовпадение → `{ok:false, error:"unauthorized"}`.
2. **Актор** — `actor` обязателен, `v12GetUserRole(actor)` должен давать `WAREHOUSE`, `PRODUCTION` или `ADMIN`; иначе `{ok:false, error:"forbidden"}`. Все дальнейшие записи идут через `v12WithActor(actor, ...)`, поэтому аудит/история/роли получат **реального отборщика**, а не владельца скрипта (в коде уже есть `_v12ActorOverride`).
3. **Идемпотентность** — если `batchId` уже есть в `PICKING_BATCHES` со статусом `APPLIED`/`FAILED` → вернуть прежний результат, **ничего не применять**.
4. **Захват проекта** — если `PICKING_CLAIMS` содержит `ACTIVE`-захват того же проекта другим актором → `{ok:false, error:"project_claimed_by:<email>"}` (мягкий режим: предупреждение; строгий — отказ).
5. **Намерения** — для каждого `item` с `checked=true` → строка намерения `SOURCE=PICKING`, `FIELD=HANDOFF`, `VALUE=true`, `BATCH_ID`, `PROJECT`. `checked=false` → `VALUE=false` (отмена; при сливе `v12IsBooleanPendingField && !value` → пропуск, см. `v12DrainPendingEdits`).
6. **Запись** — `v12EnqueuePendingRows` (лок, upsert, `flush`).
7. **Шапка партии** — `PICKING_BATCHES`: `STATUS=PENDING`, `TOTAL=items.length`.
8. **Применение** — `v12ApplyBatch(batchId)` → `v12DrainPendingEdits(batchId)` → **один** `v12RefreshProjections()`.
9. **Результат** — `STATUS=APPLIED|PARTIAL|FAILED`, `APPLIED`, `FAILED`, `ERROR` (тексты причин из `failedByRow`). Ответ сателлиту: `{ok:true, batchId, status, applied, failed, errors:[{positionId, reason}]}`.

### 8.7. Идемпотентность и отчёт для отборщика

- **Батч-ID** генерируется в сателлите **до** отправки и сохраняется в самом файле (Properties или ячейка), чтобы повторное нажатие «ПРИМЕНИТЬ» не создало вторую партию.
- Отборщик **видит результат**: колонка «Результат» / ноты на строках, либо дополнительный лист «Результат партии» в сателлите:
  `Position ID | Статус (Применено / Не применено) | Причина`.
- Причины приходят из мастерского `v12MarkReceivedByProduction`: «Не хватает доступного количества: необходимо N, доступно M», «Позиция невалидна...», «Позиция не найдена».

### 8.8. Захват проекта (`PICKING_CLAIMS`)

Проблема B4: двое берут один проект — сателлиты об этом не знают, а последствия (A9, A7) неприятны.

**Мягкий захват:**
- При выборе проекта в B1 сателлит вызывает мастер: `claimProject(project, actor, spreadsheetId)`.
- Мастер пишет `PICKING_CLAIMS`: `PROJECT`, `ACTOR`, `SPREADSHEET_ID`, `CLAIMED_AT`, `EXPIRES_AT = now + BATCH_CLAIM_TTL_MIN`, `STATUS = ACTIVE`.
- Если по проекту есть ACTIVE-захват другого актора → сателлит показывает предупреждение «Проект уже отбирает Ivan — продолжить?».
- По окончании (все галочки отправлены / «Завершить отбор») → `STATUS = RELEASED`.
- Просроченные (`EXPIRES_AT < now`) автоматически считаются `EXPIRED` — чтобы забытый захват не блокировал работу.

Это решает 90 % практических коллизий: обычно конфликт возникает не на позиции, а на уровне проекта.

### 8.9. Политика выдачи материала (конфликт A7 — не решается сателлитами)

Система **принципиально не резервирует** из физического склада (`MATERIAL_STATE` — контрольный лист). Двое отборщиков могут «успешно» выдать один и тот же материал по двум BOM. Это нужно решать явной политикой. Варианты:

**Вариант «мягкий» (минимум изменений):**
- Оставить как есть + `PICKING_CLAIMS` по проектам.
- Добавить в `v12ConsistencyCheck` отчёт о материалах, где `sum(reservedQty) > warehouseQty` (`v12RecalculateWarehouseConsistency` уже возвращает `inconsistencies` — сейчас результат **никем не используется**, его надо начать потреблять).
- Вывести предупреждение в сателлит: «Остаток склада меньше суммарной потребности по материалу».

**Вариант «строгий» (рекомендуемый, если склад реально один):**
- Перед применением партии считать по каждому `materialKey` суммарную выдачу **всех незакрытых намерений HANDOFF** (`PENDING_EDITS` с `FIELD=HANDOFF` и `VALUE=true`, включая чужие партии) и сравнить с `warehouseQty` из `MATERIAL_STATE`.
- Если `warehouseQty - ужеОбещанное < выдаваемое` → пометить позиции партии `FAILED` с причиной «Материал выдан/зарезервирован под другой проект».
- Это «квазирезерв»: не запись в `MATERIAL_STATE`, а проверка на момент применения. Он полностью в духе текущей модели («система не резервирует, а проверяет консистентность»).

### 8.10. Спутник: что именно в нём реализуется

Сателлит — **отдельный Apps Script-проект**, привязанный к своему файлу. Состав:

| Функция | Назначение |
|---|---|
| `satOnOpen()` | Меню «Отборка», кнопка «ПРИМЕНИТЬ», «🔄 Обновить» |
| `satRefresh()` | Читает `SpreadsheetApp.openById(MASTER_ID)` → `POSITION_STATE`; **мапит колонки по именам заголовков**, а не по индексам; фильтрует по B1 и «активна и не передана»; **пишет только колонки 1…12**; удаляет строки, выпавшие из выборки; **не трогает колонку 13** |
| `satGetFilter()` | Читает свой B1 (список проектов тянется из мастера) |
| `satSubmitBatch()` | Собирает отмеченные строки, формирует payload, `UrlFetchApp.fetch(MASTER_URL, {method:"post", payload: JSON.stringify(...)})` (или `appendRow` в `PICKING_INBOX`) |
| `satShowResult(json)` | Пишет результат в лист «Результат партии» / ноты |
| `satCheckVersion()` | Сравнивает `V12_CONFIG.VERSION` мастера (через `v12GetMasterMeta`) и свою константу; при расхождении — предупреждение |

**Ключевые защиты в сателлите:**
- **Обновление не затирает галочки**: `satRefresh()` пишет диапазон `(2, 1, lastRow-1, 12)`, колонка 13 не входит. Строки, у которых `Position ID` совпал, обновляются «на месте», чтобы **галочка не поехала на чужую позицию**.
- **Нативный автофильтр** (`createFilter`) — сортировка/фильтр по любому столбцу без пересборки. Фильтр проекта (B1) — отдельный механизм (пересборка только строк своего файла, это никому не мешает).
- **Колонка «Обновлено»** (взять `UPDATED_AT` из POSITION_STATE) — отборщик видит свежесть данных.

### 8.11. Дебаунс применений (конфликт B6)

Если 5 отборщиков жмут «Применить» каждые 2 минуты — это 5 полных пересборок всех пяти проекций. Меры:

1. **Только своя партия** (уже даёт `v12DrainPendingEdits(batchId)`).
2. **Сериализация локом** — второй одновременный `doPost` получит `{skipped:true}` и должен повторить.
3. **Отложенное применение**: `doPost` регистрирует партию (`PENDING`) и сразу возвращает `batchId`; `v12ScheduledBatchDrain` (каждые 1–5 мин) применяет **все накопленные** партии **одним** `v12RefreshProjections()`. Это радикально снижает число пересборок.
4. **Окно часового синка** — перенести `v12ScheduledUpdate` на ночное время либо вызывать `v12RunFullSync` только когда очередь партий пуста.

## 10. Что эта стратегия НЕ решает

1. **Физический дефицит (A7).** Сателлиты разделяют рабочее место, но не материал. Нужна политика §8.9.
2. **Двойная работа по одному проекту** — решается только «мягко» через `PICKING_CLAIMS`; при одновременном выборе одного проекта двумя отборщиками возможен оверлап до истечения TTL.
3. **Возврат ошибочной передачи** — остаётся ручным: «↩ Вернуть из архива» по каждому Position ID (`v12PromptReturnFromArchive`), причина обязательна. Массового отката партии **нет** — это стоит добавить отдельно (undo по BATCH_ID).
4. **Задержка применения** (вариант 2 / отложенный дренаж) — отборщик видит результат не мгновенно.
5. **Ошибки данных в исходном BOM** — позиция невалидна → передача `blocked`. Сателлит только покажет причину, исправляет экономист.
6. **`v12Toast` в сателлите** — механизм мастера не работает в другом файле; нужны свои уведомления.
