## 3. 🔴 Найденная регрессия: P7 ломает чекбоксы

### Механизм
`v12ClearBody` → `clearBody` → `clearRange`, а `clearRange` содержит:
```js
range.clearContent();
range.clearDataValidations();   // ← удаляет data-validation, а не только значения
```
Функции проекций вызывают `v12ClearBody(...)` перед записью строк, то есть **на каждом полном пересчёте валидации тела листа удаляются**.

Внесённый в P7 «гвард по числу строк» возвращает управление ДО повторной установки валидации:
```js
function v12InstallDeficitCheckboxes(rowCount) {
  if (rowCount > 0 && _v12ProjectionUiState.deficitCheckboxes === rowCount) {
    return;               // ← валидации только что стёрты clearBody, но не восстановлены
  }
  _v12ProjectionUiState.deficitCheckboxes = rowCount;
  ...
}
```
Аналогично `v12InstallPickingCheckboxes`.

### Последствие
- 1-й полный пересчёт Сводки/Отборки: `_v12ProjectionUiState.*` пуст → валидации устанавливаются, чекбоксы видны.
- 2-й полный пересчёт при **том же** числе строк: `clearBody` стирает валидации → гвард делает `return` → **чекбоксы «Реальная поставка» (Сводка) и «Отметка получено» (ОТБОРКА) перестают быть чекбоксами** (ячейки становятся обычными/текстовыми).
- Путь `v12RefreshDeficitSummaryRow` (одиночная правка строки) валидации не стирает и восстанавливает чекбокс только для одной строки — то есть после полного пересчёта чекбоксы остаются лишь в последней затронутой строке.

Полный пересчёт (`v12RefreshProjections`) вызывается после реальной поставки, передачи производству, правки склада, обработки диапазона и полной синхронизации — то есть регрессия проявляется быстро в реальной эксплуатации.

### Почему не поймали локальные тесты
В моках `_local_tests/*` методы `clearDataValidations()` и `setDataValidation()` — пустышки, а тесты проверяют **значения** ячеек, а не наличие валидаций. Поэтому S1–S9 и C1–C8 остаются зелёными.

### Что НЕ затронуто (гвард корректен)
- `v12InstallWorkingBomCheckboxes` и `v12InstallDashboardCheckboxes` гварда не имеют и всегда восстанавливают валидацию — корректно.
- `v12ApplyDashboardColors` (условное форматирование) — гвард безопасен: `clearRange` НЕ сбрасывает условное форматирование (оно отдельно от data-validation).

### Рекомендация (минимальная правка)
Убрать гвард из `v12InstallDeficitCheckboxes` и `v12InstallPickingCheckboxes` (вернуть безусловное `clearDataValidations`+`setDataValidation`), **либо** изменить `clearRange` так, чтобы он не сбрасывал валидации (`clearContent()` без `clearDataValidations()`), **либо** запоминать не «число строк», а факт того, что валидации действительно установлены после последнего `clearBody`. Гвард в `v12ApplyDashboardColors` можно оставить.

## 4. Прочие замечания (не критично, к сведению)

1. **`v12GetWarehouseQty` стала сиротой.** После удаления `v12GetWarehouseQtyForPositionRow` и вызова `v12GetWarehouseQty(...)` в `v12SetRealDeliveryQty` определение `v12GetWarehouseQty(materialKey, index)` осталось в `v12_material_state.js` без очевидных вызывающих. Требует проверки grep-ом; если вызовов нет — кандидат на удаление (я не смог это подтвердить: в режиме Explore недоступен поиск по файлам).
2. **JSDoc `v12BuildPositionRow`** по-прежнему упоминает `warehouseQty` в перечне `ops` — параметр больше не читается (косметика).
3. **P6 неполон по стоимости.** `v12GetPositionsByBom(reg.bomId, idx)` фильтрует весь индекс по `BOM_ID` на каждый BOM → O(BOMs × positions). Индекс не перечитывается (это и было целью), но скан остаётся; для десятков тысяч строк стоит сгруппировать позиции по `BOM_ID` заранее.
4. **WORKING BOM без harvest.** `v12HarvestPickingInput` есть только для ОТБОРКИ. У WORKING BOM чекбокс теперь рабочий (B1), но при пропущенном быстром `onEdit` отметка будет сброшена пересборкой (нет «страховки»). Раньше колонка была нерабочей, поэтому ценность бага возросла. Рекомендуется добавить аналогичный `v12HarvestWorkingBomInput`.
5. **B5 неполно.** Остались строгие `=== true` для чтения признаков «Получено»/`RECEIVED_BY_PRODUCTION` внутри `v12AggregateBomStates` (косвенно — через `production === RECEIVED`, что безопасно) и в местах, где признак уже приведён. Явных пропусков, ломающих логику, не обнаружено, но единообразие не полное.
6. **Порядок присваивания гварда.** В `v12InstallDeficitCheckboxes`/`v12InstallPickingCheckboxes` состояние записывается до проверки `maxRows <= 0` — безвредно, но при откате P7 это исчезнет автоматически.

## 5. Заключение

Внесённые изменения в целом **улучшили систему**: исправлены обе критические функциональные ошибки (WORKING BOM-чекбокс; незаполнявшийся `BOM_REVISION`), устранена опасность потери пользовательских триггеров, подключён возврат из архива, удалён существенный объём мёртвого кода и реализованы два главных ускорения (единое чтение `POSITION_STATE`, снятие O(N²)-доступа к складу). Регрессий в этих частях не найдено.

**Единственная выявленная регрессия — P7** (гварды чекбоксов в Сводке и ОТБОРКЕ): из-за `clearRange → clearDataValidations()` валидации стираются каждый полный пересчёт, а гвард препятствует их восстановлению — чекбоксы перестают работать со второго пересчёта при неизменном числе строк. Поскольку это прямо подрывает ключевой сценарий (отметка реальной поставки и передачи производству), **изменение P7 в части двух `Install…Checkboxes` следует откатить** (гвард `v12ApplyDashboardColors` — оставить).

После отката P7 система будет соответствовать заявленному в `project_info__31.md` состоянию без оговорок. Дополнительно рекомендуется закрыть п. 1 (проверить/удалить `v12GetWarehouseQty`), п. 3 (предгруппировка позиций по BOM) и п. 4 (harvest для WORKING BOM).
