# BOM CONTROL SYSTEM V12 — разбор кодовой базы и предложение по переходу на веб + БД

> Отчёт подготовлен в **Explore Mode** (режим исследования). Здесь только анализ и варианты; реализация — в **Act Mode**.

## 1. Что это за система

Система управления обеспечением производства по спецификациям BOM: связывает **потребность** (сколько материалов нужно на изделие-проект), **резерв** (что уже закрыто запасом), **закупку** (заказано / ожидаемая поставка), **физический склад** и **факт передачи материалов в производство**. Роли: экономист, снабженец, кладовщик, производство, админ.

Реализация — **Google Apps Script** (`runtimeVersion: V8`) поверх **Google Sheets**: одна «мастер-таблица» с листами-справочниками (`POSITION_STATE`, `MATERIAL_STATE`, `PENDING_EDITS`, журналы) и листами-проекциями (`Сводка дефицитов`, `ОТБОРКА`, `WORKING BOM`, `СНАБЖЕНИЕ`, `Dashboard`). Источник задания — файлы BOM в **Google Drive** (Google Таблицы или CSV) в фиксированной папке. Плюс «сателлиты» — отдельные Apps Script-проекты в личных таблицах кладовщиков, которые отправляют «лоты» отборки в мастер через веб-приложение.

Ключевое следствие для рефакторинга: **вся предметная логика уже вынесена в чистые функции и декларативно описана в `v12_config.js`** — это резко снижает риск переписывания. Основная часть кода (~70%) — это не бизнес-логика, а **обходы ограничений Google Sheets**: очередь намерений, блокировки, ручная идентификация пользователя, батч-запись, реконсиляция потерянных событий `onEdit`, сателлиты для параллельной работы.

## 2. Архитектура

### 2.1. Главный принцип — SOURCE ≠ STATE ≠ VIEW

Зафиксирован в `v12_config.js` и `task_progress.md`:

```
ИСХОДНЫЕ BOM (Drive, только чтение)
      │  v12_source.js (парсинг, алиасы заголовков)
      ▼
 BOM_REGISTRY (реестр: BOM ID, ревизия, hash источника)
      │  v12_change_engine.js (detectBOMChanges → ChangeSet → applySourceRevision)
      ▼
 POSITION_STATE  ← ЦЕНТРАЛЬНОЕ ОПЕРАЦИОННОЕ СОСТОЯНИЕ (32 колонки)
      │      ▲
      │      │ очередь намерений PENDING_EDITS (правки пользователей)
      │      └ v12_queue.js → v12_operations.js / v12_handoff.js
      │
      ├─► MATERIAL_STATE (физический склад, КОНТРОЛЬНЫЙ, не источник потребности)
      │
      └─► ПРОЕКЦИИ (v12_projections.js) — пересобираются целиком:
            DEFICIT_SUMMARY · ОТБОРКА · WORKING BOM · СНАБЖЕНИЕ · DASHBOARD
```

1. **SOURCE** — исходные BOM, принадлежат экономисту, система их **никогда не пишет** (`ТЗ №136`).
2. **STATE** — `POSITION_STATE`: на одну строку-BOM-позицию хранит все 8 канонических количеств, состояния, флаги, валидацию, жизненный цикл.
3. **VIEW** — проекции: производные «экраны» для ролей. Они **не хранят истину**, а полностью пересобираются из `POSITION_STATE`.

### 2.2. Стиль кода

- Один Apps Script-проект, **все функции глобальные**, без модулей/импортов; порядок файлов не важен.
- Модульность «по файлам»: `v12_*.js` — мастер, `sat_*.js` — сателлит отборщика, `utils/sheet_service/lock/logger.js` — generic-слой.
- Все обращения к таблице — через `sheet_service.js` (`readSheetValues`, `writeValues`, `batchWrite`, `batchWriteBlock`, `clearBody`, `ensureSheet`).
- Блокировки — через реентрантный `acquireScriptLock()` (`lock.js`).
- Логирование — буферизованное `logSystem()` + `flushSystemLog()` (`logger.js`).
- Константы/схема/статусы/цвета — в единственном `V12_CONFIG` (`v12_config.js`).

### 2.3. Точки входа

| Точка входа | Файл | Что делает |
|---|---|---|
| `onOpen()` → `v12OnOpen()` | `v12_controller.js` | строит меню «BOM CONTROL V12», обновляет индикатор неприменённых изменений |
| `v12OnEdit(e)` | `v12_trigger.js` | перехват правок: быстрый путь (запись намерения в очередь) / медленный путь (склад, фильтр B1, откат) |
| `v12ScheduledUpdate()` | `v12_trigger.js` | полная синхронизация источника **раз в сутки в 03:00** |
| `v12ScheduledBatchDrain()` | `v12_trigger.js` | дежурный слив лотов отборщиков **каждые 5 минут** |
| `doPost(e)` / `doGet(e)` | `v12_webapp.js` | веб-API транспорта лотов: `rows`, `submit`, `status`, `claim`, `release`, `pickers`, health |
| Кнопка-картинка «ПРИМЕНИТЬ» | `v12_ui.js` | `insertImage(blob…)` + `assignScript("v12ApplyChangesUI")` на 4 листах |

### 2.4. Стек и внешние зависимости

- **Google Apps Script V8**, сервисы: `SpreadsheetApp`, `DriveApp`, `PropertiesService` (script + user), `LockService`, `Session`, `UrlFetchApp` (сателлит), `ContentService` (JSON API), `Utilities` (UUID, MD5, base64).
- Области доступа мастера: `drive`, `spreadsheets`, `script.container.ui`, `userinfo.email`, `script.scriptapp`. У сателлита — `spreadsheets.currentonly` + `script.external_request`.
- Веб-приложение мастера: `executeAs: USER_DEPLOYING`, `access` (в README — «любой пользователь с аккаунтом Google»); в `appsscript.json` сейчас `"access": "MYSELF"` — **расхождение**, которое нужно учесть при развёртывании.
- Развёртывание — `clasp` (`.clasp.json`, `rootDir: ""`, `skipSubdirectories: false`), исключения — `.claspignore` (`sat_*.js`, `_local_tests/**`, `_tmp_*.js`).
- Тесты — локальные Node-скрипты в `_local_tests/*.js` + прогон `_tmp_run.js` (моки `SpreadsheetApp` и т.п.), проверка синтаксиса — `node --check`.

### 2.5. Важное следствие для будущей архитектуры

Ядро расчёта — **чистая функция без I/O**:

```js
v12CalculatePositionState({ requiredQty, reservedQty, orderedQty, realDeliveryQty,
                            receivedByProduction, row }) → { deficitQty, uncoveredNeed,
  overOrderedQty, shortDeliveryQty, availableForProduction, readyForHandoff,
  supplyState, productionState, flags, valid, missing }
```

Этот файл (`v12_calculate.js`) и `v12_projections.js::v12BuildPickingRecords` переносятся в новый backend **как есть** (перевести на TypeScript почти механически). Риск изменения бизнес-логики здесь минимален — это лучший «рычаг» рефакторинга.

## 4. Ключевые абстракции

### 4.1. `V12_CONFIG` (`v12_config.js`)
- **Ответственность**: единственный источник правды по схеме (листы, номера колонок, статусы, роли, цвета, настройки транспорта) + зафиксированные решения по конфликтам ТЗ (К1–К7).
- **Ключевые блоки**: `SHEETS`, `COLUMN_COUNT`, `*_COLUMNS` (индексы 1-based), `HEADERS` (канон заголовков), `SUPPLY_STATE`, `PRODUCTION_STATE`, `LIFECYCLE_STATE`, `VALIDATION_STATUS`, `FLAGS`, `BOM_STATUS(+COLOR)`, `ROLES`, `COLORS`, `AUDIT_ACTIONS`, `SOURCE_UI`, `PENDING_FIELD`, `PENDING_STATUS`, `PICKING_BATCH_STATUS`, `SETTINGS`, `BATCH`, `WEB_ACTIONS`, `PICKING_FILTER`, `DRIVE.FOLDER_ID`.
- **Почему важно**: перенос на БД — это, по сути, **транскрипция этого файла в DDL + enum'ы**. Все состояния и переходы уже пронумерованы и названы.

### 4.2. `v12CalculatePositionState` (`v12_calculate.js`, строка ~28)
- **Ответственность**: чистая функция — вся арифметика и все состояния позиции.
- **Формулы (это и есть «бизнес-логика, которая не меняется»)**:
  - `deficitQty = max(0, required − reserved)` — **не вычитаем ordered**
  - `uncoveredNeed = max(0, deficit − ordered)`
  - `overOrderedQty = max(0, ordered − deficit)`
  - `shortDeliveryQty = max(0, ordered − realDelivery)`
  - `availableForProduction = reserved + realDelivery` (К1)
  - `readyForHandoff = valid && !received && available ≥ required && required > 0` (К3 — «готово к передаче» ≠ «передано»)
- **Состояние снабжения** (порядок ветвлений критичен): `NO_REQUIREMENT → RESERVED → NOT_ORDERED → PARTIALLY_ORDERED → ORDERED → PARTIALLY_DELIVERED → DELIVERED`.
- **Состояние производства**: `RECEIVED` → `NOT_AVAILABLE` → `READY_FOR_HANDOFF` (если валидна, иначе `PARTIALLY_AVAILABLE`) → `PARTIALLY_AVAILABLE` → `NOT_AVAILABLE`.
- **Флаги**: `OVER_ORDERED`, `SHORT_DELIVERY`, `CHANGED` (при невалидности).
- **Используется**: `v12ApplyComputedToRow` → все операции, синхронизация, проекции.

### 4.3. `v12GeneratePositionId` / `v12BuildMaterialKey` (`v12_utils.js`)
- **positionId** = `bomId + ":" + materialKey`, при коллизии внутри BOM — `#2`, `#3`, … Это **стабильный идентификатор строки** на всю жизнь позиции; на нём держатся: очередь намерений, галочки в сателлите, архивация, откат.
- **materialKey** (К5) = `code|manufacturer`, а при пустом артикуле — `name|model[|manufacturer]|unit`.
- **bomId** = имя файла BOM без расширения (при первичном создании в `BOM_REGISTRY`), поиск существующей записи — **по имени BOM** (`v12UpsertSourceBOM`).
- **`v12ValidatePosition`** (ТЗ №8, К4): обязательны № п/п, Наименование, Модель, Ед.изм, Кол-во > 0, Крайний срок. **Артикул не обязателен**; `Зарезервировано = 0` — валидный дефолт.

### 4.4. `POSITION_STATE` (`v12_position_state.js`, 32 колонки)
- **Ответственность**: центральная таблица операционного состояния. Входные поля (потребность, резерв, заказ, реальная поставка, даты, факт передачи, жизненный цикл) + производные (validation, supplyState, productionState, deficit, uncovered, overOrdered, shortDelivery, available, flags, updatedAt).
- **Жизненный цикл**: `ACTIVE → ARCHIVED` (при передаче производству) → `ACTIVE` (при возврате из архива); `REMOVED` — позиция исчезла из источника. Архивные/удалённые исключаются из проекций и агрегаций.
- **Правило ручного редактирования**: `POSITION_STATE` руками править нельзя (кроме ADMIN) — `v12HandlePositionStateEdit` откатывает.

### 4.5. `MATERIAL_STATE` — физический склад (`v12_material_state.js`)
- **Ответственность**: остаток на складе по `materialKey`. `warehouseQty` — ввод кладовщика; `reservedQty` — **контрольная агрегация** резервов из активных позиций; `freeQty = max(0, warehouse − reserved)`.
- **Ключевая тонкость**: склад **не участвует** в расчёте доступности (`availableForProduction = reserved + realDelivery`). Склад — контрольная книга; несоответствие `reserved > warehouse` фиксируется как `RESERVATION_PHYSICAL_INCONSISTENCY` (ТЗ №30) и теперь **показывается** в `v12ConsistencyCheck` (раньше вычислялось и никуда не выводилось).

### 4.6. Очередь намерений `PENDING_EDITS` (`v12_queue.js`, 12 колонок)
- **Ответственность**: фиксация правок пользователя «в очередь» и пакетное применение по кнопке «ПРИМЕНИТЬ».
- **Поля намерения** (`PENDING_FIELD`): `HANDOFF`, `REAL_DELIVERY`, `ORDERED_QTY`, `EXPECTED_DATE`, `DASHBOARD_DONE`.
- **Правило «last-wins»** по ключу `SOURCE|POSITION_ID|FIELD`; для чекбокс-полей `value=false` означает **отмену** намерения, для типизированных (`Заказано=0`, очистка даты) — обычное значение.
- **Канал без потерь**: сначала попытка взять лок (с backoff `[0, 300, 800] мс`) и upsert по ключу; если лока нет — атомарный `appendRow` (не теряется, дубли потом схлопываются `v12CompactPendingEdits`).
- **Реконсиляция**: `v12RebuildPendingFromChecked` приводит множество чекбокс-намерений к фактическим галочкам (лечит потерянные `onEdit` при массовой отметке).
- **Применение**: `v12ApplyChanges` → `v12DrainPendingEdits(batchId, interactive)` — один пересчёт проекций на всю пачку, идемпотентно, с буферами логов и одним `operationId`.
- **Права при авторe-неизвестном**: намерения без автора применяются **только интерактивно** («ПРИМЕНИТЬ» человеком) и проверяются по роли нажавшего; в фоне такие намерения остаются в очереди.

### 4.7. Операции (`v12_operations.js`, `v12_handoff.js`)
- `v12SetOrderedQty(positionId, qty, index, ctx)` — абсолютное значение, 0 = сброс заказа.
- `v12SetExpectedDate(positionId, date, …)` — нормализация даты (Date/строка/серийный номер Sheets), пусто = очистка.
- `v12SetRealDeliveryQty(positionId, qty, …)` — **дельта идёт на склад**: `warehouse += (new − old)`; `REAL_DELIVERY_DATE` проставляется при первой положительной отметке, сбрасывается при обнулении.
- `v12MarkReceivedByProduction(positionId, sourceUI, skipRefresh, ctx)` — идемпотентная передача: проверяет валидность и `available ≥ required`, пишет факт+кол-во+дату+кто, **архивирует** позицию и **списывает склад на `required`**.
- `v12ReturnFromArchive(positionId, reason)` — единственный путь отмены передачи: возвращает количество на склад, сбрасывает флаг, `lifecycle=ACTIVE`, пересобирает проекции. Причина обязательна (аудит).
- Все операции поддерживают **два режима**: одиночный (сами пишут и пересобирают) и пакетный (`ctx` — копят записи в буферах, проекции пересобираются один раз).

### 4.8. Проекции (`v12_projections.js`)
| Проекция | Фильтр состава | Особенности |
|---|---|---|
| `DEFICIT_SUMMARY` (15 кол.) | активные, не переданные, `available < required`, `deficit > 0` | редактируемые: Заказано(10), Ожидаемая(11), Реальная поставка(13); автофильтр; цвет строки по статусу |
| `ОТБОРКА` (13 кол.) | `lifecycle=ACTIVE`, не передано, фильтр по коду проекта из **B1** | порядок: BOM → «На складе» вверх → № строки; цвет строки; «Дата поставки» — приоритет: дата создания BOM (если закрыто резервом) → реальная дата поставки → ожидаемая |
| `WORKING BOM` (16 кол.) | все `ACTIVE` | чекбокс передачи (15) |
| `СНАБЖЕНИЕ` (10 кол.) | `deficit > 0` и материал не обеспечен | агрегация по `materialKey`; колонка «Проекты»: «<дефицит> - <проект> - <крайний срок>», по строке на проект, сортировка по сроку вверх |
| `DASHBOARD` (11 кол.) | все активные BOM, кроме `EXCLUDED_BOMS` | агрегат по BOM → статус; чекбокс «Выполнено» (1); «BOM ID» скрыт визуально |

**Статус BOM** (`v12ComputeBomStatus`, приоритет сверху вниз): `Ошибка данных` → `Скомплектован, готов к работе` (все получены) → `На складе, ждет отборки` (все на складе) → `Есть незаказанные компоненты` → `Ожидается поставка (Опаздывает)` → `(В срок)`.

**Исход снабжения** (`v12ProcurementOutcome`, единый для сводки и статуса BOM): `NOT_ORDERED` (нет заказа **или нет ожидаемой даты**), `PARTIAL` (ordered < deficit), `ON_TIME` (ожидаемая ≤ крайний срок), `LATE`.

### 4.9. RBAC (`v12_roles.js`)
- `V12_ROLE_MAP` — карта email → роль **прямо в коде** (7 адресов: ECONOMIST, 3× PROCUREMENT, WAREHOUSE, VIEWER, ADMIN).
- Матрица прав — в `v12CanEditField(role, action)`:
  - ECONOMIST: `SOURCE_BOM_WRITE`, `DEADLINE`, `REAL_DELIVERY`
  - PROCUREMENT: `ORDERED_QTY`, `EXPECTED_DATE`
  - WAREHOUSE: `WAREHOUSE_QTY`, `PICKING_CHECKBOX`, `PICKING_BATCH_SUBMIT`, `PICKING_CLAIM`
  - PRODUCTION: `PICKING_CHECKBOX`, `WORKING_BOM_CHECKBOX`, `DASHBOARD_CHECKBOX`, `PICKING_BATCH_SUBMIT`
  - ADMIN: `*`; VIEWER: ничего
- **Если `V12_ROLE_MAP` пуст — все становятся ADMIN** (режим «из коробки»).
- Нормализация email обязательна: в карте есть адрес с заглавной буквой, а Google отдаёт нижний регистр.

### 4.10. Транспорт лотов (`v12_batches.js` + `v12_webapp.js` + `sat_*.js`)
- **Лот** = одна отправка «ПРИМЕНИТЬ» из личного файла: `BATCH_ID`, проект, отборщик, список `positionId`. Идемпотентность по `BATCH_ID` (повтор возвращает прежний результат).
- **Мягкий захват проекта** (`PICKING_CLAIMS`): конфликт не блокируется, а показывается; TTL 120 мин; просроченные → `EXPIRED`.
- **Безопасность API**: общий секрет в Script Properties (`PICKING_BATCH_TOKEN`, формат `PBT-…`) + актор передаётся явно и проверяется по `V12_ROLE_MAP` (WAREHOUSE / PRODUCTION / ADMIN). Веб-приложение работает как владелец скрипта, поэтому `Session.getActiveUser()` там **не** источник личности.
- **Флаг синхронизации** (`V12_SYNC_IN_PROGRESS`) с TTL 5 мин: пока идёт полный синк, приём лотов отклоняется (иначе лот сослался бы на удаляемые позиции).
- **Ограничение размера лота**: `MAX_ITEMS = 1500` (лимит исполнения Apps Script 6 минут).

### 4.11. `v12BuildPickingRecords` (`v12_projections.js`)
- **Чистая** сборка строк ОТБОРКИ: `[{ row[], color }]`. Один и тот же алгоритм используют мастер-лист **и** веб-эндпоинт `rows` для сателлита — чтобы мастер и личный файл не разошлись в трактовке. Это готовая точка переиспользования в новом backend.

## 5. Потоки данных

### 5.1. Экономист меняет исходный BOM → система пересчитывает
1. Экономист правит файл BOM в папке Drive (`DRIVE.FOLDER_ID`) и запускает «🔄 Полная синхронизация» (или ждёт 03:00).
2. `v12RunFullSync` (`v12_trigger.js`) поднимает лок + флаг синхронизации, сначала сливает очередь (`v12DrainPendingEdits`) и добирает лоты.
3. `v12ListSourceBOMFiles` — список файлов (spreadsheet/CSV) минус `EXCLUDED_BOMS`.
4. `v12ReadSourceBOM` → `v12ParseSourceRows` — парсинг по алиасам заголовков.
5. `v12UpsertSourceBOM` — поиск/создание записи в `BOM_REGISTRY` по имени, MD5-hash материалов, инкремент `SOURCE_REVISION`, запись в `BOM_REVISION`.
6. `v12SyncBOM` → `v12DetectBOMChanges` (сравнение полей) → `ChangeSet` → `v12ApplySourceRevision` (batch-запись новых/изменённых, `REMOVED` для исчезнувших).
7. `v12RecalculateWarehouseConsistency` + `v12RefreshAllProjections`.

### 5.2. Снабженец вводит «Заказано» и «Ожидаемую поставку»
1. Правка ячейки «Сводки дефицитов» → `v12OnEdit` → `v12CaptureCheckboxEdit` → `v12CaptureDeficitEdit`.
2. Права проверяются по роли (если автор определён); намерение нормализуется (`v12NormalizePendingValue`) и пишется в `PENDING_EDITS` (upsert или `appendRow`).
3. `v12ReconcilePendingHandoffs` пересобирает множество чекбокс-намерений по фактическим галочкам.
4. Снабженец нажимает **«ПРИМЕНИТЬ»** → `v12ApplyChangesUI` → `v12ApplyChanges` → `v12DrainPendingEdits(undefined, true)`.
5. Разбор `v12ResolvePendingIntents` (last-wins) → по каждому намерению `v12WithActor(user)` → `v12ApplyPendingIntent` → `v12SetOrderedQty` / `v12SetExpectedDate` / `v12SetRealDeliveryQty`.
6. Накапливаются буферы: записи `POSITION_STATE`, складские дельты, `ARCHIVE`/`MATERIAL_HISTORY`/`EVENT_LOG`; `POSITION_STATE` пишется блочно/отрезками (`v12WritePositionBatch`).
7. Один `v12RefreshProjections()`; строки очереди помечаются `DONE`/`FAILED`; старые обработанные вычищаются (`QUEUE_PURGE_DONE_DAYS = 30`); сбрасывается индикатор.

### 5.3. Кладовщик передаёт материал производству
1. Кладовщик работает в **личном файле**: «Отбор» → «🔄 Обновить список» → `satRefresh` → `satFetchPickers` + `satFetchClaim` + `satFetchRows`.
2. Мастер отдаёт строки через `doPost` → `v12WebRows` → `v12BuildPickingRecords` (тот же алгоритм, что и мастерский лист).
3. Сателлит пишет колонки 1–12, **не трогая колонку 13**: галочки сопоставляются **по Position ID** (`satWriteRows`).
4. «ПРИМЕНИТЬ» → `satSubmit` → `satResolveBatchId` (защита от двойного клика 2 мин) → `satFetchSubmit(batchId, project, items)`.
5. Мастер: `v12VerifyBatchRequest` (токен + роль) → `v12WebSubmit` → `v12SubmitPickingBatch` (идемпотентность, мягкий захват, намерения с `BATCH_ID`) → `v12ApplyBatch(batchId)` → `v12DrainPendingEdits(batchId)`.
6. По каждой отмеченной позиции: `v12MarkReceivedByProduction` → проверка валидности и доступности → фиксация передачи → `v12ArchivePosition` → списание склада на `required` → `ARCHIVED`.
7. Лот получает `APPLIED` / `PARTIAL` / `FAILED`, ошибки по позициям пишутся в колонку «Ошибка» (до 15 строк). Сателлит показывает результат и снимает галочки **только** по факту применения.
8. Если лок был занят — лот остаётся `PENDING` с `retryAfterSec`; его добьёт `v12ScheduledBatchDrain` (каждые 5 мин) или `v12RecoverStuckBatches`.

### 5.4. Производство отмечает проект «Выполнено»
1. Чекбокс в Dashboard → очередь, поле `DASHBOARD_DONE`, `POSITION_ID` = `BOM ID`.
2. «ПРИМЕНИТЬ» → `v12ApplyDashboardDoneIntent`: гейт «BOM скомплектован» (агрегат `v12AggregateBomStates`, статус `READY`) → `v12SetBomDone(bomId, true, skipRefresh)` → запись в `EXCLUDED_BOMS`.
3. Отмеченный BOM **исчезает** из Dashboard (проекция фильтрует excluded). Отмена — только через меню «↩ Вернуть проект в Dashboard».

## 6. Неочевидные поведения и решения (самое важное для того, кто будет переписывать)

### 6.1. Почему существует кнопка «ПРИМЕНИТЬ» (и почему на веб её можно убрать)
До V3 `onEdit` сам применял правку, удерживая общескриптовый лок и пересобирая 5 проекций — а фоновая пересборка конкурировала с набором текста. Результат: введённые числа «сбрасывались в 0.0», галочки снимались, всплывало «Система занята». Поэтому правки **только фиксируются** в очереди, а применяются пакетно.

**Следствие для новой архитектуры**: вся машинерия очереди (`PENDING_EDITS`, реконсиляция, схлопывание дублей, `last-wins`, индикатор) — **не бизнес-требование, а обход ограничений Google Sheets**. В веб-приложении с БД правку можно применить в транзакции сразу. Но есть два бизнес-смысла, которые терять нельзя и нужно решить явно:
1. «Заказ считается оформленным только когда заполнены **оба** поля — Заказано и Ожидаемая поставка» (это правило живёт в `v12ProcurementOutcome`, не в очереди).
2. Пользователи привыкли к явному «подтвердить пачку». Вариант: оставить режим черновика (draft) на клиенте и отправлять пачку одним запросом — UX сохраняется, серверная очередь не нужна.

### 6.2. Идентификация пользователя — самая «дорогая» часть системы
`Session.getActiveUser().getEmail()` **не отдаёт адрес чужого аккаунта** в исполнении по установленному `onEdit`-триггеру (документированное ограничение). Из-за этого:
- права проверяются дважды: при захвате (если личность известна — откат и уведомление) и при применении (от имени нажавшего);
- намерения без автора **применяются только интерактивно** и проверяются по роли применяющего — иначе владелец скрипта коммитил бы чужие правки;
- e-mail можно указать вручную («🔑 Мой доступ»), он хранится в свойствах пользователя **и** в общем реестре скрипта по анонимному ключу `Session.getTemporaryActiveUserKey()` (TTL 30 дней, потому что ключ ротуется).

**Этот слой целиком исчезает при переходе на нормальную аутентификацию** — и это главный аргумент в пользу переписывания.

### 6.3. Склад не влияет на доступность
`availableForProduction = reservedQty + realDeliveryQty`. `MATERIAL_STATE.warehouseQty` — **контрольная книга**, а не источник доступности. Поэтому состав строк «Сводки» и «ОТБОРКИ» от складского остатка **не зависит** (и `v12HandleMaterialStateEdit` сознательно НЕ пересобирает проекции — раньше это стирало чужие неприменённые галочки).
Асимметрия, которую надо сохранить: **склад меняется дельтами** операций (реальная поставка `+delta`, передача `−required`, возврат `+returnedQty`), но при этом сам расчёт доступности от склада не зависит.

### 6.4. «Реальная поставка» и «Выполнено» работают только «вверх»
- Галочка «Реальная поставка» (`v12ApplyRealDeliveryIntent`) ставит `realDeliveryQty = required`. Снятие галочки **ничего не отменяет** — защита от случайного стирания реального прихода; корректировка возможна только через администратора (или, в текущем коде, через `v12SetRealDeliveryQty` с явным количеством, что из UI недоступно).
- «Выполнено» доступно только при статусе BOM `Скомплектован, готов к работе`; после применения BOM уходит в `EXCLUDED_BOMS` и строки в дашборде нет — отмена только отдельным пунктом меню.
- Отменить передачу можно **только** `v12ReturnFromArchive` (с обязательной причиной).

### 6.5. `BOM ID` = имя файла
`v12UpsertSourceBOM` ищет запись в `BOM_REGISTRY` **по имени BOM**. Переименование файла в Drive = **новый BOM** (новая позиция, потеря истории по старому id). `positionId` встроен во все ссылки (очередь, лоты, архив), поэтому переименование источника — самое разрушительное действие в системе. В регламенте это указано как «без необходимости не переименовывать».

### 6.6. Проекции уничтожаются целиком
`v12ClearBody` → `clearRange` очищает значения **и сбрасывает заливку в белый** (иначе «хвосты» цветов от прошлых строк), но **не сбрасывает data-validation** — этим управляет владелец колонки (`v12Install*Checkboxes`, `v12InstallPickingBomFilter`). Раньше `clearDataValidations` вызывался на каждом пересчёте и терял чекбоксы.
Ещё тонкость: `v12EnsureTableFilter` **не пересоздаёт автофильтр**, если он уже покрывает нужный диапазон — иначе пользовательская сортировка/фильтр сбрасывались бы на каждом пересчёте. Индикатор «Неприменённых изменений: N» пишется в **строку 1** (пересборка трогает только строки 2+).

### 6.7. Идемпотентность и «канал без потерь» — сквозные инварианты
- «галочка стоит ⇒ позиция будет передана» (реконсиляция по фактическим галочкам);
- повторная передача → `already` (без ошибки, но с пометкой отборщику);
- повторная отправка лота → прежний результат;
- при занятом локе намерение всё равно записывается (`appendRow`), а не теряется;
- возврат из архива возвращает количество на склад ровно один раз.

### 6.8. Производительность: где сломается на объёмах
- Проекции пересобираются **целиком** при каждом «ПРИМЕНИТЬ» (5 листов, полная clear+write). На десятках тысяч позиций это упрётся в лимит исполнения.
- Именно поэтому: синхронизация перенесена с «каждый час» на **03:00** (полный синк держит лок и мешает работе днём), а лоты дренируются пакетом раз в 5 минут, а не по одному.
- Оптимизации, которые уже сделаны (и которые надо сохранить как требования): индексы `Map` (positionIndex, positionsByBom, materialIndex, historyIndex), чтение `POSITION_STATE` **один раз** на пересчёт и раздача проекциям, `BOM_REVISION`/`EXCLUDED_BOMS` — один раз на пересчёт, буферы логов и аудита, один `operationId` на пачку, `batchWriteBlock` для плотных пачек, ленивая генерация UUID.

### 6.9. Странности, которые надо знать
- Кнопка «ПРИМЕНИТЬ» — **картинка** (base64 PNG в коде), а не UI-элемент; на веб это не нужно.
- `v12Install` создаёт кнопку и **мягкую** защиту листа ОТБОРКА (`setWarningOnly`), потому что жёсткая защита сломала бы пересборку проекций тем же скриптом.
- Миграции схем (`v12MigratePickingSchema`, `…SupplySchema`, `…DashboardSchema`, `…CanonicalHeaders`, `v12ClearPhantomValidations`) — живут в `v12_sheet_service.js` и нужны только на Sheets.
- `v12RevertEdit` **не может** откатить правку диапазона (у `onEdit` нет `oldValue`) — такой случай только логируется. На веб-форме проблема исчезает.
- Тесты — Node-скрипты с моками; проверка синтаксиса `node --check`. Юнит-тесты **домена** переносятся в новый стек почти без изменений (что даёт бесплатную страховку рефакторинга).
- `appsscript.json` мастера содержит `"webapp": { "executeAs": "USER_DEPLOYING", "access": "MYSELF" }`, хотя README требует доступа «любой пользователь Google» — при переносе это просто перестаёт иметь значение.

## 9. Предложение по рефакторингу: варианты реализации

### 9.0. Что сохраняем (инварианты бизнес-логики)

Переписывание не должно изменить ни одно из этого:

1. **Потребность и резерв** приходят только из BOM источника (резерв — «уже закрыто», не перемещается автоматически).
2. Формулы: `deficit = max(0, required − reserved)`, `uncovered = max(0, deficit − ordered)`, `overOrdered = max(0, ordered − deficit)`, `shortDelivery = max(0, ordered − realDelivery)`, `available = reserved + realDelivery`, `readyForHandoff = valid ∧ ¬received ∧ available ≥ required ∧ required > 0`.
3. Порядок ветвлений `supplyState` и `productionState` и приоритет статусов BOM — как в `v12_calculate.js` / `v12ComputeBomStatus`.
4. **Валидация ТЗ №8** (№ п/п, Наименование, Модель, Ед.изм, Кол-во > 0, Крайний срок; Артикул необязателен) и статус «Ошибка данных», блокирующий передачу.
5. Заказ оформлен только при **обоих** полях: количество И ожидаемая дата.
6. Передача производству **идемпотентна**, требует валидности и полной доступности; списывает склад на `required`; возврат — только по причине и с возвратом на склад.
7. «Реальная поставка» и «Выполнено» — только «вверх».
8. Матрица прав по ролям (ADMIN/ECONOMIST/PROCUREMENT/WAREHOUSE/PRODUCTION/VIEWER) и состав «своих» полей у каждой роли.
9. `positionId` и `materialKey` как стабильные ключи (с теми же правилами построения).
10. Код проекта = часть имени BOM до первого пробела/дефиса/подчёркивания (фильтр ОТБОРКИ, колонка «Проекты»).

### 9.1. Три варианта платформы

#### Вариант A — классическое веб-приложение + реляционная БД (**рекомендуется**)
- Backend: **Node.js + TypeScript** (Fastify/NestJS) или **Python + FastAPI**; PostgreSQL; миграции (Prisma/Knex/Alembic).
- Frontend: **React/Vue SPA** (или SSR) с роль-ориентированными «рабочими местами»: `/economist`, `/procurement`, `/warehouse`, `/production`, `/admin`.
- Ядро расчёта переносится **дословно** (чистые функции) + юнит-тесты из `_local_tests` — низкий риск регрессий.
- Аутентификация: сессии/JWT в httpOnly cookie, `argon2/bcrypt`, роли в БД, админка для доступов.
- Плюсы: снимается **всё**, ради чего написан каркас (очередь, сателлиты, токен, анонимные ключи, лимит 6 минут, ночная синхронизация); реальная параллельная работа; нормальные отчёты и поиск; тестируемость; масштабирование; импорт/экспорт Excel.
- Минусы: нужен сервер (VPS/on-prem) и сопровождение; требуется обеспечить ввод BOM (см. 9.2).
- Трудоёмкость: средняя (домен уже декомпозирован, тесты есть).

#### Вариант B — «веб-обёртка» над Google Sheets (без смены БД)
- Backend остаётся Apps Script: `doGet` отдаёт HTML Service / или статический SPA, общается через `doPost`.
- Плюсы: минимум работы, нет сервера, данные остаются в Drive.
- Минусы: **медленные базы spreadsheet не убираются** — это прямо противоречит цели задачи. Проблема `onEdit`-личности, лимитов исполнения и пересборки проекций сохраняется. Подходит только как временный шаг.

#### Вариант C — low-code / платформа (AppSheet, Битрикс24, 1С:УНФ, Retool и т.п.)
- Плюсы: быстрый старт, готовая админка и авторизация.
- Минусы: лицензии и вендор-лок; формулы придётся переписывать под ограничения платформы; слабый контроль над идемпотентностью и транзакциями; риск, что сложные правила (например, `readyForHandoff` с валидацией) придётся «размазывать» по представлениям.

**Рекомендация: Вариант A**, возможно с первым шагом как «пилот на одном участке» (например, только ОТБОРКА) для проверки UX.

### 9.2. Сущность BOM: как заполнять новые спецификации

Три варианта:

**(1) Импорт из Excel/CSV (минимальные изменения для экономиста).**
- Загрузка файла в веб-приложение → тот же парсер, что в `v12ParseSourceRows` (алиасы заголовков уже покрыты: `№ п/п|Строка|№`, `Артикул|Код`, `Кол-во|Требуется|QTY`, `Крайний срок|Срок|DEADLINE`, `Производитель`).
- На экране импорта — предпросмотр и подсветка невалидных строк (замена статуса «Ошибка данных», который сейчас выясняется уже после синхронизации).
- Плюсы: экономисты сохраняют привычный инструмент; риск минимален; быстрый старт.
- Минусы: два источника правды для «заготовки» BOM; нет онлайн-редактирования.

**(2) Полноценная сущность BOM в БД с веб-редактором.**
- `bom` + `bom_position` как доменные таблицы; редактор строк с inline-валидацией, копирование BOM, версии/ревизии с diff.
- Плюсы: единый источник правды; мгновенная валидация на вводе; история изменений и откат ревизий; никакой зависимости от Drive.
- Минусы: нужно написать редактор (по объёму — отдельный небольшой продукт); экономисты переучиваются.

**(3) Гибрид — сущность в БД как источник правды + импорт/экспорт Excel (рекомендуется).**
- BOM живёт в БД как сущность; Excel/CSV — **канал наполнения** (импорт) и **канал выгрузки** (экспорт, печать, согласование).
- Ревизии: загрузка новой версии создаёт `revision`, применяется тот же интеллектуальный diff, что уже реализован в `v12_change_engine.js` (`POSITION_ADDED/DELETED/QUANTITY/RESERVE/DEADLINE/MATERIAL`). Сохранение операционных данных (заказ/поставка/передача) при изменении ревизии — уже решённая задача: текущий код обновляет поля существующих позиций и **не сбрасывает** операционные значения — это надо воспроизвести ровно так же.
- Веб-редактор добавляется вторым этапом — для правок и мелких BOM.

**Рекомендация — вариант (3)**: на старте импорт из Excel (привычный процесс экономистов не ломается), BOM уже в БД; редактор — следующая итерация.

### 9.3. Эскиз модели данных (PostgreSQL)

```
users(id, email UNIQUE, full_name, role, password_hash NULL, is_active, created_at)
roles/permissions        -- достаточно enum роли + таблица permissions(role, action)
sessions(id, user_id, token_hash, expires_at)  -- или JWT + refresh

material(id, material_key UNIQUE, code, manufacturer, name, model, unit, warehouse_qty, updated_at)
bom(id, code, name, status, is_done, source_revision, created_at, deadline, created_by)
bom_position(id, bom_id FK, position_id UNIQUE, row_no,
             material_id FK, material_code, manufacturer, material_name, model, unit,
             required_qty, reserved_qty,                     -- из BOM
             ordered_qty, expected_date,                     -- снабженец
             real_delivery_qty, real_delivery_date,          -- экономист
             deadline, received_qty, received_at, received_by,
             lifecycle, validation, updated_at, version)     -- version = optimistic lock
-- производные (deficit, uncovered, over_ordered, short_delivery, available,
--  supply_state, production_state, flags) — ВЫЧИСЛЯЕМЫ в домене;
--  при необходимости материализуются (generated columns / materialized view)
bom_revision(id, bom_id, revision, created_at, created_by, payload_hash)
archive(id, position_id, bom_id, received_qty, received_at, received_by, source_ui, history JSONB)
audit_log(id, operation_id, actor_id, action, bom_id, position_id, field, old_value, new_value, reason, data JSONB, created_at)
event_log(id, event_id, event_type, position_id, bom_id, actor_id, data JSONB, created_at)
```

Что **не нужно** воспроизводить: `PENDING_EDITS`, `PICKING_BATCHES`, `PICKING_CLAIMS` (в новом стеке вместо лота — обычный HTTP-запрос в транзакции; вместо «мягкого захвата» — блокировка строки `SELECT … FOR UPDATE` или advisory lock на проект, либо оптимистическая блокировка по `version`), `SYSTEM_LOG` (заменяется структурным логированием приложения), «индикатор неприменённых изменений».

### 9.4. Аутентификация и админка

- **Вариант 1 (если есть Google Workspace)** — OAuth/SSO по Google-аккаунтам: адреса из `V12_ROLE_MAP` переносятся один-в-один; пароли не нужны.
- **Вариант 2 (рекомендуется по умолчанию)** — локальные логины: админ создаёт пользователя, выдаёт временный пароль; хранение `argon2id`; сессии в httpOnly-cookie; сброс пароля админом.
- **Админка**: CRUD пользователей, назначение роли, включение/выключение доступа, просмотр аудита и журналов, управление справочником материалов и склада, повторное применение/откат передачи (то, что сейчас делается «Вернуть из архива» и «снять Выполнено»).
- **Ролевые рабочие места** = отдельные маршруты/меню по роли, а не общий лист с защитой колонок. Права проверяются **на сервере** по каждому действию (аналог `v12CanEditField`, но по-настоящему доверенно), а не «в момент применения» — необходимость в двойной проверке исчезает вместе с `onEdit`.

### 9.5. Что делать с «ПРИМЕНИТЬ» (решение, которое надо принять осознанно)

| Подход | Плюсы | Минусы |
|---|---|---|
| **Немедленное применение** (каждая правка = транзакция + аудит) | проще всего, нет очереди, нет «забыл нажать» | терпит частичный ввод (снабженец ввёл количество, но не дату — строка остаётся «Не заказано», что уже и так корректно по логике) |
| **Клиентский черновик + «Сохранить»** (массовая отправка) | сохраняет привычку и позволяет валидировать пачку целиком | чуть сложнее UI; нужен черновик на сервере/у клиента |
| **Серверная очередь (как сейчас)** | максимальная совместимость поведения | переносить в БД нет смысла — это лечение симптома Sheets |

Рекомендация: **немедленное применение + явная валидация на форме** (обе величины заказа, дата ≤/≥ срока и т.д.), с журналом, из которого любое действие можно откатить.

### 9.6. Ввод BOM и совместимость с существующими файлами

- Забрать из текущей схемы: `DRIVE.FOLDER_ID` → разовый импорт всех существующих BOM (миграция не нужна, но данные пригодятся для выверки).
- Сохранить формат заголовков и алиасы, чтобы старые файлы импортировались без правок.
- Сохранить правило «имя файла/BOM = код+название» как **поле**, а не как внешний идентификатор: в БД `bom.id` — суррогатный ключ, поэтому переименование больше не разрушает связи (сейчас это самая опасная связь в системе).

### 9.7. Этапы внедрения (предлагаемая последовательность)

1. **Каркас**: репозиторий, стек, БД, миграции, аутентификация, админка (пользователи+роли), CI.
2. **Ядро домена**: перенос `v12_calculate.js` + `v12_utils.js` (materialKey/positionId/валидация/даты) + тесты из `_local_tests` — «зелёный» прогон как критерий готовности.
3. **Справочники и материалы**: `material` + `bom` + `bom_position`; импорт BOM из Excel/CSV с предпросмотром и валидацией; ревизии и diff (по логике `v12_change_engine.js`).
4. **Рабочее место снабженца** (`DEFICIT_SUMMARY` + `SUPPLY`): таблица дефицитов, ввод заказа/ожидаемой даты, статусы и цвета из конфига, фильтры, экспорт.
5. **Рабочее место кладовщика** (`MATERIAL_STATE` + `ОТБОРКА` + передача): склад, список отборки по проекту, передача (идемпотентная), возврат из архива.
6. **Рабочее место производства** (`WORKING BOM` + `Dashboard` + «Выполнено»): агрегаты по BOM, статусы, отметка выполнения с гейтом, отмена.
7. **Аудит/журналы/отчёты**: выгрузки, печать, история по позиции (сейчас — JSON-история внутри строки архива).
8. **Параллелизм**: оптимистические блокировки/`FOR UPDATE`, отсутствие «захватов» как отдельной сущности.
9. **Рабочее место экономиста + веб-редактор BOM** (второй этап, если выбран гибрид 9.2(3)).
10. **Резервное копирование, деплой, регламенты** (`REGULATIONS.md` переписать под веб: раздел «Отборка в личном файле» станет ненужным, раздел про `PENDING_EDITS` и «откат галочки» — тоже).

### 9.8. Риски и на что обратить внимание

- **Потеря неочевидных правил.** Наивысший риск — не арифметика, а «мелочи»: приоритет ветвлений `supplyState`, «заказ только при обеих величинах», «только вверх», гейт «Выполнено» только при «Готов к работе», сохранение операционных данных при обновлении ревизии BOM. Их нужно зафиксировать тестами-переносом до написания UI.
- **Ключи.** `positionId` уже используется как стабильный ключ — при импорте в БД его стоит сохранить (или сделать вычисляемым детерминированно из `bom_id + material_key`), иначе историю и архив связать не удастся.
- **Дубли и `#2`, `#3`** в `positionId` при повторяющихся материалах внутри одного BOM — правило генерации надо перенести дословно.
- **Хостинг.** Заводской контур, скорее всего, on-prem/VPS: PostgreSQL + контейнеры (API + reverse-proxy + статика). Нужно решить вопрос резервного копирования и внешнего доступа.
- **Данные пользователей.** Текущая «аутентификация» фактически отсутствует (роль по e-mail из карты в коде; все — ADMIN при пустой карте). В новой системе это надо закрыть: реальная аутентификация, отключение неактивных, парольная политика.
- **Период параллельной работы.** Если решено работать «в оба контура» какое-то время, потребуется экспорт/импорт между ними; дешевле — одномоментный переход, поскольку система **ещё не эксплуатируется** (можно загрузить только справочники и BOM).
