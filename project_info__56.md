# Дефект захвата (38 → 30): почему часть галочек НЕ попадает в PENDING_EDITS — v2

> Пользователь: «Из 38 отметок в pending попало только 30 позиций — проблема сохраняется». Предыдущие Fix 1–4 (лок, upsert, реконсиляция, один Edit ID) внесены и проходят тесты, но на реальных 38 быстрых отметках теряется 8. Ниже — уточнённый разбор: **корень в том, что захват доверяет числу событий `onEdit`, а Google не гарантирует событие на каждый быстрый клик.**

## Что подтвердилось про лок (не причина номер один)
`lock.js`: `acquireScriptLock({ tryOnly: true, timeoutMs: 10000 })` вызывается как `LockService.getScriptLock().tryLock(10000)` —
- при быстрой отметке лок берётся/отпускается за доли секунды, очередь ожиданий не растёт → потери из-за лока нет;
- **но** если в момент отметки идёт долгое «Применить изменения»/полный синк (>10 c), `tryLock(10000)` вернёт `false`, и `v12EnqueuePendingRows` **отбрасывает намерение** (логирует WARNING). Это отдельный, более редкий сценарий потери — но он есть.

Вывод: 8 потерянных из 38 при быстрых кликах — это **потерянные события `onEdit`**, а не перезапись строк.

## Истинная причина: захват зависит от числа событий, а события «не доезжают»
Сейчас `v12CaptureCheckboxEdit` фиксирует намерения **по данным события** (`e.range` + `e.values`/`e.value`):
- один клик по чекбоксу = одно событие `onEdit`;
- при быстрой отметке многих чекбоксов Apps Script **не гарантирует вызов `onEdit` на каждую правку** — часть событий «проглатывается» (особенно при кликах подряд, пока предыдущий обработчик ещё выполнялся, и при мульти-выделении через Ctrl, где `e.range` может отражать лишь один из диапазонов);
- каждая обработка делает несколько RPC (`readSheetValues(PENDING_EDITS)` под локом, запись, индикатор). Чем дольше обработчик, тем больше событий теряется.

Итог: сколько событий «доехало» — столько и строк. Отсюда 38 → 30.

## Ключевая идея исправления: сделать захват САМОВОССТАНАВЛИВАЮЩИМСЯ (сканирующим)
Захват не должен зависеть от того, сколько событий пришло. Вместо разбора только `e.values` — при любой правке чекбокс-колонки **просканировать саму колонку** и зафиксировать (upsert) намерения по фактическому состоянию галочек.

### Предлагаемый `v12CaptureHandoffByScan` (для ОТБОРКИ и WORKING BOM)
Алгоритм (на каждую правку, затрагивающую чекбокс-колонку):
1. Прочитать ОДНИМ `getValues` сразу колонки `Position ID` (1) и `CHECKBOX` (12/14) на всю высоту листа.
2. Для каждой строки с непустым `Position ID` и **установленной** галочкой — upsert намерения `HANDOFF=true` (существующая логика upsert по ключу `SOURCE|POSITION_ID|FIELD`).
3. Для строк, которые событие явно **сняло** (`e.value/e.values` = false в затрагиваемых ячейках) — upsert `HANDOFF=false` (отмена), как сейчас.

Свойства:
- **Идемпотентность и самовосстановление:** даже если 7 из 38 событий потеряны, любое следующее доехавшее событие повторно просканирует лист и доберёт все стоящие галочки — в очереди окажутся все 38 (последний скан видит полное состояние).
- **Устойчивость к мульти-выделению (Ctrl):** не важно, какой `e.range` пришёл — скан читает лист целиком.
- **Дёшево:** один `getValues` пары колонок на правку (несколько сотен строк), вместо доверия к форме события.
- **Совместимость:** для Сводки (`v12CaptureDeficitEdit`) остаётся прежняя логика (там типизированные поля — сканировать нечего).

Риск, который скан НЕ закрывает: если потеряно САМОЕ ПОСЛЕДНЕЕ событие, последняя галочка не попадёт ни в один скан. Именно на этот случай остаётся **Fix 3 (реконсиляция при Apply)** — она доберёт оставшиеся галочки на этапе применения. Вместе скан + реконсиляция дают инвариант «галочка стоит ⇒ намерение будет учтено».

## Дополнительно устранить (вторичные источники потери)
1. **Отбрасывание при занятом локе.** В `v12EnqueuePendingRows` при `tryLock=false` намерение теряется. Варианты:
   - сделать запись очереди **без лок-зависимого дропа**: при неудаче один короткий ретрай, а при повторной неудаче — не отбрасывать, а писать по принципу «прочитать getLastRow и записать» (риск гонки мал по сравнению с полной потерей) — либо
   - уменьшить время удержания лока (вынести `readSheetValues` из-под лока — см. п.2).
2. **Убрать чтение всей очереди под локом.** В upsert мы читаем `PENDING_EDITS` под локом — это удлиняет удержание. Можно читать очередь ДО лока, а под локом только писать (аппендить/обновлять), приняв редкий риск, либо кэшировать индекс ключей.
3. **`v12UpdatePendingIndicator()`** читает лист — можно вызывать вне лок-секции (уже так, но лишний RPC на каждую правку; при скане можно обновлять реже).

## Почему прошлые фиксы не закрыли проблему
- Fix 1 (лок) — устранил перезапись строк, но не потерю событий.
- Fix 2 (upsert) — устранил дубли «off+on», но если события нет — upsert нечего обновлять.
- Fix 3 (реконсиляция при Apply) — закрывает потерю, но **только в момент нажатия «Применить»**; в самом листе `PENDING_EDITS` до применения видно 30, а не 38 — что и наблюдает пользователь.
- Fix 4 (один Edit ID) — ускорил захват, снизил окно, но не устранил природу.

## Рекомендуемый минимальный набор (v2)
1. **Сканирующий захват** `v12CaptureHandoffByScan` для ОТБОРКИ и WORKING BOM (самовосстановление — главный фикс).
2. **Fix 3 (реконсиляция при Apply)** оставить как страховку для «потерянного последнего события».
3. **Убрать дроп при занятом локе** (ретрай/без дропа) и вынести чтение очереди из-под лока.
4. (опц.) Явный **автопересбор очереди по кнопке/триггеру** — тот же скан, доступный как отдельное действие «пересобрать намерения из галочек».

## Как проверить
- Локальный тест: разметить 38 чекбоксов в ОТБОРКЕ, смоделировать, что «доехало» только ~30 событий `onEdit` (вызвать `v12OnEdit` для 30 из 38 строк), затем — что при одном следующем событии (или при Apply) в очереди оказываются все 38 (скан доберёт недостающие). Проверить идемпотентность (повторный скан не плодит дубли благодаря upsert).

# РЕАЛИЗОВАНО (сканирующий захват)

## Изменение в `v12_queue.js` — `v12CaptureCheckboxEdit`
Захват для ОТБОРКИ (`CHECKBOX`=12) и WORKING BOM (`CHECKBOX`=14) переведён на **сканирующий** режим:
1. Значения **редактируемых** событием строк берутся из события (`e.value`/`e.values`) — как раньше.
2. Вся колонка `Position ID` + `CHECKBOX` читается ОДНИМ `getValues` (`getRange(2, 1, lastRow-1, column)`).
3. Для строк, которых НЕ было в событии, берётся **фактическое состояние листа**: если галочка стоит — фиксируется намерение `HANDOFF=true`.

Итог: захват **самовосстанавливающийся**. Даже если Google не прислал `onEdit` на часть быстрых кликов (38 отметок → 30 событий), ЛЮБАЯ следующая правка просканирует лист и доберёт все стоящие галочки. Upsert по ключу `SOURCE|POSITION_ID|FIELD` не плодит дубли — повторный скан идемпотентен. Роль-проверка и обработка Сводки (`v12CaptureDeficitEdit`) не изменены.

## Почему это закрывает «38 → 30»
- Раньше число строк очереди равнялось числу **доехавших событий** — отсюда потеря при быстрых кликах.
- Теперь число строк очереди равно числу **фактически отмеченных галочек** (последний успешный скан видит полное состояние листа).
- Страховка на «потерянное последнее событие» остаётся: **реконсиляция при Apply** (`v12ReconcileCheckedHandoffs`) доберёт галочки, если скан ни разу не отработал после последней отметки.

## Верификация
Новый тест **`_local_tests/v12_queue_capture_fix_test.js`** (F1–F11) — все PASS, ключевые для этого дефекта:
- **F10**: 5 галочек стоят в листе, но `onEdit` «доехал» только для 2 строк → в очереди оказываются **все 5** (скан добрал потерянные 3);
- **F11**: повторный скан не плодит дубли (5 строк — 5 живых намерений);
- F1–F9: upsert, off→on, разные ключи, DONE не воскрешается, безопасный отказ при занятом локе, реконсиляция при Apply — как ранее.

Полный прогон `_tmp_run.js`: **`node --check` — 22 файла, 0 ошибок; 12/12 тестов PASS, 0 fails.**

## Остаточные ограничения (осознанные)
- Скан читает всю таблицу на каждую правку чекбокса — на листах в тысячи строк это один `getValues`, приемлемо.
- Снятие галочки фиксируется только для строк из события (для остальных строк сканируется только факт «стоит»). Если событие отмены потеряно, отмена не восстановится — это защита «передача только вверх» уже заложена в применении.
