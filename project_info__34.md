## 1. Быстродействие

**P-1 🔴** `v12BuildRevisionDateMap()` вызывается **дважды** за полный пересчёт — в `v12RefreshPicking` и в `v12RefreshDashboard` (по одному полному чтению `BOM_REVISION` каждое). `v12BuildExcludedMap()` читает `EXCLUDED_BOMS` внутри Dashboard. → строить `revDates`/`excluded` один раз в `v12RefreshProjections` и передавать параметром (как `posData`).

**P-2 🔴** Одна правка `onEdit` в Сводке читает `POSITION_STATE` **4–5 раз**: `v12BuildPositionIndex` в `v12SetOrderedQty`/`v12SetExpectedDate`; повторно в `v12HarvestDeficitInput`; ещё раз в `v12ReadSheet` внутри `v12RefreshDeficitSummaryRow`; плюс `v12RefreshSupply()` и `v12RefreshDashboard()` (каждый — полное чтение + полная перезапись своего листа). Путь «Реальная поставка»: `v12GetDeficitRequiredQty` (индекс #1) + `v12SetRealDeliveryQty` (индекс #2) + `v12RefreshProjections` → harvest (индекс #3). → строить индекс один раз в `v12HandleDeficitEdit` и прокидывать вниз; передавать `posData` в агрегаты.

**P-3 🔴** Пакетная передача (ОТБОРКА, диапазон) — **O(N) полных чтений**: `v12HandlePickingRangeEdit` для каждой строки вызывает `v12MarkReceivedByProduction`, внутри — `v12BuildPositionIndex()` (полное чтение `POSITION_STATE`) и `v12AdjustWarehouseQty → v12BuildMaterialIndex()` (полное чтение `MATERIAL_STATE`). ~2·N чтений на операцию → риск лимита 6 мин / окна триггера. → передавать общий `index` и Material-кэш, строить индексы один раз.

**P-4 🟠** `v12GetPositionsByBom(bomId, index)` линейно фильтрует **весь** индекс позиций на каждый BOM → O(BOMs × positions) в полном синке. → сгруппировать позиции по `BOM_ID` заранее.

**P-5 🟠** `v12ApplySourceRevision` вызывает `v12UpdatePosition` по одной позиции (`batchWrite` на строку) → сотни `setValues` при большом diff. → агрегировать в один батч на ChangeSet.

**P-6 🟠** `v12HandleDeficitRangeEdit` читает Position ID по одной ячейке в цикле (N одиночных чтений). → читать колонку одним `getValues()`.

**P-7 🟡** Harvest (`v12HarvestDeficitInput`, `v12HarvestPickingInput`) строит собственный индекс `POSITION_STATE` ещё до проекций → «одно чтение» из отчёта №31 верно только для самих проекций.

**P-8 🟡** Множественные `SpreadsheetApp.flush()` на одну правку — дорого; число вызовов можно сократить (один flush перед «опасным» чтением).

**P-9 🟡** Гвард `v12ApplyDashboardColors` в реальности почти не срабатывает: `_v12ProjectionUiState` — модуль-глобал, а Apps Script **не сохраняет глобалы между запусками**. Гвард безопасен, но его польза переоценена (та же механика ранее и создала P7).

## 2. Конфликты и гонки

**C-1 🔴** `clearRange` уничтожает **все** data-validation тела листа; восстанавливаются только чекбокс-колонки проекций и фильтр B1 ОТБОРКИ → любая другая валидация стирается молча при каждом пересчёте. → убрать `clearDataValidations()` из `clearRange` или вести явный список поддерживаемых валидаций.

**C-2 🔴** Часовая `v12ScheduledUpdate` держит ScriptLock на весь `v12RunFullSync`; `waitLock(30000)`. Если синк > 30 с — параллельная правка не берёт лок, `waitLock` бросает, `v12OnEdit` ловит → **правка не применяется** (может спасти только harvest). → `tryLock` + уведомление; короче синк.

**C-3 🟠** Реентрантность лока на модуль-глобалах `_lockDepth`/`_heldLock` — корректна в одном исполнении, но хрупка.

**C-4 🟠** `v12RevertEdit` не откатывает диапазон (`e.oldValue` отсутствует → no-op молча).

**C-5 🟠** Несогласованный источник значения: `v12HandleDeficitEdit` берёт снимок `e.value`, `v12HandlePickingEdit` — живое `e.range.getValue()`.

**C-6 🟠** Ручная правка `WAREHOUSE_QTY` пересчитывает проекции, но не вызывает `v12RecalculateWarehouseConsistency()` → контрольные `RESERVED_QTY`/`FREE_QTY` в MATERIAL_STATE устаревают до синка.

**C-7 🟠** `v12HandleDeficitRangeEdit` **безусловно** вызывает `v12RefreshProjections()` даже без изменений.

**C-8 🟡** Двойного начисления склада по «реальной поставке» нет — harvest начисляет только при `currentReal < required`. Механизм согласован.

## 3. Бизнес-логика

**B-1 🔴** Статус Dashboard **«Ожидание поставки (опаздывает)» недостижим**: `v12AggregateBomStates` объявляет `late: 0`, но нигде не инкрементирует его; ветка `agg.late > 0` в `v12ComputeBomStatus` — мертва. `minDeadline` считается, но для «опаздывает» не используется. → вычислять `late` по `expectedDate > deadline`.

**B-2 🟠** Чекбокс ОТБОРКИ работает **только в одну сторону** (действие при `checked`; снятие галочки — ничего). Успешная передача **архивирует** позицию и вычитает склад → случайная отметка необратима из листа (только через меню «↩ Вернуть из архива»).

**B-3 🟠** Валидация по ТЗ №8 требует «Крайний срок» → позиция с пришедшим материалом, но без срока, **не может быть передана** производству (гейт по валидности), пока срок не проставят.

**B-4 🟠** При передаче склад уменьшается на `required` независимо от источника покрытия (даже если покрытие — резерв BOM), с клампом до 0 → возможное занижение/обнуление.

**B-5 🟠** Чекбокс Сводки «Реальная поставка» фиксирует **полную** потребность (`required`), а не фактически принятое количество → частичные поставки через Сводку невозможны.

**B-6 🟡** Harvest реальной поставки работает только «вверх» — снятая в листе галочка при пропущенном `onEdit` не понизит уже сохранённую поставку.

**B-7 🟡** «Мёртвые» листы: `EVENT_LOG` и `MATERIAL_HISTORY` нигде не пишутся (проверено по всем файлам). `MATERIAL_HISTORY` только читается (`v12GetPositionHistory`) → колонка «История» в ARCHIVE **всегда пуста**.

**B-8 🟡** `v12GetWarehouseQty` — **мёртвая** функция (вызовов нет).

**B-9 🟡** `v12ConsistencyCheck` выдаёт ложные «ошибки» для BOM из реестра без позиций.

**B-10 🟡** СНАБЖЕНИЕ/Dashboard обновляются «по половине пары»: только когда заданы и «Заказано», и «Ожидаемая поставка».

**B-11 🟡** RBAC «из коробки» выключен: при пустом `V12_ROLE_MAP` все — ADMIN. Как только карта заполнена, пользователь вне карты получает роль `""` и теряет доступ ко всем действиям — заполняйте карту полностью.

**B-12 🟡** `toNumber` заменяет только **первую** запятую на точку → «1,234.56» парсится как 1.234 (важно при импорте).

## 5. Слепые зоны тестов
`_local_tests/*` используют моки, где `clearDataValidations()`/`setDataValidation()` — пустышки. Поэтому тесты проверяют **значения**, но не наличие чекбокс-валидаций (именно так была пропущена регрессия P7), не моделируют блокировки/тайм-ауты/лимиты исполнения и не покрывают статусы Dashboard (B-1). → добавить в моки счётчики валидаций и тест «два пересчёта при неизменном числе строк → валидации восстановлены».

## 6. Ручная проверка в Apps Script
`clasp push` → `v12Install` → `v12RunFullSync` → `v12RunDebug` → `v12ConsistencyCheck`. Сценарии: (1) два полных пересчёта подряд — чекбоксы остаются рабочими; (2) BOM с просроченным приходом — статус «опаздывает» (сейчас недостижим); (3) массовая отметка ОТБОРКИ на большом диапазоне — замер времени; (4) отметка во время/после часового синка — правка применилась.
