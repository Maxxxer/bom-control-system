# BOM CONTROL SYSTEM V12 — Почему в ОТБОРКЕ не все позиции «На складе» уходят после «ПРИМЕНИТЬ»

> Отчёт сохранён в `project_info__51.md`. Режим Explore — только чтение; изменения не вносились.

## Краткий ответ (TL;DR)

- **«Сброс чекбокса» — это штатное поведение, а не сбой.** `v12RefreshPicking` при каждой пересборке **всегда** записывает в колонку чекбокса (12) значение `false`. «Отметка получено» — это лишь триггер, реальное состояние живёт в очереди `PENDING_EDITS` и в `POSITION_STATE`.
- **Позиция остаётся «На складе» потому, что её передача не применилась.** Статус «На складе» — это `PRODUCTION_STATE === READY_FOR_HANDOFF`, который выставляется **ровно теми же двумя условиями**, что проверяет гейт передачи (`v12MarkReceivedByProduction`): `validation === VALID` и `availableForProduction >= required`. Значит, по-настоящему готовая строка гейт пройти обязана — и «застрять» она может лишь в двух случаях:
  - **(A)** её намерение вообще не попало в очередь (не зафиксировано при клике — напр., пустой `Position ID`), **или**
  - **(B)** намерение разрешилось **не в ту физическую строку** `POSITION_STATE` → это происходит при **дубликате `Position ID`**.
- **Наиболее вероятная первопричина — дубликаты строк `POSITION_STATE` с одинаковым `Position ID`.** При повторном «Применить» система всегда бьёт в уже архивированную строку-дубликат и возвращает `already` — поэтому видимая строка не уходит **никогда**.
- **Точную причину конкретной строки система сама пишет**: колонка **`Ошибка`** в `PENDING_EDITS`, тост «не применено: N», `SYSTEM_LOG`, а системно — меню **«🧩 Проверка консистентности»** (ищет дубликаты `positionId`).

## 1. Как работает «Применить» (модель V3) — два разнесённых шага

1. **Клик по чекбоксу** → `onEdit` → `v12CaptureCheckboxEdit(e, "ОТБОРКА")` (`v12_queue.js`). Ничего не пересчитывается — только **фиксируется намерение** строкой в `PENDING_EDITS` (поле `HANDOFF`, `VALUE = true`, статус `PENDING`).
2. **Кнопка «ПРИМЕНИТЬ»** (`v12ApplyChangesUI → v12ApplyChanges → v12DrainPendingEdits`) — читает очередь, схлопывает намерения по **last-wins** (`SOURCE|POSITION_ID|FIELD`) и применяет пакетно, **один раз** пересобирая проекции. Для `HANDOFF` вызывается `v12MarkReceivedByProduction(pid, "PICKING", true, ctx)` (`v12_handoff.js`).

## 2. Почему чекбокс «сбрасывается» — это не баг

`v12RefreshPicking` (`v12_projections.js`) строит строку из `POSITION_STATE` и жёстко пишет `false` в колонку 12, затем заново навешивает check-box валидацию. После каждого «Применить» **все** галочки обнуляются, а успешно переданные строки исчезают (фильтр: `LIFECYCLE_STATE !== ACTIVE` → `continue`; `RECEIVED_BY_PRODUCTION` → `continue`). Непереданные строки возвращаются с пустой галочкой.

**Симптом «галочка сброшена, строка осталась» = «передача для этой строки не привела к архивации».**

## 3. Строгий гейт передачи (`v12_handoff.js`)

```js
if (received && RECEIVED_BY_PRODUCTION_QTY >= required) return { status: "already" };
if (validation !== V12_CONFIG.VALIDATION_STATUS.VALID)  return { status: "blocked", reason: "Позиция невалидна…" };
if (available < required)                               return { status: "blocked", reason: "Не хватает доступного количества…" };
// плюс: if (!pos) return { status: "blocked", reason: "Позиция не найдена" };
```
При `blocked` намерение помечается `FAILED` с текстом в `PENDING_EDITS` (колонка `Ошибка`).

## 4. Ключевой логический вывод

`READY_FOR_HANDOFF` (`v12_calculate.js`) ⟺ `valid && availableForProduction >= required && !received && required > 0`. Это **ровно** условия гейта. Колонки `VALIDATION_STATUS`/`PRODUCTION_STATE`/`AVAILABLE_FOR_PRODUCTION` в `POSITION_STATE` всегда пишутся **вместе** (`v12ApplyComputedToRow`). Поэтому строка, показанная в пересобранной ОТБОРКЕ как «На складе», **не может** быть отклонена гейтом «невалидна/не хватает количества» — если её производные колонки не рассогласованы (легаси-данные, §6.4).

## 5. Механизм (B): дубликат `Position ID` — главная системная причина

`v12BuildPositionIndex` (`v12_sheet_service.js`) делает `index.set(id, …)` — при дубликатах **остаётся только последняя строка**. Тогда:
1. Гейт всегда попадает в последнюю строку с этим id и **архивирует её** (одна из двух уходит).
2. Видимая первая строка-дубликат остаётся `ACTIVE` и «На складе» → **остаётся в листе с пустой галочкой**.
3. Повторное «Применить» снова попадает в уже архивированную → `already` (не ошибка) → **строка не уходит никогда**.

Косвенно это подтверждает сам код: `v12ConsistencyCheck` (`v12_controller.js`) прямо ищет `"Обнаружены дубликаты positionId"`, а в `project_info__9.md` отмечено, что суффиксы `#2/#3` «могут плыть».

**Как дубликаты появляются (Путь 1 — реальный дефект):** `v12RunFullSync` строит `positionsByBom` один раз на прогон, а `v12PersistNewPositions` обновляет **только `positionIndex`, но не `positionsByBom`**; при этом `v12GetPositionsByBom` **предпочитает устаревший `byBom`**. Если в папке Drive два файла с **одинаковым именем BOM** (реестр матчится по имени), второй проход увидит пустой `existing` → те же `positionId` **допишутся повторно** → дубликаты.

## 6. Прочие причины

- **6.1 Намерение не зафиксировано:** `v12CaptureCheckboxEdit` пропускает строку без `Position ID` (`if (!positionId) continue`) или если диапазон не задевает колонку 12 (тогда правка откатывается `v12RevertEdit`).
- **6.2 last-wins «отмена»:** для чекбоксных полей `VALUE=false` = отмена → интент пропускается в `v12DrainPendingEdits`.
- **6.3 Часовой синк (`v12ScheduledUpdate`)** пересобирает ОТБОРКУ и обнуляет галочки; намерения сохраняются, но визуально «слетают».
- **6.4 Устаревшие производные колонки `POSITION_STATE`** (легаси/сдвиг при миграции схемы): лист показывает «На складе», а гейт отклоняет. Признак: «Доступно для производства» < «Требуется», но статус «На складе».
- **6.5 Лок занят:** `v12DrainPendingEdits` берёт лок через `tryOnly` → при занятости возвращает `skipped` и **ничего не применяет** (обычно всю пачку).

## 7. Как подтвердить (диагностика)

1. `PENDING_EDITS` → колонки `Статус`/`Ошибка` — прямые причины `FAILED`.
2. Тост «Применено: X, не применено: Y».
3. `SYSTEM_LOG` — ошибки передачи.
4. Меню **«🧩 Проверка консистентности»** — «Обнаружены дубликаты positionId».
5. Ручной поиск в `POSITION_STATE` строк с одинаковым `Position ID` (колонка 1).
6. Сверка у застрявшей строки: `Валидация` / `ProductionState` / `Доступно` vs `Требуется`.

**Вывод:** «На складе» и гейт передачи смотрят на одни и те же поля, поэтому по-настоящему готовая строка не может «застрять» без причины (A) или (B). **Наиболее вероятный первопричинный дефект — дубликаты строк `POSITION_STATE` с одинаковым `Position ID`** (усиленный тем, что `v12PersistNewPositions` не обновляет `positionsByBom`, а `v12GetPositionsByBom` предпочитает устаревший `byBom`). Быстрая проверка: `PENDING_EDITS` (колонка «Ошибка») и меню «Проверка консистентности».
